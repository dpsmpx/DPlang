# Планы разработки языка: v0.x → v1.0

Как читать:

- `[+]` — сделано, `[ ]` — открыто. Версии идут по порядку; текущая —
  первая открытая.
- У версии — **ворота**: условие, без которого следующая не начинается.
  Сравнения — по порядку целей Р6 и Р25: сначала корректность, потом
  скорость разработки и токены. Критерии остановки — `docs/direction/RISKS.md`.
- Открытые решения с этой версией в сроке — `docs/direction/OPEN_DECISIONS.md`;
  их решают до соответствующего шага.
- **Срок.** Язык получает ориентировочно 1/6 рабочего ресурса автора и
  развивается параллельно VoxelRPG; календарных сроков нет, VoxelRPG
  язык не ждёт (Р21).
- **VoxelRPG.** До v1.0 основная кодовая база VoxelRPG на язык не
  переносится и его production-конвейер C++ не заменяется; можно —
  тесты, замеры, синтетические проекты, proof-of-concept и тестовые
  приложения (Р22). После v1.0 — только по Р31 и решению в
  `DECISIONS.md` VoxelRPG.
- Подробный первый план реализации (v0.0, v0.1) —
  [`IMPLEMENTATION.md`](IMPLEMENTATION.md). Definition of Done v1.0 —
  [`docs/direction/DEFINITION_OF_DONE.md`](../docs/direction/DEFINITION_OF_DONE.md).

## <a id="by-size"></a>Сложность

Метка у задач и в `TODO.md`: `М` — мелкая, быстрая, безопасная; `С` —
средняя; `Т` — тяжёлая; `К` — капитальная. Это цена и риск, а не
очередь.

## <a id="versions"></a>Версии

### [ ] v0.0. Замер до компилятора (Р24)

- `С` Эталонный набор задач с эталонами на C++ и тестами — внутренний
  материал (Р5), без кода VoxelRPG.
- `С` 2–3 варианта синтаксиса: краткие спецификации, образцовые
  программы, прототип проверки (не компилятор).
- `С` Прогон: модель решает задачи на C++ и на вариантах; правильность,
  циклы исправления, токены.
- Решения: О1 (синтаксис), О20 (токенизатор).

**Ворота:** вариант синтаксиса выбран и записан решением; критерий
остановки К-2 не сработал.

### [ ] v0.1. Ядро-срез

- `Т` Спецификация ядра в ориентире ~20 тыс. токенов (Р20).
- `К` Компилятор ядра на Linux: лексер, парсер, дерево без потерь, AST,
  модули, HIR, типы ядра, определённая инициализация, ссылки без побега,
  Core IR с верификатором, эталонный интерпретатор, C-бэкенд, runtime
  Linux, CLI `check`/`build`/`test`/`fmt`/`explain`, машиночитаемая
  диагностика.
- `С` Тесты: лексер, парсер, семантика, типы, IR, бэкенд, отказ
  компиляции, снимки диагностики, различающие (интерпретатор против
  native), фаззинг парсера.
- `С` Первая программа — CLI-инструмент на C-; первые замеры.
- Решения: О2, О3, О6–О9, О16–О18, О21.

**Ворота:** на эталонном наборе модель пишет на C- не менее корректно,
чем на C++, и тратит меньше токенов (К-2); бюджет ядра (Р-4) соблюдён.

### [ ] v0.2. Native-срез

- `Т` Цели Windows x86-64 и Android arm64: описания целей, порты
  runtime, кросс-сборка, тесты под Wine и в эмуляторе arm64.
- `Т` C ABI в обе стороны, FFI, генераторы привязок: Vulkan из
  `vk.xml`, SDL3, JNI.
- `Т` Графическая тестовая программа на трёх целях.
- `С` Класс D в компиляторе и стандартной библиотеке; межплатформенный
  повтор.
- Решения: О5, О10, О11, О23.

**Ворота:** запуск на трёх целях; повтор совпадает побитово на x86-64 и
arm64.

### [ ] v0.3. Память и параллелизм

- `Т` Исключительный изменяемый доступ, линейные ресурсы (О4 полностью).
- `Т` Стандартная библиотека: коллекции (О12), пулы и хэндлы, арены,
  кадровые аллокаторы.
- `Т` Структурные задачи, атомики, мьютекс, каналы (О13); TSan на
  сгенерированном C.
- `С` Многопоточная программа с повтором; начало программы с большими
  данными.

**Ворота:** сравнение с планом Б на эталонном наборе (К-3); нет ошибок
безопасности памяти в безопасном коде (К-4); доля `unsafe` в пределах
(Р-6).

### [ ] v0.4. Инструменты и сборка

- `Т` Пакеты, манифест, lockfile (О22, О25); инкрементальная сборка и
  кэш; проверка воспроизводимой сборки.
- `Т` Движок `fix` и механизм редакций (прототип); `query`; language
  server (диагностика, определения, ссылки, переименование).

**Ворота:** двойная сборка даёт одинаковые хэши; `fix` переводит
синтетическое изменение редакции на корпусе тестов.

### [ ] v0.5. Стабилизация спецификации

- `Т` Спецификация в объёме v1.0; тесты соответствия на каждый
  нормативный пункт.
- `Т` Фаззинг: генератор корректных программ и различающее сравнение.
- `Т` База замеров на представительных нагрузках с эталонами на C++
  (`docs/policy/BENCHMARKS.md`).
- `С` Программа с большими данными и программа с FFI.
- Решения: О14, О15.

**Ворота:** покрытие нормативных пунктов — полное; база замеров
записана; производительность — в порогах раздела G DoD или с планом.

### [ ] v0.6–v0.9. Путь к v1.0

- `К` Проект проверки (DoD, L) — первый consumer project; с его началом
  политика совместимости переходит в режим production (решение в
  `DECISIONS.md`).
- `Т` Эксперимент эволюции (DoD, J).
- `Т` Производительность (DoD, G), документация (DoD, K), прогоны
  выпуска (DoD, I).

**Ворота v1.0:** выполнены все разделы A–L DoD; решение автора.

### После v1.0

- Сравнительное исследование главной метрики (Р32; DoD, раздел 3).
- Миграция VoxelRPG — только по Р31 и решению в его `DECISIONS.md`.
