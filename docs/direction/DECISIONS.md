# Решения

Здесь записано, **что решено и почему**. Это источник истины: если
другой документ расходится с решением, прав этот документ, а
расходящийся исправляется. Решение меняется только правкой здесь — с
записью в историю (раздел 6), а не молча в другом месте.

## Какой документ за что отвечает

| документ | отвечает на вопрос |
|---|---|
| `docs/direction/DECISIONS.md` | что решено и почему |
| `docs/direction/GOAL.md` | ради чего язык и как мерить цели |
| `LICENSE` | на каких условиях существует код (Р4) |
| `ROADMAP/` | что предстоит сделать и в каком порядке |

| `TODO.md` | текущие хвосты и подтверждённый долг |
| `docs/research/` | исследования и заметки с источниками; решением не являются |
| `docs/*.md` (появятся с кодом: спецификация, устройство компилятора) | как устроено сейчас |
| `docs/archive/` | отработанное; опорой для решений не служит |

Написание синтаксиса в решениях (`!T`, `try`, `check` и т. п.) — рабочее:
решена семантика, окончательное написание — по итогам замера (Р24).

## 2. Решения

### Р0. Режим изменений языка: до и после production-кода
- **Решение.**
  - **До первого consumer project** — проекта с production-кодом на
    языке (не тестов, не замеров и не синтетических примеров) —
    разрешены быстрые изменения: синтаксис, семантику, форматы
    компилятора можно менять без совместимости.
  - **После появления production-кода** действует другой режим:
    ломающее изменение требует решения (запись здесь); по возможности
    даётся механическая миграция; компилятор поддерживает старую и новую
    редакцию (Р18); изменения проходят корпусные и регрессионные тесты;
    перед выпуском компилятора — проверка на представительном
    consumer project.
- **Цель режима.** Не обещать невозможное «никогда не менять код
  потребителя», а сделать изменение языка настолько контролируемым,
  чтобы основная стоимость изменения лежала в компиляторе и
  инструментах, а не в ручном переписывании крупного consumer project.
- **Почему.** До потребителя совместимость — только тормоз; после —
  требование автора. Основание — правило VoxelRPG «совместимость в
  разработке не нужна» (его Р0, переносится по Р3), требование Р2 и
  решение автора 3 октября 2026 (вторая запись в истории).

### Р1. Главная задача
- **Решение.** Свой язык: краткость синтаксиса и упор на работу с ИИ;
  экономия токенов, скорость сборки, надёжность, проверяемость.
  Совместимость с другими языками по синтаксису — не цель. Подробно и с
  мерами — `docs/direction/GOAL.md`. Порядок целей при конфликте — Р6.
  Решение автора 3 октября 2026.
- **Рассмотрено и отклонено:** диалект, синтаксически идентичный C++20 и
  совместимый с его компиляторами (постановка того же дня).

### Р2. Требования к результату
- **Решение.** Язык:
  - предназначен для продолжения разработки VoxelRPG — после v1.0 и
    только по решению в `DECISIONS.md` VoxelRPG (Р22);
  - понятен ИИ (Claude) без проблем;
  - собирает реальные приложения для конечных устройств (у VoxelRPG —
    Android arm64 и Windows x64);
  - меняется так, что основная стоимость изменения лежит в компиляторе
    и инструментах: коду потребителя нужны в худшем случае небольшие и
    по возможности механические правки (Р0, Р18).
  Решение автора 3 октября 2026.

### Р3. Инженерная культура VoxelRPG
- **Решение.** В репозиторий переносится инженерная культура VoxelRPG и
  лучшие практики по исследованию: источник истины — этот файл с
  историей; `ROADMAP/` и `TODO.md`; правила агента в `CLAUDE.md`; коммит
  и пуш после каждого законченного куска; PR в `main` — сразу,
  черновиком; проверки — целевые после задачи, полные перед вливанием;
  поиск секретов; CI в пределах минут закрытого репозитория; хук начала
  сессии. Решение автора 3 октября 2026.
- **Уточнение (4 октября 2026): GitHub Actions не используется.** Слово
  автора: «Перестань использовать GitHub Actions». Workflow в
  репозитории нет; проверки — `tools/check/run.sh` нужного уровня в
  сессии, итог полного прогона — в описании PR; состояние Actions не
  проверяется и не ожидается. Где решения и политики говорят «CI», это
  такой прогон, пока автор не решит иначе (свой раннер или другая
  система — только по его решению).
- **Как устроено.** `CLAUDE.md`, `tools/check/`, `.claude/`.
- **Уточнение (постановка 3 октября 2026).** Структура документации —
  `docs/README.md`: видение и решения (`docs/direction/`), проект
  архитектуры и языка (`docs/design/`, затем `docs/spec/` и описание
  устройства), политики (`docs/policy/`: совместимость, детерминизм,
  тесты, замеры, платформы, инженерия, безопасность, выпуск), аудиты
  (`docs/audits/`), планы (`ROADMAP/`), хвосты (`TODO.md`), вехи
  (`docs/CHANGELOG.md`). Принципы: планирование до реализации,
  маленькие проверяемые изменения, работа через PR, обязательные
  проверки, запись архитектурных решений, регулярные аудиты, устранение
  долга, никаких скрытых незаписанных решений; `TODO.md` — только
  незавершённое и подтверждённый долг; CHANGELOG не заменяет описание
  устройства.
- **Критерий качества документации.** По документам другой ИИ-агент или
  разработчик может: понять архитектуру; найти нужный компонент; понять
  контракт; внести изменение; запустить правильные проверки;
  истолковать результат. Документация — часть инженерной системы, а не
  архив истории.

### Р4. Лицензия — проприетарная
- **Решение.** Unlicense снят. Исходный код языка, компилятора, runtime,
  инструментов и других собственных компонентов в общественное
  достояние не передаётся. `LICENSE` — временная редакция: все права у
  правообладателя; на исходный код, двоичные файлы, SDK и инструменты и
  на распространение права не предоставляются без письменного
  разрешения; сторонние компоненты — под своими лицензиями
  (`docs/THIRD_PARTY.md`, уведомления — в поставке, когда она
  появится). Решение автора 3 октября 2026.
- **Почему.** Язык — самостоятельный интеллектуальный актив и
  возможная основа коммерческих продуктов и будущих проектов.
- **Дальше.** Окончательный текст — с юристом по интеллектуальной
  собственности, но не сейчас: до тех пор действует временная редакция,
  в том числе для production-кода компилятора (слово автора, 3 октября
  2026). Ранние версии репозитория с Unlicense посторонним не
  показывались и не передавались: репозиторий приватный с создания
  (слово автора, 3 октября 2026).
- **Уточнение (решение автора 3 октября 2026, позднее).** Модель
  лицензирования проектируется сейчас, а не после v1.0: что
  лицензируется и на каких условиях — компилятор и инструменты, runtime
  и стандартная библиотека, генерируемый код, привязки, документация и
  спецификация; права на исходники, двоичные файлы и SDK по
  отдельности; коммерческое использование; патенты, товарный знак,
  вклады, смена условий между версиями. Результат — исследование и
  спецификация будущей лицензии (`docs/research/LICENSING.md`). Модель
  принята — Р39; текст `LICENSE` пишется по ней и после проверки
  юристом. До тех пор
  действует временная редакция. Закрытость до v1.0 (Р5) не меняется:
  выбор модели не означает открытия или распространения чего-либо.
- **Рассмотрено и отклонено:** Unlicense; открытые лицензии на этапе
  разработки; отложить проектирование модели до v1.0 (прежняя редакция
  этого решения).

### Р5. Проект закрытый
- **Решение.** Репозиторий остаётся private. До v1.0 не публикуются:
  исходники; внутреннее устройство компилятора; runtime; IR; внутренняя
  документация; история разработки; внутренние наборы замеров (в том
  числе эталонный набор задач); материалы с закрытой информацией
  VoxelRPG. Решение автора 3 октября 2026.
- **Почему.** Защита интеллектуальной собственности; кроме того, до
  v1.0 язык — R&D: без обязательств перед внешними пользователями, без
  публичной совместимости незрелых API, без раскрытия незавершённых
  архитектурных решений и без внешнего цикла обратной связи.
- **Дальше.** Открытие части проекта, open-core, community edition,
  публикация двоичных файлов или другая модель после v1.0 — отдельное
  решение. Закрытость сейчас обязательна; модель после v1.0 — открытый
  вопрос.

### Р6. Порядок целей при конфликте
- **Решение.** Приоритет — по уровням; внутри уровня — по номеру.
  - **Уровень 1 — обязательные свойства.**
    1. Корректность и надёжность: язык не ускоряет разработку ценой
       снижения корректности.
    2. Детерминированность и воспроизводимость: для заявленной
       детерминированной части одинаковые входы дают одинаковый
       результат (Р12).
    3. Контролируемость поведения и ресурсов: память, время выполнения,
       выделения памяти, параллелизм, FFI, платформозависимое
       поведение.
    4. Долгосрочная эволюционируемость: изменения языка и компилятора
       по возможности не заставляют переписывать consumer project
       (Р0, Р18); особенно — после начала использования в VoxelRPG.
  - **Уровень 2 — производственные свойства.**
    5. Проверяемость: компилятор ловит как можно больше ошибок до
       запуска.
    6. Скорость разработки: после требований выше язык реально
       уменьшает стоимость изменений.
    7. Скорость цикла обратной связи и сборки: `check` и локальные
       проверки быстрые, глубокие — в CI.
    8. Удобство разработки с ИИ: Claude и другие агенты лучше понимают
       проект, выдают меньше ошибочных изменений и эффективнее их
       исправляют.
  - **Уровень 3 — вторичные свойства.**
    9. Простота языка и инструментов: не добавлять возможность только
       потому, что она интересна.
    10. Эргономика и удобство синтаксиса — не ценой требований выше.
    11. Переносимость: архитектура поддерживает целевые native-платформы,
        но переносимость не ломает модель языка.
- **Правила применения.**
  - Две возможности на одном уровне — предпочитать более простую.
  - Возможность, которая ускоряет разработку, но ухудшает
    детерминизм, повышает вероятность ошибок, создаёт скрытое
    поведение, резко усложняет компилятор или ухудшает долгосрочную
    совместимость, в текущем виде не принимается.
- **Принцип.** «Надёжность и контролируемость ограничивают дизайн, а
  скорость разработки оптимизируется внутри этих ограничений.»
- **Связь с Р1 и Р2.** Краткость синтаксиса и экономия токенов — меры
  целей 6–8 и 10, а не самостоятельные цели выше уровня 1. Требование Р2
  «понятен ИИ» — цель 8: при конфликте уступает целям 1–7.
  Решение автора 3 октября 2026.

### Р7. Синтаксис (П1)
- **Решение.** Знакомый, короткий, однозначный синтаксис: фигурные
  скобки, короткие английские ключевые слова, один канонический формат
  (форматировщик — часть инструментов, настроек стиля нет).
  - Грамматика однозначная; разбор не зависит от информации о типах и
    объявлениях (в отличие от C++). Класс грамматики — в спецификации.
  - Пользовательских макросов, меняющих грамматику, нет.
  - Пользовательской перегрузки операторов на первом этапе нет;
    операторы над встроенными типами (в том числе векторами и
    матрицами, Р8) определяет язык.
  Решение автора 3 октября 2026.

### Р8. Типы (П2)
- **Решение.** Статическая типизация.
  - Явные типы — на границах: сигнатуры функций, публичные объявления,
    поля типов, глобальные константы. Внутри тел функций — вывод типов,
    локальный в пределах функции (глобального вывода нет).
  - Встроенные типы: целые фиксированной ширины 8/16/32/64 бит со знаком
    и без знака и целое размера адреса для индексов и длин; `f32` и
    `f64` (IEEE 754 binary32/binary64); `bool`; строки; срезы
    (представления без владения: адрес и длина); массивы фиксированной
    длины; векторы, матрицы и кватернионы; тип «может не быть»
    (единственный способ выразить отсутствие значения — неявного null
    нет); тип «значение или ошибка» (Р10); суммы типов с `match`, полноту
    которого проверяет компилятор.
  - Обобщённые типы — ограниченной мощности: параметры — типы и
    константы времени компиляции; ограничения задаются явно; без
    специализации и без вычислений на уровне типов. Сложной системы
    метапрограммирования над типами нет.
- **В спецификации.** Кодировка и представление строк; правила
  числовых преобразований (предложение: неявные — только расширяющие
  без потерь); способ реализации обобщённых типов и его цена для сборки
  (по замеру, Р24); точность векторной математики (`f32`, `f64` — по
  замеру).
  Решение автора 3 октября 2026.

### Р9. Память (П3)
- **Решение.** Сборщика мусора нет; проверка заимствований Rust не
  копируется автоматически. Базовая модель:
  - явные аллокаторы;
  - арены;
  - хэндлы с поколением: обращение по устаревшему хэндлу обнаруживается
    проверкой поколения, а не даёт неопределённое поведение;
  - краткоживущие ссылки;
  - явные границы `unsafe` (Р11).
- **Принцип.** «Необязательно иметь borrow checker, но обычный код не
  должен легко позволять получить use-after-free, dangling reference или
  невалидный ownership state.»
- **Открыто до спецификации.** Какие дополнительные статические
  гарантии нужны. Кандидаты: ссылка не переживает область, где создана
  (не хранится в полях и глобальных данных, не возвращается из функции);
  исключительность изменяемого доступа к параметрам (против
  инвалидации итераторов и срезов); правила освобождения арены. Решение —
  по исследованию и замеру (Р24).
  Решение автора 3 октября 2026 (принято с осторожностью).

### Р10. Ошибки (П4)
- **Решение.** Ошибка — значение: тип «значение или ошибка» (`!T`),
  передача выше (`try`), очистка (`defer`, `errdefer`). Исключений и
  раскрутки стека нет. Молчаливо проигнорировать ошибку нельзя:
  компилятор требует обработать её или отбросить явной, видимой в коде
  конструкцией. Решение автора 3 октября 2026.

### Р11. Нет неопределённого поведения в обычном коде (П5)
- **Решение — фундаментальный принцип.** В коде вне `unsafe`:
  - использование переменной до инициализации — ошибка компиляции;
  - индексация массивов, срезов и строк проверяется по границам;
  - переполнение целочисленной арифметики обнаруживается; заворачивание
    и насыщение — только явными операциями; деление на ноль и сдвиг на
    ширину типа и больше обнаруживаются;
  - порядок вычислений однозначно определён спецификацией;
  - плавающая точка — по IEEE 754, без «быстрой математики» по
    умолчанию (Р12).
  - Обнаруженное нарушение не продолжает выполнение с неопределённым
    состоянием; механизм (остановка с диагностикой или ошибка-значение)
    — в спецификации.
- **`unsafe`** не запрещён, но локализован и видим: явно помеченные
  блоки или функции; что разрешено внутри (сырые адреса, обращение без
  проверки, переинтерпретация памяти, вызов внешнего кода) —
  перечислено в спецификации; компилятор выдаёт перечень `unsafe`-мест
  модуля. Отключение проверок — только так: глобального режима сборки
  «без проверок» по умолчанию нет.
  Решение автора 3 октября 2026.

### Р12. Детерминизм — свойство языка (П6)
- **Решение.** Код формально делится на **детерминированный** (явно
  помеченный: модуль или функция) и **недетерминированный или
  платформозависимый**. Компилятор проверяет, что детерминированный код
  не обращается к недетерминированному; данные извне попадают в него
  только явно, через параметры.
- **Исключаемые источники недетерминизма** в детерминированном коде:
  - **время** — нет доступа к часам;
  - **случайность** — только детерминированный генератор, состояние или
    ключ которого передаётся явно; общего изменяемого генератора нет;
  - **порядок обхода** — у контейнеров определён и не зависит от адресов
    и случайной соли хэша;
  - **параллелизм** — результат не зависит от планирования потоков
    (только детерминированное объединение результатов);
  - **внешний ввод-вывод** — нет;
  - **значения адресов** — не влияют на результат;
  - **плавающая точка** — только операции IEEE 754 с корректным
    округлением (сложение, вычитание, умножение, деление, квадратный
    корень); без слияния в FMA, кроме явного вызова; без «быстрой
    математики»; без смены режима округления и сброса денормалов;
    трансцендентные функции — собственные реализации стандартной
    библиотеки, а не платформенная libm.
- **Область гарантии.** Одинаковые входы (включая зерно) дают одинаковый
  результат при одной редакции языка и одной версии стандартной
  библиотеки. Цель — побитовое совпадение между поддерживаемыми
  платформами (arm64, x86-64), проверяемое межплатформенными тестами
  повтора; точная формулировка гарантии — в спецификации.
  Решение автора 3 октября 2026.

### Р13. Проверяемость (П7)
- **Решение.** Контракты (`pre`, `post`, `assert`), тесты в языке,
  expect-тесты, фаззинг и проверка свойств, детерминированный повтор —
  часть production-инструментов. По умолчанию — дешёвые автоматические
  проверки (`check`, `test`); глубокие (длинный фаззинг, долгие повторы)
  — в CI. Контракты проверяются во время выполнения в отладочной и
  безопасной сборке; статически — там, где компилятору это дёшево.
  Язык не превращается в систему доказательства теорем.
  Решение автора 3 октября 2026.

### Р14. Модули (П8)
- **Решение.** Модуль — единица компиляции и видимости. Заголовочных
  файлов как основного интерфейса нет. Публичный интерфейс помечается
  явно; компилятор выводит из него машиночитаемую сводку, которую
  используют компилятор (зависимые модули собираются по сводке), IDE и
  инструменты, ИИ-агенты. Циклическая зависимость модулей — ошибка
  компиляции. Решение автора 3 октября 2026.

### Р15. Команды инструментов (П9)
- **Решение.** `check`, `build`, `test`, `fmt`, `fix`, `explain`,
  `query`. Обязателен машиночитаемый режим диагностики (формат — в
  спецификации). Цели по времени (например, `check` за десятки
  миллисекунд на модуль) — целевые показатели замеров, а не обещанные
  заранее свойства: назначаются после реальных замеров.
  Решение автора 3 октября 2026.

### Р16. Архитектура компилятора и бэкенды (П10)
- **Решение.** Конвейер: **фронтенд → IR → интерфейс бэкенда →
  C-бэкенд**.
  - IR не зависит от цели, его семантика определена без неопределённого
    поведения и достаточна для второго бэкенда (LLVM или другого
    native).
  - C-бэкенд — первый практический (bootstrap). Генерируемый C
    максимально исключает зависимость от неопределённого поведения C и
    от особенностей конкретного компилятора C; целевые компиляторы —
    clang из Android NDK, clang поверх MinGW-w64; MSVC — цель,
    проверяется отдельно.
  - Собственный сложный оптимизирующий бэкенд — только если замер
    докажет необходимость.
  Решение автора 3 октября 2026.

### Р17. Взаимодействие через C ABI (П11)
- **Решение.** C ABI обязателен: вызов C из языка; вызов языка из C;
  стабильное представление типов, помеченных для C ABI (раскладка — как
  у C на целевой платформе; у остальных типов гарантии раскладки нет);
  генерируемые заголовки C для экспортируемого; правила безопасности
  FFI (вызов внешнего кода — граница `unsafe`, кроме объявлений,
  признанных безопасными по правилам спецификации). Привязки Vulkan,
  SDL3, JNI и других — машинно генерируемые, где это оправдано.
  Шаблоны C++ напрямую не поддерживаются; C++ — только через C ABI.
  Решение автора 3 октября 2026.

### Р18. Эволюция языка (П12)
- **Решение.** Механизм редакций обязателен: отметка редакции или
  версии — в манифесте модуля; модули разных редакций собираются
  вместе. Каждое ломающее изменение по возможности сопровождается:
  отметкой редакции; миграцией в компиляторе; `fix --edition`;
  инструментами модернизации; регрессионными тестами. После появления
  production-кода требования строже (Р0).
  Решение автора 3 октября 2026.

### Р19. Стандартная библиотека (П13)
- **Решение.** Маленькая. Приоритет: коллекции, строки,
  форматирование, математика, хэндлы, арены, задачи и параллелизм,
  сериализация, TOML, журнал, тестирование. Игровой движок в неё не
  входит. ECS и другие специализированные механизмы — кандидаты:
  окончательный статус — по фактическому использованию и цене
  поддержки. Решение автора 3 октября 2026 (принято с ограничением).

### Р20. Спецификация (П14)
- **Решение.** Спецификация компактная и хорошо индексируемая. 20 тыс.
  токенов — ориентир, а не догма: если для корректности нужно немного
  больше, спецификацию не ухудшают ради цифры.
- **Принцип.** «Claude должен получать достаточно информации для
  корректного действия без необходимости читать десятки тысяч строк
  документации.» Решение автора 3 октября 2026.

### Р21. Срок относительно VoxelRPG
- **Решение.** Язык развивается параллельно VoxelRPG и не блокирует
  его. На язык — ориентировочно 1/6 рабочего ресурса автора; VoxelRPG —
  основная production-линия. Календарного требования нет: версия 1
  VoxelRPG язык не ждёт, язык не обязан завершиться к версии 1 VoxelRPG.
  Приоритет до первого выпуска VoxelRPG — по `DECISIONS.md` VoxelRPG.
  До v1.0 язык развивается независимо. Решение автора 3 октября 2026.

### Р22. Когда язык можно использовать в VoxelRPG
- **Решение.** До v1.0 основная production-кодовая база VoxelRPG на язык
  не переносится. Можно: независимые тесты компилятора, проекты-замеры,
  небольшие синтетические проекты, отдельные proof-of-concept,
  тестовые приложения для native-целей. После v1.0 решение о переносе
  конкретной части VoxelRPG принимается только в
  `docs/direction/DECISIONS.md` VoxelRPG; этот репозиторий решений за
  VoxelRPG не принимает. Решение автора 3 октября 2026.
- **Уточнение (постановка 3 октября 2026).** До v1.0 также нельзя:
  заменять существующий production-конвейер C++ VoxelRPG; ломать
  `ROADMAP` VoxelRPG; добавлять в язык возможность только потому, что
  она понадобилась одной временной интеграции. Можно: экспериментальные
  ветки интеграции и небольшие proof-of-concept — они не становятся
  обязательной частью VoxelRPG и создаются в его репозитории по его
  правилам.

### Р23. Что означает v1.0
- **Уточнение (постановка 3 октября 2026).** Полный Definition of Done —
  `docs/direction/DEFINITION_OF_DONE.md` (разделы A–L: спецификация,
  компилятор, native-приложения, взаимодействие, детерминизм,
  надёжность, производительность, инструменты, сборка и выпуск,
  эволюция, документация, проверка на реальном проекте) — с
  измеримыми критериями и способом проверки; он заменяет перечень ниже
  как рабочий. «Опубликованная спецификация» в постановке автора здесь
  значит выпущенная, версионированная и внутренне согласованная;
  публикация наружу — отдельное решение (Р5).
- **Решение.** v1.0 — не «есть все задуманные возможности», а:
  стабильная базовая спецификация; компилятор production-качества;
  native-приложения на реальных целевых платформах; C ABI;
  гарантии детерминизма; тестовая инфраструктура; фаззинг;
  регрессионный набор; диагностика; форматировщик; инструменты сборки
  и тестов; документированные runtime и ABI; воспроизводимые сборки;
  политика совместимости; возможность эволюции языка без постоянного
  переписывания consumer code; успешная проверка на крупном
  production-style проекте. VoxelRPG не обязан быть первым таким
  проектом. Решение автора 3 октября 2026.

### Р24. Решения о языке — по замеру
- **Решение.** Архитектура языка не выбирается только по вкусу: там,
  где решение можно измерить на реальной задаче, сначала ставится
  эксперимент, затем принимается решение. Поэтому после решений по П
  следующий этап — эталонный набор задач и опыт с 2–3 вариантами
  синтаксиса, а не код компилятора (`ROADMAP/ROADMAP.md`).
  Решение автора 3 октября 2026.


### Р25. Ценности языка (уточнение Р6)
- **Решение.** Ценности автора по порядку: корректность;
  предсказуемость; детерминированность там, где она заявлена;
  статическая проверяемость; безопасность работы с памятью и ресурсами;
  контролируемая производительность; удобство сопровождения; качество
  диагностики; скорость разработки; удобство разработки с ИИ. Скорость
  разработки достигается не отказом от строгих гарантий.
- **Как сочетается с Р6.** Порядок между уровнями задаёт Р6; Р25 уточняет
  состав и порядок внутри уровней (таблица — `docs/direction/VISION.md`,
  раздел 3). Различие: у автора статическая проверяемость стоит выше
  безопасности памяти и контролируемой производительности; по Р6
  безопасность памяти — часть корректности, контролируемая
  производительность — часть контролируемости (оба — уровень 1),
  проверяемость — уровень 2. На практике они не конкурируют:
  проверяемость — главный способ обеспечить безопасность памяти.
  Решение автора 3 октября 2026; сочетание с Р6 подтверждено автором
  в тот же день.

### Р26. Граница стабильности и политика совместимости
- **Решение.** Конвейер: исходник → лексер и парсер → AST → HIR
  (типизированное представление) → Core IR → оптимизация → бэкенд →
  runtime и ABI → native-программа или пакет. Каждый артефакт отнесён к
  классу стабильности:
  - **S0 — стабильный контракт для пользователя:** исходный язык в
    пределах редакции; публичный API стандартной библиотеки в пределах
    её мажорной версии; C ABI объявлений `extern`; форматы данных
    стандартной сериализации; форматы манифеста пакета и lockfile;
    схема машиночитаемой диагностики и коды ошибок.
  - **S1 — версионированный внутренний контракт:** Core IR (граница
    фронтенда и бэкендов, со спецификацией и верификатором); контракт
    компилятора и runtime; сводки интерфейсов модулей.
  - **S2 — нестабильная реализация:** AST, HIR, оптимизации, генерация
    кода, сгенерированный C, внутреннее устройство runtime и
    стандартной библиотеки, кэши и объектные файлы.
- **Правила.** Изменение реализации компилятора не означает
  переписывания проекта: S2 и S1 меняются без изменения исходников
  потребителя. Стабильного ABI между модулями, собранными разными
  версиями компилятора, нет: программа собирается одной версией, runtime
  и стандартная библиотека линкуются статически. Без пересборки
  меняются только данные, конфигурация и внешние библиотеки за C ABI.
  Сохранённые данные не зависят от раскладки типов в памяти и версии
  компилятора. Абсолютной обратной совместимости нет: что гарантируется,
  что допускается как ломающее изменение и как это проверяется —
  `docs/policy/COMPATIBILITY.md`; устройство — `docs/design/ARCHITECTURE.md`.
  Решение автора 3 октября 2026 (граница и требование политики);
  классификация S0–S2 и правила — запись сессии по поручению автора.

### Р27. Назначение языка
- **Решение.** Системный язык общего назначения с сильной ориентацией
  на разработку игр и движков. Не DSL, не экспериментальный язык и не
  скриптовый слой; программы — native-приложения, а не программы внутри
  интерпретатора. Пригодность проверяется на подсистемах уровня
  VoxelRPG: рендер, Vulkan и платформа, мир и чанки, процедурная
  генерация, сущности и ECS, игровая логика, ИИ, физика, сохранение и
  сериализация, интерфейс, ввод, звук, многопоточность и система задач,
  инструменты, тесты, замеры (`docs/direction/VISION.md`, раздел 5).
  Решение автора 3 октября 2026.

### Р28. Платформы первой волны
- **Решение.** Linux x86-64 (хост и цель), Windows x86-64, Android
  arm64. Архитектура допускает позже iOS, другие настольные цели и
  другие цели ARM и x86-64. Платформозависимый код — только за явно
  определёнными границами (описание цели, runtime под ОС, модуль
  `platform` стандартной библиотеки, объявления с атрибутом цели); язык
  и компилятор не содержат повсеместных платформенных исключений.
  Уровни поддержки — `docs/policy/PLATFORMS.md`. Решение автора 3
  октября 2026.

### Р29. Классы поведения и воспроизводимость (уточнение Р12)
- **Решение.** Поведение формально делится на четыре класса:
  гарантированно детерминированное; определяемое реализацией;
  платформозависимое; намеренно недетерминированное. Правила для
  числовых типов, плавающей точки, случайности, порядка обхода,
  хэш-таблиц, параллелизма и планирования задач, сериализации, времени
  и внешнего ввода-вывода, а также определения воспроизводимой сборки и
  воспроизводимого выполнения игровых систем —
  `docs/policy/DETERMINISM.md`. Слово «детерминированный» применяется
  только в смысле этого документа. Решение автора 3 октября 2026.

### Р30. Сосуществование с C и C++
- **Решение.** Практичная интеграция с native-миром обязательна: C ABI,
  вызов C API, native-структуры, обратные вызовы и указатели на функции,
  двоичная раскладка, границы владения, правила безопасности FFI,
  Vulkan и платформенные SDK. C++ — там, где действительно нужен, через
  C-прослойку (`extern "C"`), а не через ABI C++ (Р17). Архитектура
  допускает смешанный код C++ и dpl в одной программе; мгновенная
  полная миграция не предполагается. Устройство —
  `docs/design/LANGUAGE.md`, раздел 5. Решение автора 3 октября 2026.

### Р31. Условия начала миграции VoxelRPG
- **Решение.** После v1.0 миграция начинается только после отдельного
  решения и аудита в `DECISIONS.md` VoxelRPG. Для первой миграции нужно
  доказать: качество не хуже; производительность и поведение памяти
  приемлемы; детерминизм сохранён; отладка не хуже; CI и выпуск не менее
  надёжны; production-разработка действительно ускоряется. Миграция —
  постепенная, со смешанным кодом C++ и dpl (Р30). Измеримые пороги —
  `docs/direction/DEFINITION_OF_DONE.md`, раздел 2. Решение автора 3
  октября 2026.

### Р32. Главная метрика успеха
- **Решение.** Главный показатель — сколько production-работы можно
  выполнить быстрее при том же или более высоком уровне качества,
  надёжности, контролируемости и предсказуемости; не число
  возможностей, строк компилятора или сложность системы типов. После
  v1.0 — сравнительное исследование на реальных задачах: текущий
  процесс на C++ против dpl и его инструментов (время реализации,
  плотность ошибок, регрессии, усилия на тесты, объём кода, усилия на
  ревью, цена рефакторинга, время сборки, производительность, усилия на
  отладку, успешность ИИ-агента). Протокол —
  `docs/direction/DEFINITION_OF_DONE.md`, раздел 3. Решение автора 3
  октября 2026.

### Р33. Главный принцип проекта
- **Решение.** «Сначала спроектировать систему, способную десятилетиями
  эволюционировать. Затем реализовать минимальное ядро, доказать его на
  реальных программах, довести до v1.0 и только после этого
  использовать его как production-язык для VoxelRPG.» Реализация
  начинается после проектирования и аудита плана

### Р34. Язык реализации компилятора (О16)
- **Решение.** C++20 в подмножестве VoxelRPG: без исключений и RTTI,

### Р35. Как меряется работа ИИ на этапе v0.0 (О20)

  сессии автора.

### Р36. Нарушение проверки — ловушка (О3)
- **Решение.** Выход за границы, переполнение, нарушенный контракт,
  `unreachable`, ложный `assert` — детерминированная остановка с местом
  и кодом ошибки (в отладке — стек вызовов). Программа может
  зарегистрировать обработчик аварии (отчёт, журнал), но не продолжить
  выполнение. Уточняет Р11. Решение автора 3 октября 2026.
- **Рассмотрено и отклонено:** нарушение как ошибка-значение (каждое
  индексирование становится источником ошибок); перехват ловушки
  областью задачи с отменой только задачи (сложнее runtime, риск
  продолжить с повреждённым состоянием).

### Р39. Модель лицензирования
- **Решение.** Раздельно лицензируются четыре объекта:
  1. **toolchain** — компилятор и инструменты; распространение
     контролирует правообладатель;
  2. **runtime-компоненты** — runtime, стандартная библиотека и код,
     который вставляет компилятор; встраиваются в любые программы без
     уведомлений и без раскрытия исходников;
  3. **вывод** — всё, что toolchain производит из входа пользователя;
     принадлежит пользователю, вкрапления правообладателя лицензируются
     безотзывно;
  4. **программы пользователя** — лицензия dpl их не покрывает.

  Денег с пользователей не берётся: ни роялти, ни порогов выручки, мест
  и ключей; условия одинаковы для всех и для любых целей. Монетизация,
  если понадобится, — только отдельными соглашениями (поддержка,
  сертификация). Решение автора 3 октября 2026.
- **Этапы.**
  - **Этап 0 — сейчас и до первой передачи чего-либо третьим лицам.**
    Действует временная редакция `LICENSE` (Р4). Работают правила
    `docs/policy/LICENSING.md`: карта компонентов, допуск стороннего
    кода, вклады, учёт человеческого вклада, имя.
  - **Этап 1 — к первой передаче двоичной поставки кому-либо вне
    автора.** Одна собственная проприетарная «Лицензия dpl SDK» по
    спецификации `docs/research/LICENSING.md`, раздел 21, после проверки
    юристом. Передача до v1.0 — дополнительно с договором о
    конфиденциальности (Р5).
  - **Этап 2 — после v1.0, отдельным решением по Р5.** Runtime-компоненты
    или весь toolchain — под Apache-2.0 WITH LLVM-exception, контроль —
    товарным знаком и официальной поставкой; или этап 1 остаётся.
- **Условия Лицензии dpl SDK** (ответы автора 3 октября 2026):
  - официальную поставку без изменений, вместе с лицензией и не за плату
    может распространять любой: зеркала, образы CI и контейнеров,
    менеджеры пакетов, онлайн-песочницы;
  - «организация лицензиата» включает лиц под общим контролем;
  - патентная лицензия покрывает нынешние и будущие патенты
    правообладателя, неизбежно нарушаемые разрешённым использованием;
    защитное прекращение — только патентной лицензии и только для того,
    кто заявил, что toolchain, runtime-компоненты или вывод нарушают
    патент;
  - поставка toolchain в составе чужого продукта для его пользователей
    (моды, редакторы движков) и функции toolchain как услуга для третьих
    лиц — по письменному разрешению; общая норма — новой версией
    лицензии, если случаев станет много;
  - использование с ИИ-ассистентами разрешено всегда; обучение моделей
    на поставке после v1.0 не запрещается;
  - условия выпущенной версии бессрочны и не ухудшаются; новые версии
    могут иметь новые условия;
  - применимое право — РФ (правообладатель — резидент РФ); суд и право
    для иностранных лицензиатов — с юристом. Срок, территория, способы
    использования и безвозмездность называются прямо (ГК РФ, ст. 1235,
    1286, 1286.1).
- **Знак и вклады.** Имя dpl — отдельной политикой товарного знака, не
  лицензией; до публичного использования имени — проверка у поверенного.
  Внешние вклады — только после договора с правом перелицензирования
  (CLA) или отчуждения прав (подрядчики).
- **Почему.** Язык как таковой авторским правом не охраняется (ГК РФ,
  ст. 1259 п. 5); ценность и контроль — в реализации и имени.
  Пользователи не должны получать обязательств из-за инструмента: так
  устроены GCC, LLVM, Swift, Android SDK, CUDA. Открыть можно всегда,
  закрыть открытое — нельзя. Исследование и источники —
  `docs/research/LICENSING.md`.
- **Рассмотрено и отклонено:** copyleft (GPL, LGPL, AGPL, MPL), в том
  числе с исключением для runtime; лицензии с доступными исходниками
  (BSL, FSL, Elastic, PolyForm) для toolchain до v1.0; двойное
  лицензирование; Unlicense и общественное достояние; собственная
  лицензия «на всё»; пороги выручки и роялти; разрешительная лицензия на
  двоичные файлы без исходников; запрет обучения ИИ.
- **Unlicense.** Текст Unlicense в первых коммитах — шаблон по умолчанию
  при создании репозитория; никому не предлагался и не передавался
  (репозиторий приватный с создания, участник один); кода компилятора в
  тот период не было. История не переписывается.

### Р40. Синтаксис — вариант B (О1)
- **Решение.** Запись языка — вариант B опыта v0.0
  (`docs/research/syntax/spec_B.md`):
  - конец инструкции — конец строки;
  - тип результата без стрелки: `fn f(x: i32) i32`; имя и тип —
    `x: i32`;
  - режимы параметров `&T` и `&mut T` с той же пометкой у аргумента:
    `f(&mut w)`;
  - ошибка в сигнатуре — `!T`;
  - вариант перечисления — `.V`, если тип ясен из окружения, иначе
    `E.V`;
  - переменные — `let` (неизменяемая) и `var`; `if let v = opt`;
  - атрибуты — `@det`.

  Решение автора 4 октября 2026 по опыту
  `docs/audits/2026-10-04-syntax-experiment.md`.
- **Почему.** Правильность всех трёх вариантов равна C++: 56 из 56 с
  первой попытки, К-2 не сработал. B на 22% короче C++ в решениях модели
  и на 4,5% короче A по записи. От C отличается на 1–3%, но сохраняет
  пометку изменения у аргумента и неизменяемые переменные —
  проверяемость и контролируемость, уровень 1 Р6.
- **Пересмотр.** Объём сравнивался в символах: ключа для точного счёта
  (Р35) не было. Когда ключ появится, прогон `r1` пересчитывается в
  токенах (`bench/experiment.py restore r1`, затем `tokens r1`). Если
  другой вариант окажется заметно дешевле B — больше разброса двух
  прогонов, — вопрос возвращается автору; иначе решение остаётся.
  Решение автора 4 октября 2026.
- **Не решено здесь.** Опыт покрыл подмножество языка. Запись
  остального ядра — в стиле B, в спецификации ядра (Р20). Именованные
  множества ошибок в публичных сигнатурах — О2; числовые преобразования
  — О8; расширение файлов — П15 (Р38).

### Р41. Ошибки в сигнатурах (О2)
- **Решение.** Тип ошибки — объявленное перечисление ошибок.
  - Публичная функция пишет его в сигнатуре: `pub fn read(s: str)
    ReadError!str`.
  - Непубличная функция может писать `!T`: тип ошибки выводится из
    `fail` и `try` в её теле.
  - Правило вывода — в спецификации ядра.

  Решение автора 4 октября 2026.
- **Почему.** Сводка модуля (S1, Р14, Р26) не меняется от правки тела
  функции: новая ошибка в публичной функции видна в её сигнатуре.
  Краткость записи B (Р40) сохраняется внутри модуля, где интерфейс не
  стабилен.
- **Рассмотрено и отклонено:**
  - везде `!T` с выводом — правка тела молча меняет публичный
    интерфейс;
  - везде явный `E!T` — длиннее без выигрыша внутри модуля.

### Р42. Типы ядра (О6–О9)
- **Решение.**
  - **Обобщённые типы (О6)** — мономорфизация с удалением дублей и
    кэшем по модулям. В v0.1 — только встроенные обобщённые: `List[T]`,
    `?T`, `!T`, `[]T`. Пользовательские обобщённые — когда они
    понадобятся программе (`docs/policy/ENGINEERING.md`, раздел 2).
  - **Вычисления при компиляции (О7)** — только константы и чистые
    функции без ввода-вывода, с лимитом шагов; вычислений над типами
    нет (Р8). В v0.1 — только константы из константных выражений.
  - **Числовые преобразования (О8):**
    - неявно — только расширяющие, без потерь;
    - `T(x)` — проверяемое преобразование: ловушка, если значение не
      помещается (Р36);
    - `T.wrap(x)` — с заворачиванием по модулю 2^n.
  - **Строки (О9)** — UTF-8, длина в байтах. Данные извне проверяются
    на UTF-8 при входе.

  Решение автора 4 октября 2026.
- **Почему.** Рекомендации сессии из `OPEN_DECISIONS.md`. Объём ядра
  v0.1 — по нужде программ v0.1 (Р-4, бюджет ядра).
- **Рассмотрено и отклонено:**
  - обобщённые через стирание типов или словари — цена во время
    выполнения;
  - неявные сужающие преобразования — тихая потеря значения (Р11).

### Р43. Устройство компилятора v0.1 (О17, О18, О21, О26)
- **Решение.**
  - **Эталонный интерпретатор Core IR (О17)** — только для тестов:
    оракул различающих тестов и детерминизма; в production-пути его
    нет.
  - **Отладка (О18)** — `#line` в сгенерированном C. DWARF и PDB
    напрямую — только со вторым бэкендом.
  - **Связывание (О21)** — runtime и стандартная библиотека
    связываются статически (Р26).
  - **Фронтенд (О26):**
    - семантика — функции модуля без побочных эффектов с явными
      входами (сводки зависимостей);
    - кэш — по модулю;
    - мелкие запросы в духе rustc и Salsa — только если замер `check`
      и отклика language server в v0.4 покажет нужду.

  Решение автора 4 октября 2026.
- **Почему.** Рекомендации сессии из `OPEN_DECISIONS.md`: проще всего

- **Рассмотрено и отклонено:**
  - интерпретатор как режим исполнения программ — второй путь

  - мелкие запросы с первого дня — сложность без замера (Р24).

### Р44. Ссылки без побега (О4, часть v0.1)
- **Решение.** Ссылка `&T` или `&mut T` живёт только:
  - как параметр функции;
  - как временное заимствование в цикле `for x in &list`.

  Её нельзя хранить в полях и глобальных данных и нельзя возвращать
  из функции. Компилятор проверяет это статически. Исключительный
  изменяемый доступ и линейные ресурсы — v0.3 (О4).
  Решение автора 4 октября 2026.
- **Почему.** Висячая ссылка в безопасном коде невозможна статически
  при малой цене в компиляторе (`docs/design/LANGUAGE.md`, раздел 2.2).
- **Рассмотрено и отклонено:**
  - отложить проверку до v0.3 — ядро v0.1 мерилось бы без главной
    гарантии ссылок.

### Р45. Память `List[T]` и `str` в v0.1
- **Решение.** `List[T]` и `str` — значения, как в опыте v0.0.
  - Присваивание, передача по значению и запись в поле копируют
    содержимое.
  - Память освобождается автоматически, когда значение выходит из
    области или перезаписывается.
  - Это освобождение памяти встроенных контейнеров, а не деструктор:
    у пользовательских типов деструкторов нет, ресурсы — по О5.
  - Память берётся из кучи runtime по умолчанию. Явные аллокаторы и
    арены (Р9) — v0.3, вместе с коллекциями (О12).

  Решение автора 4 октября 2026.
- **Почему.**
  - Нет общих изменяемых данных и утечек, а с Р44 — и висячих ссылок
    (Р6, уровень 1).
  - Модель та же, на которой модели писали в опыте v0.0 (Р40).
  - Компилятор проще, чем с перемещениями.
- **Рассмотрено и отклонено:**
  - перемещение и явный `clone()` — больше правил и отказов, решения
    опыта v0.0 местами перестали бы собираться;
  - без освобождения до v0.3 — долгие программы растут в памяти.

### Р47. Сообщения компилятора — по-английски

### Р48. Запись плавающих в `str(x)` — как `repr` в Python, без `.0`
- **Решение.** `str(x)` у `f32` и `f64` даёт кратчайшую запись, которая
  читается обратно в то же число (у `f32` — в то же `f32`). При
  десятичном порядке от −4 до 15 форма обычная, без хвоста `.0`: `0.1`,
  `100`, `0.0001`, `1000000000000000`. Иначе — экспоненциальная:
  `1e+16`, `1.5e-07`. Особые значения — `-0`, `inf`, `-inf`, `nan`.
  Решение автора 4 октября 2026.
- **Почему.** Прежняя форма `%g` писала `100.0` как `1e+02` — неожиданно
  и для людей, и для моделей. Запись `repr` привычна, а C-бэкенд и
  runtime (шаги 8–9 v0.1) повторяют её с первого дня.
- **Рассмотрено и отклонено:** `%g` — неожиданная запись; `repr` с `.0`
  (`100.0`) — длиннее, а тип и так виден в коде.

### Р49. Онлайн-компилятор: строится, запуск — отдельным решением
- **Решение.** В репозитории строится онлайн-компилятор — безопасный
  интерфейс к тому же компилятору для будущей страницы на dpsmpx.com.
  Устройство — `docs/service/README.md`. Решение автора 5 октября 2026.
  - **Только компиляция.** Сервис проверяет программу и возвращает
    диагностику. Программы пользователя он не исполняет: исполнение —
    отдельное решение со своим слоем изоляции и своей моделью угроз.
  - **Одно ядро.** CLI, worker сервиса и будущие адаптеры (language
    server, WASM) компилируют через один вход ядра
    (`compiler/api/compile.h`). Своей логики компиляции у сервиса нет.
  - **Пределы ресурсов** — только в онлайн-профиле: один файл
    конфигурации (`service/config/online-v1.json`). В ядре есть один
    параметр — предел глубины вложенности. Он защищает от переполнения
    стека; у CLI порог высокий, онлайн-профиль задаёт свой.
  - **Изоляция — слой вокруг ядра.** Worker — режим `dpl worker` в
    отдельном процессе: seccomp без сети, файлов, процессов и `exec`;
    rlimits на CPU, память и файлы; пустое окружение; временный
    рабочий каталог; уничтожение по таймауту. Шлюз не компилирует в
    своём процессе. Docker и облака ядру не нужны.
  - **Контракт** — JSON с версией API (`/api/v1/...`), отдельной от
    версии компилятора и версии языка. Детерминированная часть ответа —
    одна и та же при одинаковом входе и версии.
  - **Шлюз** — временно на Python 3 stdlib, без сторонних пакетов.
    Он заменяется шлюзом на dpl, когда язык сможет: FFI (v0.2),
    потоки (v0.3), ввод-вывод в библиотеке. Тесты шлюза — чёрный ящик по
    HTTP; они и будут приёмкой замены.
  - **Серверная компиляция, не WASM.** Сборка компилятора в браузере —
    передача двоичной сборки каждому посетителю. До v1.0 её закрывают
    Р4, Р5 и Р39 (этап 1: лицензия SDK и договор о конфиденциальности).
    Ядро остаётся пригодным для WASM: C++20 без зависимостей, без
    системных вызовов при компиляции из памяти. Пересмотр — вместе с
    решением по Р5 после v1.0.
  - **Запуск выключен.** Публичный доступ — только отдельным решением
    автора по Р5. До него: проверка имени у поверенного (Р39) и
    выполнение DoD сервиса (`docs/service/README.md`). До решения
    `available` в конфигурации — `false`: сервис отвечает «недоступен»,
    а сайт не показывает неработающую страницу.
  - **Граница ответственности.**
    - dpl — компилятор, контракт, версии, диагностика, детерминизм.
    - dpsmpx/SocialMediaImage — страница, редактор, HTTP-клиент, показ
      диагностики.
    - Инфраструктура — точка входа, TLS, внешний rate limit,
      оркестрация worker-ов, мониторинг.
- **Почему.**
  - Р5 не меняется: построить и проверить можно внутри, открыть — только
    решением.
  - Изоляция и пределы — свойства устройства, а не обещания. Их
    проверяют тесты злоупотреблений.
  - Шлюз на dpl сейчас невозможен: в v0.1 нет ввода, сети, времени,
    процессов и FFI.
- **Рассмотрено и отклонено:**
  - WASM в браузере до v1.0 — Р4, Р5, Р39;
  - шлюз на Go — новый язык и тулчейн;
  - шлюз на C++ — свой разбор HTTP, больше поверхности атаки;
  - пределы в ядре для всех режимов — по слову автора, только в
    онлайн-профиле;
  - исполнение программ пользователя — без отдельной модели угроз.

### Р50. Тесты в языке — атрибут `@test`
- **Решение.** Тест — функция с атрибутом `@test`; она запускается
  командой `dpl test`. Решение автора 9 октября 2026.
  - Функция-тест не берёт параметров и возвращает ничего или `E!void`
    (`!void`). Тест прошёл, если вернулся без ловушки и без ошибки;
    проверки внутри — `assert`.
  - `dpl test` находит тесты во всех модулях программы, кроме
    стандартной библиотеки. Функция `main` для этого не нужна.
  - Каждый тест исполняется отдельным процессом: ловушка или ошибка
    валит только его.
  - Сборка тестов — в профиле `test`: как `debug`, с ASan и UBSan,
    если компилятор C их умеет.
- **Почему.** Атрибут — та же запись, что у `@det`: новых ключевых
  слов нет. Это декларативные метаданные без макросов (Р7).
  Отдельный процесс на тест следует из Р36: после ловушки исполнение
  не продолжается.
- **Рассмотрено и отклонено:**
  - блок `test "имя" { … }` — новое ключевое слово, имя `test`
    перестаёт быть доступным;
  - отложить `dpl test` — шаг 10 v0.1 остался бы без команды.

### Р51. Аргументы программы и файлы — модуль `os`
- **Решение.** Стандартная библиотека v0.1 даёт программе ввод через
  модуль `os` (`stdlib/os.dpm`, `import os`). Решение автора 9 октября
  2026.
  - `os.args() List[str]` — аргументы программы без её имени.
  - `os.read_file(path: str) os.IoError!str` — файл целиком; текст
    проверяется на UTF-8.
  - `os.IoError` — `NotFound`, `PermissionDenied`, `InvalidUtf8`,
    `Other`.
  - Внутри модуля — встроенные функции компилятора на простых типах.
    Они доступны только модулям стандартной библиотеки; FFI — v0.2.
  - Ввод-вывод — недетерминированный класс (Р12, Р29): из `@det` его
    звать нельзя, когда появится проверка классов.
- **Почему.** Параметр у `main` поменял бы вход программы
  (module.main). Глобальные встроенные функции дали бы имена без модуля
  и тип ошибки, встроенный в язык. Модуль с `import` — тот же путь, что
  у будущей библиотеки.
- **Рассмотрено и отклонено:**
  - `fn main(args: []str)`;
  - глобальные `args()` и `read_file()`.

### Р53. Проверяемая арифметика целых — `checked_*`
- **Решение.** Встроенные функции `checked_add(a, b)`, `checked_sub(a, b)`,
  `checked_mul(a, b)`, `checked_div(a, b)` и `checked_neg(a)` возвращают
  `?T`. Результат — точное значение, если оно в типе `T`, иначе `none`;
  ловушки нет. `checked_div` даёт `none` и при делителе 0. Операнды —
  целые, общий тип — как у бинарных операторов; `checked_neg` — только
  знаковые. Решение автора 10 октября 2026.
- **Почему.** По Р36 переполнение — ловушка. Коду, для которого
  переполнение — данные (разбор, калькуляторы, проверка ввода), нужна
  проверка без ловушки. Замер ворот v0.1: без неё модель пишет такие
  проверки вручную, на t16 разрыв с C++ (`__builtin_*_overflow`) —
  самый большой (`docs/audits/2026-10-10-k2-experiment.md`).
- **Рассмотрено и отклонено:** операторы вида `+?` — новая запись в
  грамматике ради редкой операции; функции в модуле стандартной
  библиотеки — v0.1 не умеет обобщённых функций библиотеки.

### Р54. Встроенное отображение `Map[K, V]`
- **Решение.** Встроенный тип `Map[K, V]` — отображение ключей `K` в
  значения `V`; значение по Р45, как `List`. Решение автора 10 октября
  2026 — третий шаг снижения цены ворот v0.1.
  - **Порядок обхода — по возрастанию ключа** (как `std::map`); от
    истории вставок и удалений он не зависит. Прежде было «порядок
    вставки» — заменено по поручению автора 10 октября (история).
  - **Доступ.** `m[k]` — место, как `xs[i]`: чтение и изменение
    отсутствующего ключа — ловушка; `m[k] = v` вставляет или заменяет;
    `m[k] += 1` — только у существующего ключа. Без ловушки —
    `m.get(k)`, результат `?V`. Ещё `m.contains(k)`, `m.remove(k)` →
    `?V`, `m.clear()`, `m.keys()` → `List[K]` и `len(m)`.
  - **Обход** `for k in &m` даёт ключи по порядку; значение — `m[k]`.
    Менять `m` в теле такого цикла нельзя (E0412); для этого обходят
    `m.keys()`.
  - **Литерал** — только пустой `[]` по ожидаемому типу; заполнение —
    присваиваниями.
- **Уточнения сессии** (мелочи по `CLAUDE.md`, на просмотр автору):
  - ключ в первой версии — целое, `bool` или `str` (E0424): у плавающих
    `nan != nan`, составные ключи — когда замер покажет нужду;
  - отображения не сравниваются (`==`, `<` — E0422);
  - поиск, вставка и замена — O(1) в среднем (хэш без случайной соли:
    детерминизм, Р12); `remove` — O(n); обход и `keys()` — O(n log n):
    снимок ключей сортируется.
- **Почему.** Замер ворот v0.1: в задачах со словарями (t15 — счета по
  имени, t16 — переменные калькулятора) решения на dpl пишут поиск
  перебором по `List` вручную, а C++ берёт `std::map`.
- **Почему по возрастанию ключа** — для модели, которая пишет и читает
  код:
  - вывод определяется содержимым, а не историей: чтобы предсказать
    порядок, не нужно прослеживать вставки и удаления («удалённый и
    вставленный снова ключ уходит в конец» больше не правило);
  - самый частый вывод — отчёт по имени или номеру — получается без
    `keys()` и `sort()`;
  - так же устроен `std::map` из C++, с которым язык сравнивается.
- **Рассмотрено и отклонено:**
  - порядок вставки (как `dict` в Python) — был до замены: порядок
    зависит от истории изменений;
  - хранить пары упорядоченно — вставка O(n); снимок ключей при обходе
    дешевле, пока замер не покажет иного;
  - только методы без `m[k]` — длиннее запись изменения;
  - пары в обходе (`e.key`, `e.value`) — новый встроенный тип пары;
  - непустой литерал `[k: v]` — новая запись в грамматике.

### Р55. Класс D объявляется на модуле и уточняется на функции (О10)
- **Решение.** Детерминированный класс (Р12) объявляется атрибутом
  `@det`. По умолчанию — у модуля: тогда все его функции принадлежат
  классу D. Отдельная функция может быть объявлена `@det` в модуле без
  этой пометки. Решение автора 10 октября 2026.
  - **Модуль помечает тот, кто его импортирует:** `@det import physics`.
    Модуль, импортированный так хотя бы одним модулем программы,
    принадлежит классу D целиком, и компилятор проверяет все его
    функции. Уточнение автора 10 октября (история).
  - Функция класса D вызывает только функции класса D и встроенные
    функции без ввода-вывода.
- **Почему.** Модуль — естественная граница симуляции: одна пометка, и
  проверка ловит случайный вызов недетерминированного кода. Функция —
  для смешанных модулей, где делить файл неудобно.
- **Рассмотрено и отклонено:** только модуль — смешанный модуль
  приходится делить; только функция — много пометок, легко забыть.
- **Рассмотрено и отклонено для записи модуля:** `@!det` первой строкой
  модуля (как `#![...]` в Rust) — рекомендация сессии; `@det module` —
  новое ключевое слово.

### Р56. NaN в классе D приводится к каноническому после каждой операции (О11)
- **Решение.** В коде класса D результат каждой операции с плавающей
  точкой, давший NaN, заменяется каноническим NaN (одно и то же значение
  битов на всех целях). Так значения совпадают побитово и в памяти, а
  не только в выводе. Решение автора 10 октября 2026.
- **Почему.** Ворота v0.2 требуют побитового повтора на x86-64 и arm64,
  а знак и биты NaN, которые дают процессоры, у них разные. Канон только
  при выводе оставил бы расхождение в памяти и в побитовых
  преобразованиях.
- **Цена.** Проверка на каждой операции с плавающими в коде класса D;
  вне класса D её нет. Замер — на шаге 4 v0.2.
- **Рассмотрено и отклонено:** биты NaN не определены, канон — только
  при выводе и сериализации (рекомендация О11) — дешевле, но повтор не
  побитов в памяти.

### Р57. Ресурсы — `defer`, `errdefer` и линейные типы; неявных деструкторов нет (О5)
- **Решение.** У типов нет деструкторов, которые компилятор вызывает
  сам. Ресурс, который нужно закрыть явно (окно, файл, объект Vulkan,
  дескриптор из FFI), — значение линейного типа: его нужно поглотить
  ровно один раз — закрыть или передать дальше. Незакрытый ресурс и
  повторное закрытие — ошибка компиляции. Закрытие пишется в коде:
  `defer close(r)`; `errdefer` — закрыть, только если блок выходит с
  ошибкой. Решение автора 10 октября 2026.
- **Почему.** Вызовы закрытия видны в коде, их порядок задан явно — для
  Vulkan он важен. Модель видит, где ресурс освобождается, и не держит в
  голове скрытые вызовы; забытое закрытие ловит компилятор. Значения
  dpl (Р45) по-прежнему освобождаются сами.
- **Рассмотрено и отклонено:** деструкторы (как `Drop` в Rust) — скрытые
  вызовы и неявный порядок; только `defer` без проверки — забытое
  закрытие становится утечкой.
- **Как устроено:** запись — `@linear` (Р59), правила поглощения и
  `errdefer` — Р60.

### Р58. Сгенерированные привязки хранятся в репозитории (О23)
- **Решение.** Привязки (Vulkan из `vk.xml`, SDL3, JNI) генерируются
  программой из репозитория, а результат — модули `.dpm` — лежит в
  репозитории и проходит ревью. Генератор и вход (`vk.xml`, заголовки)
  закреплены по версии; повторная генерация даёт те же байты, это
  проверяет `tools/check/run.sh`. Решение автора 10 октября 2026.
- **Почему.** Изменение привязки видно в ревью; сборка не зависит от
  генератора и сети; воспроизводимость проверяется.
- **Рассмотрено и отклонено:** генерация при каждой сборке — изменения
  не видны, сборка зависит от генератора.

### Р59. FFI: `extern fn` с `@link`, дескрипторы и срезы, `@linear`, `@c`
- **Решение.** Решение автора 10 октября 2026 (шаг 5 v0.2).
  - **Функции C** объявляются строкой без тела: `extern fn
    SDL_Init(flags: u32) bool`. Библиотека — атрибут `@link("SDL3")`
    перед объявлением.
  - **Указателей в языке нет.** Непрозрачный тип C — `extern type
    SDL_Window`: значение — дескриптор без арифметики; `?SDL_Window` —
    дескриптор или `none` (NULL). Буферы передаются как `[]T`, `&T` и
    `&mut T`; компилятор передаёт C указатель на данные. `unsafe` не
    нужен.
  - **Линейный тип** (Р57) — атрибут `@linear` у структуры. Значение
    нужно закрыть ровно один раз: передать по значению в функцию или
    вернуть.
  - **Раскладка C** — атрибут `@c` у структуры: поля по порядку, с
    выравниванием C, только типы с видом в C. Раскладка остальных
    структур — класса I (`docs/policy/DETERMINISM.md`).
- **Почему.** Объявление в одну строку генератор привязок пишет так же,
  как человек. Без указателей безопасность памяти остаётся за
  компилятором; дескриптор и срез покрывают окна, файлы, объекты Vulkan
  и буферы. Атрибуты — та же запись, что `@det` и `@test`, без новых
  ключевых слов.
- **Рассмотрено и отклонено:** блок `extern "lib" { ... }` — новая форма
  блока; сырые указатели и `unsafe` — память можно испортить; `linear
  struct` — новое ключевое слово; раскладка C у всех структур —
  компилятор теряет свободу раскладки.


### Р60. Линейные типы: перенос, разбор, `errdefer`, циклы (Р57, Р59)
- **Решение.** Правила линейных значений и `errdefer` — шаг 5б v0.2.
  Решение автора 10 октября 2026.
  - **Что линейно.** Структура `@linear` (Р59), а также `?T` и `E!T` с
    линейным `T`. Поле линейного типа — только у структуры `@linear`.
    `List` и `Map` с линейными элементами — ошибка до v0.3 (пулы и
    хэндлы).
  - **Ровно один раз.** Линейное значение поглощается ровно один раз на
    каждом пути: передачей по значению в функцию, `return`, переносом.
    Незакрытое к концу области и поглощённое дважды — ошибка компиляции.
    Пути, которые кончаются ловушкой, не проверяются.
  - **Перенос.** `let b = a`, запись в поле литерала, `some(a)` переносят
    ресурс: `a` дальше читать нельзя. Неявных копий нет. По ссылке (`&a`,
    `&mut a`) значение передаётся без поглощения. Чтение поля не
    поглощает.
  - **Разбор.** `let S { f, g } = v` поглощает `v` и даёт переменные
    полей; линейные поля становятся новыми линейными переменными. Разбор
    — только в модуле, где объявлена `S`: снаружи ресурс закрывают его
    функции.
  - **`defer close(r)`** поглощает `r` на выходе из области; после него
    `r` — только по ссылке.
  - **`errdefer`** — как `defer`, но тело выполняется, только если
    функция возвращает ошибку (`fail`, `try`). В функции без `E!T` —
    ошибка компиляции. Для проверки линейности `errdefer` поглощает на
    путях с ошибкой; на остальных путях ресурс закрывают или
    возвращают.
  - **Циклы.** В теле цикла нельзя поглотить линейное значение, объявленное
    вне цикла; по ссылке — можно.
- **Почему.** Проверка — потоком данных, как определённая инициализация
  (`docs/design/LANGUAGE.md`, раздел 2): компилятор ловит забытое и
  повторное закрытие. Разбор в модуле типа сохраняет инкапсуляцию:
  закрыть ресурс в обход его функции нельзя.
- **Рассмотрено и отклонено:**
  - запрет присваивания линейного значения — нельзя собрать структуру из
    ресурсов;
  - линейное только в переменных — нельзя вернуть `E!Window`;
  - поглощение в цикле, если за ним `break`, — анализ сложнее;
  - встроенная `release(v)` с переносом полей по одному — компилятор
    следил бы за полями;
  - разбор вне модуля типа — ресурс закрывался бы мимо его функции.

### Р61. Вызов dpl из C: `@export`, тип `extern fn(...)`, `--lib` (Р17, Р59)
- **Решение.** Шаг 5в v0.2. Решение автора 11 октября 2026.
  - **Экспорт** — атрибут `@export` перед функцией с телом: `@export fn
    game_step(dt: f32) i32 { ... }`. Внутри dpl это обычная функция.
    Сигнатура — только типы с видом в C (как у `extern fn`); `E!T` нельзя.
    Ловушка внутри — сообщение и выход процесса, как в программе.
  - **Имя символа C** — имя функции как есть; `@export("name")` задаёт
    другое. Два одинаковых символа в программе — ошибка компиляции.
  - **Обратные вызовы** — тип `extern fn(T1, T2) R`: указатель на функцию
    C, имена параметров в запись типа не входят. Значение — имя функции
    `@export` с той же сигнатурой; его передают функциям C, хранят в
    полях `@c`, вызывают. Контекст C (`void* userdata`) — дескриптор
    `extern type`: dpl его только передаёт. Замыканий нет.
  - **Сборка для хоста C/C++** — `dpl build --lib`: статическая
    библиотека `.a` и заголовок C с объявлениями `@export` и структур
    `@c` из их сигнатур; `main` не нужна.
- **Почему.** Атрибут — та же запись, что `@det`, `@test`, `@link`, без
  нового ключевого слова (Р59). Имя символа выбирает автор кода, как в
  библиотеках C (`SDL_`, `vk`). Тип без имён печатается в сообщениях так
  же, как пишется. Статическая библиотека с заголовком — поставка модуля
  dpl из `docs/design/LANGUAGE.md`, раздел 5; динамическая добавила бы
  видимость символов и экспорт DLL на трёх целях.
- **Рассмотрено и отклонено:** `extern fn` с телом — одно слово для двух
  направлений; ключевое слово `export`; символ `модуль_имя` — имя в C не
  выбрать; колбэки без контекста; отложить колбэки до генераторов; имена
  параметров в типе; динамическая библиотека в v0.2.

### Р62. Структуры C для привязок: заимствующие поля, массивы, объединения (Р59, Р61)
- **Решение.** Шаг 6 v0.2: привязки Vulkan и SDL3 выражаются средствами
  языка, без C-прослойки. Решение автора 11 октября 2026.
  - **Заимствующие поля** `@c`: `[]T`, `str`, `&T`, `?&T`. Структура с
    таким полем — заимствующая (как и всё, что её содержит): только тип
    параметра, как срез (Р44), и значение в аргументе вызова; живёт до
    конца вызова. В таком аргументе `&` можно взять и от литерала. При
    передаче в C компилятор строит структуру C: срез — указатель на
    элементы, строка — копия с нулём в конце.
  - **Счётчик** — атрибут `@count(поле)` перед полем-срезом: длину среза
    компилятор пишет в поле-счётчик при передаче в C; задать счётчик в
    литерале — ошибка. Расхождения длины и счётчика нет.
  - **Массив** `[N]T` — поле `@c` с раскладкой массива C (`char
    deviceName[256]`).
  - **Объединение** — атрибут `@union` у структуры: поля делят память; в
    них только данные (числа, массивы, дескрипторы, `@c`-структуры из
    них); чтение другого поля — его байты.
  - **Общее начало.** Ссылка `&S` переходит в `&B`, если поля
    `@c`-структуры `B` — начало полей `S` с теми же типами (общая
    начальная последовательность C). `pNext` — `?&VkBaseInStructure`:
    `p_next: &features`.
  - **Ноль у `@c`.** Пропущенное в литерале поле `@c`-структуры — ноль,
    если ноль у типа есть: числа, `bool`, `?T`, пустые срез и строка,
    массив и структура из таких. Дескриптор, `extern fn` и `&T` задаются.
  - **Объём Vulkan** — ядро 1.3 и расширения из списка в репозитории;
    новое расширение — строка в списке и перегенерация.
  - **Объём SDL3** — функции и константы заголовков из списка в
    репозитории, типы — по надобности; смысл указателей — по описаниям
    параметров в заголовках, сомнительное пропускается с причиной.
    Решение автора 12 октября 2026.
- **Почему.** Код Vulkan и SDL3 на dpl повторяет код на C: модели его
  знают, и ручные привязки пишутся так же. Указателей и `unsafe` в языке
  по-прежнему нет: заимствование живёт только на время вызова, счётчик
  ставит компилятор. Атрибуты — та же запись, что `@c` и `@linear`.
- **Рассмотрено и отклонено:** C-прослойка генератора — своё API
  привязки и механизм «исходник C при модуле»; сначала только SDL3 и
  JNI; счётчик вручную — чтение C за концом среза; стёртая ссылка на
  любую `@c` — тип ничего не проверяет; умолчания генератора вместо нуля
  — ручные привязки писали бы то же сами; ключевое слово `union`; весь
  `vk.xml` — десятки тысяч строк в ревью.
### Р63. Вызов через таблицу функций C: `@slot(N)` (Р59, Р62)
- **Решение.** Шаг 6 v0.2, привязка JNI. Решение автора 12 октября
  2026.
  - Атрибут `@slot(N)` перед `extern fn`: функция C — запись `N`
    таблицы указателей на функции, на которую указывает первый
    аргумент. Первый параметр — дескриптор `extern type`; вызов в C —
    `(*obj)[N](obj, …)`. Так устроены `JNIEnv` и `JavaVM` (`(*env)->
    FindClass(env, name)`), так же — COM и DirectX.
  - Символа у такой функции нет: `@link` к ней не относится.
- **Почему.** Указателей и C-прослойки по-прежнему нет (Р59, Р62):
  адрес из таблицы берёт компилятор, а таблицу пишет генератор по
  заголовку. Одна запись покрывает все интерфейсы с таблицей функций.
- **Рассмотрено и отклонено:** C-прослойка генератора для JNI —
  исключение из Р62 и механизм «исходник C при модуле»; отложить JNI —
  шаг 6 не закрыт по Р58.

### Р64. Проверка графической программы v0.2: снимок кадра, Android у автора
- **Решение.** Шаг 7 v0.2. Решение автора 12 октября 2026.
  - **Кадр** — треугольник шейдером: программа читает кадр и сверяет
    пиксели с эталоном PPM в репозитории. SPIR-V шейдеров лежит в
    репозитории байтами, исходник GLSL — рядом; компилятор шейдеров
    нужен только для пересборки.
  - **Linux и Windows** — запуск в сессии: Linux на программном
    драйвере lavapipe, Windows под Wine (Vulkan Wine передаёт хосту).
  - **Android** — сессия собирает программу и пакет и проверяет
    компоновку; запускает автор на своём устройстве и присылает вывод
    или снимок, сессия сверяет. Ворота v0.2 закрываются после его
    запуска.
- **Почему.** В облачном окружении нет KVM для эмулятора Android, а
  qemu-user Vulkan не запускает; снимок со сплошными цветами и
  вершинами без пограничных пикселей одинаков на любом драйвере.
- **Рассмотрено и отклонено:** только сборка для Android с оговоркой в
  воротах; Android без SDL3 (NativeActivity); кадр без шейдеров
  (очистка и прямоугольники) — графический конвейер не проверяется.

### Р65. Цикл по срезу и вид левее действия в вызове (Р44, Р54)
- **Решение.** Решение автора 17 октября 2026, по итогам исправления
  висячих видов (срез или ссылка, пережившие изменение своего списка).
  - **Цикл по срезу.** В `for x in &xs[a..b]` менять корень среза — `xs`,
    его поля и элементы — в теле нельзя (E0412), как у обхода `Map`
    (Р54). Чтобы менять список в цикле, обходят срез копии, сделанной до
    цикла, или весь список: в `for x in &xs` элемент читается по индексу,
    длина проверяется на каждом шаге. Уточнение сессии: срез `str` —
    строка-копия (ref.slices), корень такого среза не замораживается.
  - **Вид левее действия.** Срез, ссылка `&x` для параметра `&T` и
    `&место` для C — операнды (expr.order): они видят значение на момент
    своего вычисления, даже если правее в том же вызове стоит действие,
    меняющее источник. `show(&cells[0], wipe(&mut cells))` получает
    прежний элемент. Компилятор строит такой вид над копией места,
    только если действие правее меняет его источник.
- **Почему.** Р6: надёжность и контролируемость прежде удобства.
  - Цикл: изменение источника во время обхода его среза почти всегда
    ошибка; копия всего списка на такой цикл не видна в коде; правило
    одно с обходом `Map`.
  - Вид: смысл следует из порядка слева направо, нового правила
    проверки не нужно; копия делается, только если действие правее
    меняет источник.
- **Рассмотрено и отклонено:**
  - цикл по снимку среза на начало цикла — скрытая копия, правило
    расходится с обходом `Map`;
  - живой обход среза по индексу — смысл зависит от действий тела,
    ловушка вместо ошибки компиляции;
  - ошибка компиляции для вида левее действия (E0502 на вложенные
    вызовы) — новое правило проверки и запрет записей, у которых есть
    ясный смысл.

## 3. Выведенные правила

Прямо не выбирались, но следуют из решений и правил VoxelRPG.

- **Код VoxelRPG сюда не копируется.** Защита VoxelRPG — приоритет (его
  Р12: код, его части и выдержки наружу не уходят), а этот репозиторий
  — отдельный проект (Р5, Р22). Из VoxelRPG сюда переносятся правила и
  счёт конструкций, не исходники; proof-of-concept до v1.0 — без кода
  VoxelRPG.
- **Код компилятора не пишется до итогов этапа 2** — эталонного набора
  и опыта с синтаксисом (Р24); прототипы для замеров этапа 2 — не код
  компилятора. Дальнейший порядок — `ROADMAP/ROADMAP.md`.
