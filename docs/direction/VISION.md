# Техническое видение языка DPlang

Окончательное техническое видение проекта (постановка автора 3 октября
2026, решения Р25–Р33). Что решено — `DECISIONS.md`; как устроено —
`docs/design/`; правила — `docs/policy/`. При расхождении прав
`DECISIONS.md`.

## 1. Назначение

Собственный системный язык программирования и полный production
toolchain — прежде всего для дальнейшей разработки VoxelRPG и следующих
проектов автора.

Целевой результат (формулировка автора):

> Язык должен ускорять разработку сложного программного продукта без
> снижения качества и надёжности и по возможности повышать
> контролируемость, проверяемость, воспроизводимость и предсказуемость
> разработки.

Главная метрика (Р32): сколько production-работы можно сделать быстрее
при том же или более высоком уровне качества, надёжности,
контролируемости и предсказуемости. Не число возможностей, строк
компилятора или сложность системы типов.

## 2. Чем язык является и чем — нет

| является | не является |
|---|---|
| системный язык общего назначения с сильной ориентацией на игры и движки (Р27) | DSL, скриптовый слой, язык только для игровой логики |
| компилируемый в native-приложения для конечных устройств (Р28) | язык, работающий только внутри интерпретатора |
| язык со строгими, проверяемыми гарантиями (Р11, Р12, Р13) | система доказательства теорем |
| язык, рассчитанный на десятилетия эволюции (Р26, Р33) | исследовательский язык ради идей |
| закрытый актив автора до v1.0 (Р4, Р5) | публичный продукт до v1.0 |
| язык, сосуществующий с C/C++ через C ABI (Р17, Р30) | надмножество или замена C++ с его ABI |

## 3. Ценности и порядок при конфликте

Порядок — Р6 (уровни) с уточнением Р25 (ценности автора внутри
уровней):

| уровень Р6 | ценности (Р25) |
|---|---|
| 1 — обязательные | корректность; предсказуемость; детерминированность в заявленной области; безопасность работы с памятью и ресурсами; контролируемая производительность; эволюционируемость |
| 2 — производственные | статическая проверяемость; удобство сопровождения; качество диагностики; скорость разработки; скорость сборки; удобство разработки с ИИ |
| 3 — вторичные | простота; эргономика синтаксиса; переносимость |

Скорость разработки достигается не отказом от гарантий, а механизмами,
которые снимают целые классы ошибок и ручной работы: явные контракты,
меньше неявных состояний, дешёвый рефакторинг через инструменты, точные
ошибки компилятора, автоматическая проверка инвариантов.

## 4. Техническое видение по опорам

1. **Явность.** Нет скрытого потока управления (исключений нет, выход из
   функции виден: `return`, `try`, ловушка проверки), нет неявных
   преобразований с потерей, язык сам не выделяет память — выделяет код,
   получивший аллокатор (Р9). Цена операций видна по коду.
2. **Безопасность по умолчанию, `unsafe` — видимое исключение** (Р11):
   нет неопределённого поведения вне `unsafe`; память — хэндлы с
   поколением, арены, ссылки без побега, исключительный изменяемый
   доступ, линейные ресурсы (`docs/design/LANGUAGE.md`).
3. **Детерминизм по построению** (Р12, Р29): поведение разделено на
   классы, детерминированный класс проверяется компилятором, а не
   дисциплиной (`docs/policy/DETERMINISM.md`).
4. **Эволюционируемость по построению** (Р0, Р18, Р26): малые явные
   стабильные контракты, всё остальное — внутреннее; изменения языка —
   редакциями с машинной миграцией; совместимость проверяется корпусом
   (`docs/policy/COMPATIBILITY.md`).
5. **Инструменты — часть языка** (Р15): `check`, `build`, `test`,
   `fmt`, `fix`, `explain`, `query`, машиночитаемая диагностика,
   language server — одной версии с компилятором и на одном фронтенде.
6. **Native по умолчанию** (Р16, Р28): IR-граница, первый бэкенд —
   генерация C, затем — по замеру; платформы первой волны — Linux x64,
   Windows x64, Android arm64.
7. **Взаимодействие через C ABI** (Р17, Р30): C — напрямую, C++ — через
   C-прослойку; смешанные C++ и DPlang в одном бинарнике.
8. **Маленькая стандартная библиотека** (Р19): примитивы, без игрового
   движка внутри.
9. **Замер прежде решения** (Р24): синтаксис и спорные механизмы
   выбираются экспериментом на реальных задачах.

## 5. Пригодность для систем уровня VoxelRPG

Проверка модели (Р27) на подсистемах будущего потребителя. «Чем
покрыто» — механизм языка (Я), стандартной библиотеки (Б), привязок
(П) или внешнего пакета (В).

| подсистема | что нужно от языка | чем покрыто | риск |
|---|---|---|---|
| рендер, Vulkan, платформенный слой | вызов C API, раскладка структур как в C, обратные вызовы, ресурсы с явным освобождением | Я: C ABI, `extern`-структуры, линейные ресурсы; П: привязки из `vk.xml`, SDL3, JNI | средний: объём привязок, отладка на устройстве |
| мир и чанки | плотные массивы, срезы, арены, хэндлы, быстрые циклы | Я: массивы и срезы, проверки границ; Б: арены, пулы с хэндлами | низкий; цена проверок — замер |
| процедурная генерация | детерминированная случайность по ключам, целочисленная и плавающая математика | Я: детерминированный класс; Б: ГПСЧ и хэши со спецификацией | низкий |
| сущности и ECS | хранение по типам компонентов, хэндлы, обход без лишних проверок | Б: пулы и хэндлы; ECS — кандидат (Р19), иначе код проекта | средний: эргономика без шаблонов C++ |
| игровая логика, ИИ | суммы типов, исчерпывающий `match`, конечные автоматы, контракты | Я | низкий |
| физика | векторная математика, детерминизм плавающей точки | Я: встроенные векторы и матрицы; детерминированный класс | средний: цена запрета FMA и fast-math |
| сохранение и сериализация | схема данных, независимая от раскладки в памяти и версии компилятора | Б: сериализация со схемой и версией (`docs/policy/COMPATIBILITY.md`) | низкий |
| интерфейс, ввод, звук | обратные вызовы платформы, строки и текст, буферы | Я: C ABI; Б: строки, форматирование; П: SDL3, AAudio | низкий |
| многопоточность, система задач | структурные задачи, параллельные циклы без гонок данных, атомики | Я: исключительный доступ на границе задачи; Б: задачи, атомики, каналы | средний: эргономика правил против гонок |
| инструменты | файлы, процессы, разбор текста, CLI | Б: файлы, форматирование, TOML | низкий |
| тесты и замеры | блоки тестов, expect-тесты, фаззинг, повтор | Я и Б (Р13) | низкий |

Вывод: модель покрывает все подсистемы; места среднего риска — объём
привязок, ECS без шаблонов, цена детерминизма в физике, эргономика
правил параллелизма. Они проверяются программами v0.2–v0.5
(`ROADMAP/ROADMAP.md`).

## 6. Архитектурные принципы

1. **Стабильно только то, что объявлено стабильным.** Стабильные
   контракты малы, перечислены и версионированы (Р26); всё прочее —
   внутренняя реализация, которую можно менять без следствий для кода
   потребителя.
2. **Семантика определяется спецификацией и тестами соответствия**, а не
   поведением компилятора: каждый нормативный пункт спецификации имеет
   идентификатор и тесты.
3. **Слои компилятора разделены проверяемыми границами:** AST → HIR →
   Core IR с верификатором; бэкенд видит только Core IR.
4. **Платформозависимое — только за явными границами:** описание цели
   (данные), runtime под ОС, модуль `platform` стандартной библиотеки,
   объявления с атрибутом цели. Условная компиляция — на уровне
   объявлений, и каждая ветка проверяется на своей цели.
5. **Детерминизм — по построению**, через классы поведения и проверку
   компилятора (Р29).
6. **Нет скрытого поведения:** поток управления, выделения памяти,
   преобразования и цена операций видны по коду.
7. **Диагностика — продукт:** коды ошибок стабильны, тексты проверяются
   снимками, у каждой ошибки — объяснение (`explain`) и, где можно,
   правка.
8. **Каждое изменение языка — с путём миграции** (Р18): редакция и
   `fix`, проверка корпусом.
9. **Воспроизводимость по умолчанию:** сборка из тех же входов даёт те
   же байты (`docs/policy/DETERMINISM.md`, раздел 6).
10. **Возможность добавляет реальная программа, а не интерес** (Р6, п. 9):
    у каждого механизма — программа, которой он нужен, и замер.
11. **Сначала минимальное ядро, доказанное на программах, — потом
    расширение** (Р33).
12. **Документация — часть инженерной системы** (Р3): по ней другой
    агент находит компонент, контракт и нужные проверки.

## 7. Главный принцип проекта (Р33)

> Сначала спроектировать систему, способную десятилетиями
> эволюционировать. Затем реализовать минимальное ядро, доказать его на
> реальных программах, довести до v1.0 и только после этого использовать
> его как production-язык для VoxelRPG.
