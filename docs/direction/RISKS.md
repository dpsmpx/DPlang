# Риски и критерии остановки или изменения архитектуры

Что может помешать цели (Р32, Р33), по каким признакам это видно и что
делать. Пересматривается на каждом аудите (`docs/policy/ENGINEERING.md`,
раздел 4). Пороги с пометкой «(предложение)» — ориентиры до первых
замеров.

## 1. Риски

| № | риск | признак | мера |
|---|---|---|---|
| Р-1 | **бесконечный R&D**: v1.0 не наступает | версия v0.x стоит больше чем вдвое против оценки; DoD не сокращается | у каждой версии — польза сама по себе (инструменты, программы); аудит после каждой версии; сокращение объёма раньше, чем растёт срок |
| Р-2 | ИИ пишет на dpl хуже, чем на C++ | ворота v0.0 и v0.1: правильность ниже, циклов исправления больше | правка синтаксиса, спецификации, документации, диагностики; при повторном провале — критерий К-2 |
| Р-3 | **повторение существующих языков без выгоды** | эксперименты не показывают измеримого выигрыша над C++ с правилами | сравнение с планом Б (раздел 3) на воротах v0.1 и v0.3; критерий К-3 |
| Р-4 | сложность компилятора несоразмерна выгоде | объём компилятора на возможность, частота ошибок, время `check` | бюджет ядра v0.1 — около 25 тыс. строк компилятора без тестов (предложение); возможность дороже бюджета — упрощается или откладывается |
| Р-5 | модель памяти недостаточна | ошибка безопасности памяти в безопасном коде программ проверки | это критическая ошибка (`docs/policy/SECURITY.md`); пересмотр модели (О4) |
| Р-6 | модель памяти слишком строгая | доля `unsafe` и обходных путей в программах проверки больше 5% строк вне привязок (предложение) | ослабить или переделать правило, мешающее чаще всего |
| Р-7 | цена детерминизма (плавающая точка, упорядоченные таблицы) | представительные нагрузки хуже порогов `docs/policy/BENCHMARKS.md` | сузить класс D до симуляции; рендер и прочий не-D код не затронут |
| Р-8 | C-бэкенд: неопределённое поведение C, слабая отладка, медленная компиляция C | находки санитайзеров в сгенерированном C; жалобы на отладку; компиляция C — большая часть времени сборки | второй бэкенд раньше плана (критерий К-5) |
| Р-9 | эволюция не работает | эксперимент J: ручная доля больше 1% | пересмотр механизма редакций и `fix` до v1.0 |
| Р-10 | взаимодействие с C++, Vulkan, SDK тяжелее ожидаемого | объём ручных привязок растёт | генераторы привязок; прослойка C только для необходимого |
| Р-11 | язык отнимает ресурс у Galdhold | работа над языком больше ~1/6 ресурса (Р21) или задерживает версию 1 Galdhold | приоритет Galdhold по его `DECISIONS.md`; автор ставит язык на паузу |
| Р-12 | зависимость от сессий ИИ: лимиты, обрывы, смена моделей | потеря работы, повторные разборы | пуш после каждого куска; документация как инженерная система (Р3); детерминированные проверки |
| Р-13 | расхождение компилятора со спецификацией | тест соответствия «зелёный», но поведение другое | тесты на каждый нормативный пункт; аудит спецификации |
| Р-14 | платформенные сюрпризы Android и Windows | тесты в эмуляторе и Wine зелёные, на устройстве — нет | периодические прогоны на устройствах и настоящей Windows |
| Р-15 | нет внешнего CI: GitHub Actions не используется (Р3) | ошибка, не пойманная прогоном в сессии, дошла до `main` | полный `tools/check/run.sh` в сессии перед вливанием, итог — в PR; своя система — только по решению автора |
| Р-16 | право и лицензия | — | временная редакция до юриста (Р4); закрытость (Р5) |
| Р-17 | спецификация на холодном старте дороже экономии в коде: пока модель не знает язык, каждая сессия читает спецификацию; и на незнакомом языке модель дольше работает над тем же изменением | расход сессии на dpl выше, чем на C++ (опыт v0.0: +16–18% при одном изменении на сессию; v0.1, спецификация ядра: +35% при одном изменении на сессию и +38,7% на изменение в сериях из пяти; с кратким руководством, `checked_*`, `Map` и приёмами — +18,4%, половина разрыва — само руководство в задании — `docs/audits/2026-10-10-k2-experiment.md`, раздел 6) | компактная спецификация ядра (Р20); кэш запроса; `query` и `explain` вместо полного текста; мерить токены на принятое изменение в сессии из нескольких изменений |

## 2. Критерии остановки и изменения архитектуры

| № | условие | действие |
|---|---|---|
| К-1 | после v0.3 прогноз до v1.0 при ~1/6 ресурса больше трёх лет (предложение) | аудит; сократить объём v1.0 или перейти к плану Б |
| К-2 | на воротах v0.0 и затем v0.1, после одной итерации исправлений, модель на dpl пишет менее корректно, чем на C++ | остановить язык как цель; план Б |
| К-3 | на воротах v0.3 dpl не выигрывает у плана Б ни по корректности, ни по стоимости изменений на эталонном наборе | остановить язык; план Б |
| К-4 | ошибка безопасности памяти в безопасном коде повторяется после исправления модели | пересмотр модели памяти до следующей версии; при неудаче — заимствования в духе Rust для ссылок (дороже, но доказанно) |
| К-5 | недостатки C-бэкенда (Р-8) держатся две версии подряд | второй бэкенд (LLVM) раньше плана |
| К-6 | цена проверок или детерминизма выше порогов на представительных нагрузках после оптимизаций | сузить класс D; дать явные непроверяемые операции в `unsafe` для горячих мест |
| К-7 | эксперимент J проваливается | v1.0 не объявляется до переработки эволюции |

Любая остановка или смена — решение автора записью в `DECISIONS.md`.

## 3. План Б

«Свой C++» — уровни 1–2 из первоначального обсуждения: стандартный
C++20 в подмножестве Galdhold + своя библиотека (хэндлы, арены,
детерминированная математика и случайность) + автоматические проверки +
генерация кода. Наработки языка не пропадают: политики детерминизма,
совместимости, тестов и замеров, эталонный набор, генераторы привязок,
стандартная библиотека как образец.

Рассмотрено и отклонено: взять готовый язык (Zig, Odin, Rust, Swift) —
причины в аудите `docs/audits/2026-10-03-plan-audit.md`, раздел 2;
вопрос пересматривается на критерии К-3.
