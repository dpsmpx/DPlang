# C-бэкенд

Описание устройства C-бэкенда v0.1 (`ROADMAP/IMPLEMENTATION.md`, шаг 8;
`docs/design/ARCHITECTURE.md`, Р43). Код — `compiler/backend_c/`;
runtime, с которым собирается результат, — `runtime/`
(`docs/runtime/README.md`).

## 1. Место в конвейере

Программа без ошибок понижается в Core IR, верификатор проверяет его
(`docs/ir/README.md`), бэкенд `emit_c` переводит IR в один файл C11.
Компилятор C собирает этот файл вместе с runtime в нативную программу.

Смысл каждой операции — как у эталонного интерпретатора
(`docs/ir/README.md`, раздел 5): он образец. Различающие тесты сверяют
вывод нативной программы с его выводом байт в байт: stdout, stderr и код
выхода, включая текст и место ловушки.

Программу собирает `dpl build` (`docs/compiler/cli.md`, раздел 3). Вручную
то же, со строгими флагами прохода `native`:

```sh
dpl debug c prog.dpm > prog.c
cc -std=c11 -O1 -ffp-contract=off -fno-strict-aliasing \
   -Wall -Wextra -Wpedantic -Werror -Wno-infinite-recursion \
   -I runtime/core prog.c runtime/core/dp_rt.c runtime/linux/dp_entry.c \
   -lm -pthread -o prog
```

`dpl debug c` выходит с кодом 0 и печатает C в stdout. Код 1 — у
программы ошибки, диагностика та же, что у `check`. Код 3 — внутренняя
ошибка: в IR есть конструкция, которую бэкенд не умеет перевести.

## 2. Требования к C

- **C11 без неопределённого поведения.**
  - Целые считаются функциями runtime (`dp_sadd`, `dp_umul`, …). Они
    проверяют переполнение до операции.
  - Заворачивающая арифметика и битовые операции идут в беззнаковом
    типе. Перевод в знаковый тип — арифметикой (`dp_sbits`), а не
    преобразованием вне диапазона.
  - Счётчик сдвига, делитель и `MIN / -1` проверяются до операции.
  - Плавающее в целое: значение проверяется до приведения.
  - Индекс проверяется до того, как образуется указатель на элемент.
- **Порядок как в IR.** В C порядок вычисления аргументов и частей
  выражения не задан. Поэтому каждый операнд вычисляется отдельной
  инструкцией во временное `dp_vN` в порядке IR. Место с индексом
  берётся через указатель-временное `dp_pN`, а проверка индекса делается
  при его образовании. Так ловушки срабатывают в том же порядке, что у
  интерпретатора.
- **Без предупреждений** у gcc и clang с `-Wall -Wextra -Wpedantic
  -Werror`. Вспомогательные функции типов объявлены `DP_INLINE`
  (`static inline` с `unused`): программе нужны не все.
- **Плавающие без лишней точности.** Каждая операция округляется до
  своего типа: результат `f32` приводится к `float` на каждом шаге.
  Константы пишутся точно, шестнадцатеричной записью (`%a`). Цель с
  промежуточной точностью сверх типа (x87, `FLT_EVAL_METHOD != 0`)
  не собирается: `#error` в `dp_rt.h`.

Флаги сборки сгенерированного C:

| флаг | зачем |
|---|---|
| `-std=c11` | язык сгенерированного кода и runtime |
| `-O1` | уровень тестов; смысл от уровня не зависит, прогон проверен и на `-O2` |
| `-ffp-contract=off` | без слияния в FMA (`docs/policy/DETERMINISM.md`) |
| `-fno-strict-aliasing` | запас: бэкенд не нарушает правил алиасинга, но если ошибётся, поведение останется предсказуемым |
| `-Wall -Wextra -Wpedantic -Werror` | сгенерированный код — без предупреждений |
| `-Wno-infinite-recursion` | рекурсия без выхода — законная программа dpl: она остановится ловушкой «stack overflow», а gcc считает её ошибкой при `-Werror` |
| `-lm -pthread` | `math.h`; поток `main` (`docs/runtime/README.md`) |

В тестах к ним добавляются `-fsanitize=address,undefined
-fno-sanitize-recover=all`, если компилятор C их умеет.

## 3. Типы

| dpl | C |
|---|---|
| `bool` | `bool` |
| `i8`, `i16`, `i32`, `i64`, `int` | `int8_t` … `int64_t`; `int` — `int64_t` |
| `u8` … `u64` | `uint8_t` … `uint64_t` |
| `f32`, `f64` | `float`, `double` |
| `str` | `dp_str { ptr, len }` — владеет байтами UTF-8; пустая — `{NULL, 0}` |
| `List[T]` | `{ T* ptr; int64_t len; int64_t cap; }` — владеет элементами |
| `Map[K, V]` | `{ K* keys; V* vals; int64_t len, cap; int64_t* slots; int64_t nslots; }` — пары и хэш-индекс (раздел 4) |
| `[]T` (срез) | `{ T* ptr; int64_t len; }` — представление, не владеет |
| `?T` | `{ bool has; T value; }` |
| `E!T` | `{ bool is_err; T value; E err; }`; у `E!void` поля `value` нет |
| `struct S` | поля `f_<имя>`; у пустой структуры — `char dp_empty` |
| `enum E` | `{ uint32_t tag; union { struct { p0; p1; … } v_<Вариант>; … } u; }`; объединения нет, если данных нет ни у одного варианта |

Имена в C строятся из имён dpl: в них только латиница, цифры и `_`
(`lex.ident`). Имя модуля и имя в нём пишутся с длиной впереди: `a` и
`__x` дают `1a3__x`, `a__` и `x` — `3a__1x`. Без длин оба дали бы одно
имя C. Запись типа однозначна: по ней восстанавливается тип.

| что | имя в C |
|---|---|
| составной тип | `dp_<запись>`: `dp_L_i32`, `dp_O_str`, `dp_R_E_1m3Err_void`, `dp_T_1m1S`, `dp_E_1m5Shape` |
| функция `m.f` | `dpf_1m1f` |
| локальная и параметр | `l<номер>_<имя>` |
| строка программы | `dp_s<номер>` — массив байтов |
| временные | `dp_v` (операнд), `dp_e` (значение), `dp_p` (указатель на элемент), `dp_b` (байт строки), `dp_c`, `dp_n` |

Тип, содержащий свой тип через `List` (`type.recursive`), допустим:
сначала идут объявления всех структур (`typedef struct X X;`), потом
определения в порядке зависимостей. Элемент списка — указатель, ему
хватает объявления.

## 4. Функции типов

Для каждого составного типа программы бэкенд пишет:

- `dp_eq__<запись>` и `dp_lt__<запись>` — сравнение, как у
  интерпретатора: структура и список — по частям слева направо,
  перечисление — по номеру варианта, затем по данным; `?T` и `E!T` не
  упорядочены (`<` всегда ложно);
- `dp_drop__<запись>` и `dp_copy__<запись>` — у типов с памятью
  (`ir::needs_drop`): освобождение и глубокая копия;
- методы `List[T]` — `push`, `pop`, `insert`, `remove`, `clear`, `sort`,
  `contains`, `repeat`, `split` (у `List[str]`);
- методы `Map[K, V]` (Р54) — `dp_mfind`, `dp_mset`, `dp_mvalue`,
  `dp_mget`, `dp_mcontains`, `dp_mremove`, `dp_mclear`, `dp_mkeys`.

`Map` хранит ключи и значения в массивах в порядке вставки, но наружу
этот порядок не виден: `dp_mkeys` копирует ключи и сортирует их
(`dp_sort` списка ключей), а `for k in &m` обходит такой снимок. Обход —
O(n log n), от хэша не зависит. Поиск — открытая адресация по индексу `slots`
(позиция + 1, 0 — пусто; размер — степень двойки, заполнен не больше
чем наполовину). Хэш — `dp_hash_u64` у целых и `bool`, `dp_hash_str`
(FNV-1a) у `str`, без случайной соли (`docs/runtime/README.md`).
Вставка, замена и поиск — O(1) в среднем; `remove` сдвигает пары и
строит индекс заново — O(n).

`push` удваивает ёмкость (с 4). Удвоение сверх предела буфера
(`docs/runtime/README.md`) заменяется ростом на один элемент: ловушка
«out of memory» срабатывает, только когда в предел упирается сам список.
Пределы памяти у интерпретатора и runtime разные (`trap.memory`
оставляет их реализации), поэтому различающий тест `trap_memory`
просит больше обоих.
`sort` — та же сортировка слиянием снизу вверх, что у интерпретатора:
при любом сравнении, и с `nan`, перестановка одна и та же.

## 5. Значения и память

- **Копия и перенос.** Операнд `Copy` значения с памятью копируется
  глубоко (`dp_copy__…`). Операнд `Move` забирает значение: место
  обнуляется. Значение, забранное только для чтения, освобождается после
  инструкции.
- **Присваивание** `dst = rv`: значение `rv` вычисляется во временное,
  затем находится место `dst`, его прежнее значение освобождается, и
  новое записывается. Инструкция `Drop` освобождает место и обнуляет
  его.
- **Локальные** обнулены на входе в функцию: пустое значение —
  освобождённое.
- **Параметры по ссылке** (`&T`, `&mut T`) — указатели; место параметра
  в C — `(*l<номер>_<имя>)`.

## 6. Функции, ловушки, вход

- Функция — `static` с пометкой `DP_FN`: функция без вызовов — законная
  программа dpl и не даёт предупреждения. Блоки IR — метки `bbN:`
  (только у целей переходов), инструкция — блок `{ … }` со своими
  временными, перед ним `#line` с местом инструкции в исходнике.
- Глубина вызовов (`trap.memory`): функция увеличивает `dp_depth` на
  входе и уменьшает перед `return`. Вызов проверяет предел
  (`DP_CALL_CHECK`) до входа: сверх него — ловушка «stack overflow» в
  месте вызова, как у интерпретатора.
- Место ловушки — строка `"файл:строка:столбец"`. Её передают функции
  runtime, которые могут остановить программу. Терминатор `Trap` —
  `dp_trap`, `Unreachable` — `dp_unreachable` (внутренняя ошибка, код 3).
- Вход: `dp_entry` вызывает `main` программы. Если `main` возвращает
  `E!void`, при ошибке `dp_entry` возвращает запись `E.V` из таблицы
  `dp_errname`. Сгенерированный `main` C передаёт `dp_entry` в `dp_run`
  (runtime), который даёт код выхода (`trap.exit`).

## 7. Тесты

Проход `native` в `tests/run.py` (`docs/compiler/README.md`, «Тесты»).
Каждая программа набора `run`:

1. переводится `dpl debug c`;
2. собирается с runtime компилятором C (`$CC` или `cc`) с флагами
   раздела 2 и санитайзерами, если они есть;
3. запускается в каталоге набора.

Вывод сверяется с тем же ожидаемым `X.out`, что у интерпретатора.
Программа с ошибками проверки (код 1) пропускается: её диагностику
сверяет набор `run`. Объекты runtime и программы лежат в
`build/compiler/native/`.

Проход `cross` делает то же для цели `windows-x86_64`: `dpl build
--target windows-x86_64` в профилях debug и release, запуск под Wine
(`docs/policy/PLATFORMS.md`). Без инструментов цели проход пропускается,
и итог `tests/run.py` говорит об этом.

Проверено gcc и clang. Набор `run` покрывает:

- арифметику и её ловушки;
- преобразования;
- строки и списки;
- структуры, перечисления и `match`;
- рекурсивные типы;
- ссылки;
- `defer`;
- модули;
- ошибку `main`;
- переполнение стека и предел памяти.

## 8. Пределы v0.1

- Один файл C на программу: раздельной сборки по модулям нет (кэш —
  v0.4, Р43).
- Цель — Linux (`runtime/linux/`). Windows и Android — со своими входами
  runtime (`docs/policy/PLATFORMS.md`).
- Оптимизаций на уровне IR нет; оптимизирует компилятор C.
