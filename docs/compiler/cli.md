# CLI `dpl`

Описание устройства командной строки компилятора v0.1
(`ROADMAP/IMPLEMENTATION.md`, шаг 10; команды — Р15). Код —
`compiler/driver/`. Внутреннее устройство компилятора —
`docs/compiler/README.md`.

## 1. Общее

```
dpl <команда> [аргументы]
```

| команда | что делает |
|---|---|
| `check [--format=json] <file.dpm>` | проверяет программу: главный модуль и всё, что он импортирует |
| `build [--release] [--lib] [--target <цель>] [-o <путь>] <file.dpm>` | собирает нативную программу; `--lib` — статическую библиотеку для хоста C (Р61) |
| `test [--target <цель>] [--timeout <секунды>] <file.dpm>` | исполняет тесты программы — функции `@test` (Р50) |
| `fmt [--check] <file.dpm>…` | приводит файлы к каноническому виду на месте |
| `explain <код>` | объясняет код диагностики, например `E0101` |
| `help`, `--version` | справка и версия |
| `worker …` | один запрос онлайн-сервиса (`docs/service/README.md`) |
| `debug …` | отладочные команды; их вывод не стабилен (раздел 8) |

Остальные команды Р15 — `fix` и `query` — появятся позже (v0.4).

**Коды выхода** (у программ, которые собирает `build`, — свои,
`docs/runtime/README.md`, раздел 7):

| код | значит |
|---|---|
| 0 | успех |
| 1 | в программе ошибки (диагностика); у `test` — упал хотя бы один тест; у `fmt --check` — есть файлы не в каноническом виде |
| 2 | неверный вызов или окружение: неизвестная команда или параметр, нет компилятора C или runtime |
| 3 | внутренняя ошибка компилятора |
| 4 | только у `worker` (`compiler/driver/worker.h`) |

**Окружение:**

| переменная | для чего | по умолчанию |
|---|---|---|
| `CC` | компилятор C для `build` и `test` на хосте | `cc` |
| `DPL_CROSS_CC` | компилятор C для другой цели (`--target`) | у Android — clang из NDK, у остальных — `clang` |
| `ANDROID_NDK_HOME` | каталог Android NDK | `/opt/android-ndk` |
| `DPL_RUNNER` | чем запускать тесты другой цели | у цели: `wine` для `windows-x86_64`, `qemu-aarch64` для `android-arm64` |
| `DPL_AR` | архиватор `build --lib` | у хоста — `ar`; у других — `llvm-ar` рядом с компилятором C или из `PATH` |
| `DPL_RUNTIME` | каталог runtime (`core/` и порты `linux/`, `windows/`) | `runtime/` репозитория рядом со сборкой: `<каталог dpl>/../../runtime` |
| `DPL_STDLIB` | каталог стандартной библиотеки | `<каталог dpl>/../../stdlib` |
| `DPL_BINDINGS` | каталог привязок (Р58): модуль `m` — `m/m.dpm` | `<каталог dpl>/../../bindings` |
| `TMPDIR` | временный каталог сборки | `/tmp` |

## 2. `check`

Проверяет программу: разбор, модули и имена, типы, поток, ошибки,
ссылки (`docs/spec/core.md`, разделы 1–8). Код программы не строится, и
`main` для проверки не нужна.

- **Текст** (по умолчанию) — в stderr, по сообщению на ошибку:
  `файл:строка:столбец: error[E0xxx]: сообщение`, затем строка исходника
  с отметкой `^~~` и примечания. Сообщения — по-английски (Р47) и по
  порядку: файл, позиция, код.
- **JSON** (`--format=json`) — один документ в stdout:
  `{"diagnostics":[…]}`. Схема — `docs/compiler/diagnostics.schema.json`
  (JSON Schema 2020-12). У сообщения есть `severity`, `code`, `message`,
  место (`file`, `line`, `col`, `end_line`, `end_col` — с 1; столбец — в
  символах UTF-8) и `notes`. Сообщение без места (например, E0322) — без
  полей места. Каждый снимок набора `diag` проверяется по схеме.

## 3. `build`

Собирает нативную программу:
1. проверка программы (как `check`) и её входа `main` (E0322);
2. понижение в Core IR и верификатор (`docs/ir/README.md`);
3. C-бэкенд (`docs/compiler/backend_c.md`);
4. компилятор C цели вместе с runtime (`docs/runtime/README.md`).

**Цель** — `--target <цель>` (`docs/policy/PLATFORMS.md`); по умолчанию
— хост:

| цель | компилятор C и флаги | порт runtime | программа | тесты |
|---|---|---|---|---|
| `linux-x86_64` (хост) | `$CC` или `cc`; `-lm -pthread` | `runtime/linux` | `./prog` | сама программа; профиль `test` — с ASan и UBSan |
| `windows-x86_64` | `$DPL_CROSS_CC` или `clang`; `--target=x86_64-w64-mingw32 -fuse-ld=lld -Wl,--no-insert-timestamp -D__USE_MINGW_ANSI_STDIO=1`, `-lshell32` | `runtime/windows` | `./prog.exe` | под `$DPL_RUNNER` или `wine`; без санитайзеров |
| `android-arm64` | `$DPL_CROSS_CC` или clang из NDK; `--target=aarch64-linux-android24 -static`, `-lm` | `runtime/linux` (POSIX, bionic) | `./prog`, статическая | под `$DPL_RUNNER` или `qemu-aarch64`; без санитайзеров |

Перед сборкой для другой цели инструменты проверяются пробной сборкой
пустой программы: не работают — сообщение и код 2, а не внутренняя
ошибка. Инструменты в контейнере разработки ставят
`tools/setup/cross_windows.sh` и `tools/setup/cross_android.sh`.

Runtime связывается статически (Р43): его исходники собираются вместе с
программой. Сгенерированный C пишется во временный каталог и после
сборки удаляется: места в программе даёт `#line` по исходнику `.dpm`.

Сборка воспроизводима (`docs/policy/DETERMINISM.md`, раздел 6): те же
исходники, инструменты, цель и профиль дают те же байты в любом каталоге.
- Модули программы — по пути, как он дан (`main.dpm` и соседи — от
  текущего каталога); модули стандартной библиотеки и привязок — без
  каталога установки: `stdlib/os.dpm`, `bindings/vulkan/vulkan.dpm` (в
  сообщениях, местах ловушек и `#line`).
- Компилятор C получает `-ffile-prefix-map`: текущий каталог — `.`,
  каталог runtime — `dpl-runtime`, временный каталог — `dpl-build`.
  Отладчику исходники runtime показывают командой вроде `directory`
  (gdb) или `settings set target.source-map` (lldb).
- Архив `--lib` — без времени и владельца членов (`ar rcsD`); у
  `windows-x86_64` — без времени сборки в заголовке PE
  (`-Wl,--no-insert-timestamp`).

- `-o <путь>` — где положить программу; по умолчанию — имя главного
  модуля в текущем каталоге (`prog.dpm` → `./prog`, у Windows —
  `./prog.exe`). Программа
  собирается во временном каталоге и потом копируется в `<путь>`:
  неудачная сборка прежний файл не трогает.
- **Профили** (`docs/design/ARCHITECTURE.md`, раздел 8). Проверки во
  всех профилях одни и те же (Р11); смысл программы от профиля не
  зависит.

| профиль | как выбрать | флаги C сверх общих |
|---|---|---|
| `debug` | по умолчанию | `-O0 -g` |
| `release` | `--release` | `-O2` |
| `test` | `dpl test` | `-O0 -g` и `-fsanitize=address,undefined -fno-sanitize-recover=all`, если компилятор C их умеет |

Общие флаги — `-std=c11 -ffp-contract=off -fno-strict-aliasing -w`, за
ними флаги цели; библиотеки `@link("lib")` функций C (Р59) — `-llib`
перед библиотеками цели (зачем — `docs/compiler/backend_c.md`, раздел 2). Предупреждения
компилятора C у пользователя выключены (`-w`). Сгенерированный код и без
того должен собираться без предупреждений с `-Werror`: это проверяет
проход `native`.

**Сбои.** Нет компилятора C или runtime, в `<путь>` нельзя записать
(например, это каталог) — сообщение и код 2. Компилятор C
отверг сгенерированный код — внутренняя ошибка, код 3, его собственный
вывод — в stderr.

**Библиотека** — `--lib` (Р61; `docs/spec/core.md`, ffi.lib): функции
`@export` для хоста на C или C++.
- `main` не нужна; сборка — те же шаги и профили, для любой цели.
- Сгенерированный C, `dp_rt.c` и порт runtime компилируются по одному
  (`-c`, у Linux и Android — ещё `-fPIC`) и ложатся в архив `ar rcs`.
- `-o` — путь архива, по умолчанию `lib<модуль>.a`. Заголовок — рядом,
  имя без `lib` и расширения: `out/libgame.a` → `out/game.h`, метка
  `DPL_GAME_H`.
- Вторая строка заголовка — чем компоновать хост на этой цели:
  `// Компоновка хоста (linux-x86_64): libgame.a -lm -pthread` —
  библиотеки `@link` функций C и библиотеки цели.
- Хост: `cc -I out host.c out/libgame.a -lm -pthread`. Ловушка в функции
  `@export` завершает процесс хоста с кодом 101, как программу. Глубина
  вызовов dpl считается и через колбэки; стек — потока хоста.

## 4. `test`

Тест — функция с атрибутом `@test` без параметров, с результатом `void`
или `E!void` (Р50, `docs/spec/core.md`, module.test). `dpl test`
1. проверяет программу; `main` не нужна;
2. собирает все тесты программы, кроме тестов стандартной библиотеки, в
   одну программу в профиле `test`;
3. исполняет каждый тест отдельным процессом: ловушка или ошибка валит
   только его. С `--target` — для этой цели, запуском через её runner
   (у Windows — `wine`, у Android — `qemu-aarch64`);
4. пишет отчёт в stdout.

Отчёт — строка на тест по порядку модулей (сначала импортируемые) и
объявлений, затем вывод упавших тестов и итог:

```
test calc.divides ... ok
test calc.traps ... FAILED

--- calc.traps (exit 101)
before the trap
calc.dpm:33:13: trap: index 1 is out of bounds for length 0

test result: FAILED. 1 passed; 1 failed
```

- Тест прошёл, если процесс завершился с кодом 0.
- Вывод прошедшего теста не показывается. У упавшего — его stdout, затем
  stderr: ловушка (`trap.def`) или `error: test failed with E.V`.
- Код выхода `dpl test`: 0 — все прошли (и когда тестов нет), 1 — упал
  хотя бы один.
- Предел времени — `--timeout <секунды>` на тест, по умолчанию 60
  (`kDefaultTestTimeout`, `driver/build.h`), `0` — без предела. Тест
  дольше предела снимается вместе с группой процессов (с runner-ом
  цели) и считается упавшим: `--- calc.hangs (timed out after 60 s)`,
  затем вывод, который успел дойти до файла: буфер вывода снятого
  процесса теряется.

## 5. `fmt`

Приводит файлы к каноническому виду на месте: один формат без настроек
(Р7). Печать — по AST и токенам дерева без потерь
(`compiler/syntax/printer.cpp`):
- отступ — 4 пробела, конец строки — LF, лишние пробелы убираются;
  литералы — как записаны;
- комментарий на своей строке стоит перед следующим элементом своего
  контейнера (объявление, поле, вариант, инструкция, ветвь `match`) или
  в конце контейнера; комментарий после кода остаётся в конце строки;
  комментарий внутри многострочного выражения печатается своей строкой
  перед инструкцией;
- пустые строки сохраняются, не больше одной подряд; между объявлениями
  модуля пустая строка есть всегда, кроме соседних `import`;
- пустой блок без комментариев — `{}`;
- ширина строки — до 100 символов (решение автора, 1 ноября 2026). Что
  не влезает, переносится там, где конец строки выражение не кончает
  (syntax.newline):
  - аргументы вызова, элементы списка, поля литерала структуры и
    варианта, параметры функции — по одному на строку с отступом +4,
    закрывающая скобка — своей строкой, без запятой в конце;
  - цепочка одного бинарного оператора (`a + b + c`, `x && y && z`) —
    на строку сколько влезает, оператор в конце строки, продолжение — с
    отступом +4;
  - список ломается раньше вложенного: сперва внешний, затем то, что
    всё ещё не влезает. Комментарий и длинный литерал строки не
    переносятся. Раскладка — документ с группами, как у Wadler и
    Prettier.

Перед записью печать проходит проверку круга, ту же, что `debug parse`:
- печать разбирается в то же дерево;
- печать печати не меняется;
- комментарии те же — не потеряны и не повторены.

Не прошла — внутренняя ошибка (код 3), файл не меняется. Файл с ошибками
разбора тоже не меняется: диагностика и код 1. Запись — через временный
файл рядом и переименование, права файла сохраняются; записать нельзя —
E0003.

`--check` ничего не пишет. Он перечисляет в stdout файлы, которые
изменились бы, и выходит с кодом 1, если такие есть.

## 6. `explain`

`dpl explain E0401` печатает код, заголовок и объяснение из реестра
диагностики (`compiler/support/codes.def`). Неизвестный код — код
выхода 2.

## 7. Тесты CLI

| что | где |
|---|---|
| вызовы и сообщения об ошибках вызова | набор `cli` (`tests/cli/*.args`) |
| `check --format=json` и схема | набор `diag`, каждый снимок проверяется по `diagnostics.schema.json` (`tests/schema.py`) |
| `fmt` | набор `fmt`: файл правится в копии, ожидаемое — текст после `fmt`, вывод и код; второй прогон `--check` ничего не находит |
| `build` | проход `build`: каждая программа набора `run` собирается в профилях `debug` и `release` и совпадает с эталонным интерпретатором |
| `build --lib` | проход `lib`: `tests/lib/X/main.dpm` — библиотекой, `X/host.c` — хостом с ней компилятором цели; вывод хоста на трёх целях — `X.out` |
| воспроизводимость | проход `repro` (`tests/repro.py`): две сборки в разных каталогах и с dpl по разным путям — те же байты: debug и release хоста, `--lib`, другие цели и пакет APK примера, если их инструменты есть |
| `test` | набор `test`: отчёт `dpl test`; тесты отказа E0323 — набор `fail` |

## 8. Отладочные команды

`dpl debug lex|parse|print|summary|types|ir|run|c <file.dpm>` — для
тестов компилятора; формат вывода не стабилен (S2). `debug run` —
эталонный интерпретатор (Р43: только для тестов), `debug c` —
сгенерированный C. Описание — `docs/compiler/README.md`.
