# Компилятор DPlang: устройство и сборка

Описание устройства компилятора v0.1 (`ROADMAP/IMPLEMENTATION.md`).
Целевая архитектура — `docs/design/ARCHITECTURE.md`; решения — Р34
(C++20 в подмножестве VoxelRPG), Р43 (устройство v0.1), Р47 (сообщения
по-английски).

## Сборка

```sh
cmake -S compiler -B build/compiler -G Ninja -DCMAKE_BUILD_TYPE=Debug -DDPLANG_SANITIZE=ON
cmake --build build/compiler     # → build/compiler/dplang
```

Так собирает и исполнитель тестов. Флаги для всех файлов: C++20, без
исключений и RTTI, `-Wall -Wextra -Wpedantic -Werror`. Опция
`DPLANG_SANITIZE` добавляет ASan и UBSan — для тестов и проверок.
Внешних зависимостей нет. Компилятор C++ — `$CXX` или `g++`. `clang++`
тоже собирает; в контейнере сессии — без санитайзеров, у clang там нет
библиотек ASan.

## Раскладка

| каталог | что |
|---|---|
| `compiler/support/` | исходники и позиции (`source.h`), диагностика (`diag.h`), реестр кодов (`codes.def`), UTF-8 и запись JSON |
| `compiler/syntax/` | токены (`tokens.def`), лексер (`lexer.h`), значения литералов (`literal.h`), AST (`ast.h`), парсер (`parser.h`), каноническая печать (`printer.h`), дамп AST (`ast_dump.h`) |
| `compiler/sema/` | проверка программы (`sema.h`): загрузка модулей (`loader.cpp`), объявления и сводки (`collect.cpp`, `summary.cpp`), разрешение типов в записи (`resolve.h`), вывод типа ошибки `!T` (`errinfer.cpp`), тела (`checker.h`: `check.cpp` — инструкции и поток, `check_expr.cpp` — выражения и константы, `check_pat.cpp` — образцы и полнота `match`); типы (`types.h`), объявления (`defs.h`), встроенное (`builtins.h`) |
| `compiler/ir/` | Core IR (`ir.h`), понижение AST → IR (`lower.h`), верификатор (`verify.h`), эталонный интерпретатор (`interp.h`), текстовая запись (`dump.h`); устройство — `docs/ir/README.md` |
| `compiler/backend_c/` | C-бэкенд: Core IR → C11 (`emit_c.h`); устройство — `docs/compiler/backend_c.md` |
| `compiler/driver/` | CLI `dplang` (`main.cpp`) |
| `compiler/fuzz/` | фаззер «не падает» `dpfuzz` |
| `runtime/` | runtime на C11 для сгенерированного C: ядро `core/`, вход под Linux `linux/`; устройство — `docs/runtime/README.md` |
| `tests/` | наборы золотых тестов и их исполнитель `tests/run.py` |

С шагом 11 появится `stdlib/` (`docs/design/ARCHITECTURE.md`,
раздел 10).

## Правила кода

- Подмножество C++ — как в VoxelRPG (Р34): исключений и RTTI нет.
  Ошибка — значение или диагностика.
- Ошибка пользователя — диагностика с кодом из `compiler/support/codes.def`,
  а не падение. Падение компилятора — всегда ошибка компилятора.
- Вывод детерминирован: одинаковые входы — одинаковые байты.
  Диагностика сортируется по файлу, позиции и коду.
- Изменяемого глобального состояния нет. Каждый проход — функция с явными
  входами и выходами (Р43).
- Комментарии — по-русски; имена и тексты сообщений — по-английски (Р47).

## Лексер

- Токены покрывают файл без пропусков: пробелы, комментарии и переводы
  строк — тоже токены. На этом стоит дерево разбора без потерь (шаг 3).
- Ошибка лексики не останавливает разбор: неверный участок становится
  токеном `Error`, сообщение получает код E01xx.
- Значения литералов вычисляет `syntax/literal.h`; лексер проверяет
  литералы теми же функциями.
- Правила — `docs/spec/core.md`, раздел 1.

## Парсер и дерево без потерь

- Рекурсивный спуск с приоритетами операторов (`docs/spec/core.md`,
  раздел 2). Разбор не зависит от типов (Р7).
- **Дерево без потерь** — токены файла (с пустотами) и AST, у каждого
  узла которого есть участок исходника. По участку узел находит свои
  токены, а печать токенов по порядку восстанавливает файл байт в байт.
  Отдельного слоя CST в v0.1 нет: комментарии форматер возьмёт из
  токенов по позициям (шаг 10).
- Узлы живут в арене модуля (`ast::Module`); вид — поле `kind`,
  приведение — `ast::as<T>()` (RTTI нет).
- **Восстановление.** После ошибки остаток инструкции пропускается до
  конца строки или `}`, остаток объявления — до следующего объявления
  в начале строки. Ключевое слово инструкции или объявления в начале
  строки останавливает пропуск даже внутри незакрытых скобок. Одна
  ошибка — одно сообщение, модуль разбирается до конца. У токена ошибки
  лексики парсер не сообщает.
- **Круг «разбор → печать → разбор».** `debug parse` у модуля без ошибок
  печатает его в каноническом виде, разбирает печать и сверяет дамп. Ещё
  он проверяет, что печать печати не меняется. Расхождение — внутренняя
  ошибка (код 3). Фаззер делает то же на испорченных входах.

## Проверка программы

Порядок — функции с явными входами (Р43):

1. **Загрузка** (`load_program`). Главный модуль и его импорты (Р46):
   разбор, граф без циклов, порядок зависимостей. Если модуль не найден,
   не разобран или есть цикл, дальше проверка не идёт — иначе сообщения
   были бы следствием первой ошибки.
2. **Объявления** (`collect`). Области имён модулей, типы полей,
   вариантов и сигнатур, правила сводок: тип ошибки в `pub` (Р41), нет
   закрытых типов в открытых объявлениях. Модули идут в порядке
   зависимостей, и зависимый видит только сводки своих импортов.
3. **Вывод типа ошибки** (`infer_errors`). У непубличных функций `!T`
   (Р41) — по записи их `fail` и `try`, итерациями до неподвижной точки.
4. **Тела** (`check`). Один обход: имена с областями (без затенения),
   типы с ожидаемым типом для литералов, `none`, `[]` и `.V`, неявные
   преобразования (`Expr::conv`), вызовы (`CallExpr::call`), места и
   изменяемость, ссылки (Р44, общий корень в одном вызове), поток —
   определённая инициализация, возврат, циклы, `defer` — и полнота
   `match`. Константы вычисляются при первом обращении (`const_value`).
   Результаты пишутся в поля AST (`Res`, `Local`, `type`, `conv`, `call`,
   `field`) — этим AST и пользуется понижение в Core IR.
5. **Понижение и верификатор** (`ir::lower`, `ir::verify`). Программа без
   ошибок понижается в Core IR, верификатор проверяет его инварианты;
   нарушение — внутренняя ошибка (код 3). Для запуска нужна `main`
   (`check_main`, E0322). Устройство — `docs/ir/README.md`.

Кэш по модулю (Р43) в v0.1 — в памяти одного запуска; на диске — с
инкрементальной сборкой в v0.4.

## Диагностика

Текстовый вид — одна строка на сообщение, затем строка исходника и метка:

```
path/file.dpm:3:13: error[E0101]: unterminated string literal
   3 |     let x = "abc
     |             ^~~~
```

Машиночитаемый вид — JSON `{"diagnostics": [...]}`. У каждого сообщения
есть поля `severity`, `code`, `message`, `file`, `line`, `col`,
`end_line`, `end_col` и `notes`. Схема — `docs/compiler/cli.md` (шаг 10).
Коды объясняет `dplang explain <код>`.

## Тесты

```sh
python3 tests/run.py              # собрать и прогнать (шаг «компилятор» в tools/check/run.sh)
python3 tests/run.py --bless      # переписать ожидаемое — только осознанно, дифф на ревью
python3 tests/run.py -k cli       # отбор по подстроке пути
```

Тест — вход в каталоге набора и ожидаемое `X.out` рядом с ним:

- stdout;
- `--- stderr ---` и stderr, если он не пуст;
- `[exit N]`, если код выхода не 0.

Команда запускается из каталога набора.

| набор | вход | команда |
|---|---|---|
| `cli` | `X.args` — аргументы | `dplang <аргументы>` |
| `lex` | `X.dpm` | `dplang debug lex X.dpm` — токены без пробелов |
| `parse` | `X.dpm` | `dplang debug parse X.dpm` — дамп AST и проверка круга; ошибки грамматики и восстановление |
| `print` | `X.dpm` | `dplang debug print X.dpm` — каноническая печать реальных программ (решения набора v0.0 в записи B) |
| `sema` | `X.dpm` или каталог `X/` с `main.dpm` | `dplang check` — модули, имена, сводки; ожидаемое — диагностика |
| `summary` | то же | `dplang debug summary` — сводки модулей программы |
| `types` | то же | `dplang debug types` — AST главного модуля с типами и неявными преобразованиями |
| `fail` | то же | `dplang check` — отказ компиляции: у каждого кода E04xx и E05xx — хотя бы один случай |
| `diag` | `X.dpm` | `dplang check --format=json` — снимки машиночитаемой диагностики |
| `ir` | `X.dpm` или каталог `X/` с `main.dpm` | `dplang debug ir` — золотые дампы Core IR после верификатора |
| `run` | то же | `dplang debug run` — исполнение эталонным интерпретатором: вывод, ловушки, код выхода |
| `fuzz` | `X.args` — аргументы | `dpfuzz lex\|parse\|check <аргументы>`: корпус — файлы `.dpm` наборов, зерно и число входов заданы; `check` — разбор и проверка без падений, программы без ошибок ещё понижаются и проходят верификатор |

Проход `verify` — не набор, а проверка всех программ `.dpm` наборов:
`dplang debug ir` на каждой. Программа с ошибками даёт код 1, без них — 0;
внутренняя ошибка или падение — сбой. Так верификатор Core IR проходит
по всем тестам (`docs/policy/TESTING.md`, раздел 2).

Проход `native` — различающие тесты C-бэкенда: каждая программа набора
`run` переводится `dplang debug c`, собирается с runtime компилятором C
(`$CC` или `cc`, с ASan и UBSan, если они есть) и запускается. Вывод
сверяется с тем же ожидаемым, что у интерпретатора. Подробно —
`docs/compiler/backend_c.md`, раздел 7.

Наборы добавляются вместе с шагами (`docs/policy/TESTING.md`, раздел 4);
их список — `SUITES` в `tests/run.py`.
