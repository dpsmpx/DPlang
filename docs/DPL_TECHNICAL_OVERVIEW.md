# DPL — технический обзор языка для независимой оценки

**Назначение документа:** помочь стороннему системному или игровому разработчику понять устройство DPL, его сильные стороны, ограничения и степень готовности, а затем решить, стоит ли рассматривать переход на него после выхода стабильной версии.

**Срез проекта:** 4 ноября 2026 года. Основа — рабочая ветка `ccr-2f3ecd06-svadio`, коммит `25a007e7d70df8547b430bbb98cb131a08bbb5b7` от 1 ноября 2026 года. Эта ветка содержит один коммит сверх `main` (`2ae990ee7f4fe3ce24dd50a083c06dc270bcba9c`) и связана с открытым черновым PR #47 о воспроизводимой сборке. Это описание относится к указанному срезу, а не к будущей версии 1.0.

**Как читать статус возможностей:**
- **Реализовано** — возможность есть в текущем коде/спецификации и для неё предусмотрены проверки.
- **Реализовано частично** — есть рабочая основа или демонстрация, но не выполнены все критерии выпуска.
- **Запланировано** — это пункт дорожной карты, а не обещание уже существующего инструмента.
- **Гарантия v1.0** — целевое обязательство, которое должно быть подтверждено до объявления стабильной версии.

## 1. Краткое описание

DPL (`dpl`, исходные файлы с расширением `.dpm`) — разрабатываемый компилируемый системный язык общего назначения с особым вниманием к игровым движкам, симуляциям, инструментам разработки и приложениям для конечных устройств.

Его главная идея — не предложить ещё один синтаксис для привычного C++, а перенести часть работы и ответственности из прикладного кода в компилятор и инструменты. Язык стремится сделать ряд ошибок невозможными или обнаруживаемыми до запуска: некорректный доступ к памяти, использование устаревших хэндлов, неправильное управление некоторыми ресурсами, часть ошибок конкурентного доступа и случайное попадание недетерминированных операций в детерминированную логику.

Ключевые характеристики текущего проекта:

- **Нативная компиляция.** Программа проходит фронтенд DPL, понижается во внутреннее представление Core IR, затем переводится в C11 и собирается системным C-компилятором вместе с runtime.
- **Собственная система типов и собственная семантика.** DPL не является диалектом C++ и не совместим с C++ ABI. Для сосуществования с C и C++ предусмотрен C ABI.
- **Безопасность по умолчанию.** В языке нет открытого доступа к произвольным указателям и арифметики указателей. Ссылки ограничены вызовами функций и обходами коллекций; они не могут сохраниться в поле или вернуться из функции.
- **Явные ошибки и ресурсы.** Ошибки — значения `E!T`, а ресурсы, которые нужно закрывать, описываются линейными типами `@linear` и управляются через `defer`/`errdefer`.
- **Детерминизм как проверяемая характеристика.** Код можно отнести к классу D (`@det`), в котором компилятор запрещает вызовы недетерминированного или платформозависимого кода.
- **Параллелизм с ограничениями.** Есть `parallel for`, блоки задач `tasks`/`spawn`, атомики, мьютексы и каналы. Компилятор проверяет часть правил доступа к общим данным.
- **Целевые платформы первой волны:** Linux x86-64, Windows x86-64 и Android arm64.
- **Инструменты сейчас:** `check`, `build`, `test`, `fmt`, `explain`; поддерживаются debug/release-сборки и кросс-компиляция.

DPL следует рассматривать как потенциальную альтернативу для определённого класса системных и игровых задач, а не как готовую универсальную замену C++, Rust или другого зрелого языка.

## 2. Для каких задач проектируется язык

### 2.1. Основная область применения

Язык задуман для разработки сложных приложений, в которых важны:

- предсказуемое поведение на разных платформах;
- детерминированная симуляция и воспроизведение состояния;
- контролируемые затраты памяти и производительности;
- обработка большого числа сущностей;
- многопоточность;
- работа с нативными библиотеками и системными API;
- возможность постепенно внедрять новый код рядом с существующим C/C++.

Игровая направленность выражается не в наличии встроенного игрового движка, редактора или игрового API, а в приоритетах дизайна языка: пулы сущностей и хэндлы, детерминированные вычисления, фиксируемые правила конкурентного доступа, управление ресурсами и нативная интеграция с графическими API.

### 2.2. Приоритеты проекта

При конфликте целей в документах проекта задан следующий порядок:

1. корректность и надёжность;
2. детерминизм;
3. контролируемость поведения и ресурсов;
4. эволюционируемость языка;
5. проверяемость и качество диагностики;
6. скорость разработки, сборки и работы с ИИ;
7. простота и эргономика синтаксиса;
8. переносимость за пределы выбранных целевых платформ.

Поэтому краткость синтаксиса не должна оправдывать менее надёжную семантику. Работа с ИИ — важная цель, но она оценивается не по тому, насколько код выглядит коротким, а по числу токенов и циклов исправления, необходимых для принятого и корректного изменения.

### 2.3. Чем DPL не является

DPL не является:

- скриптовым языком, который существует только внутри игрового движка;
- DSL только для описания игровой логики;
- надмножеством C++;
- заменой C++ с сохранением его ABI;
- системой формального доказательства программ;
- языком, который уже предлагает экосистему и стабильность зрелых компиляторов.

## 3. Архитектура компилятора и модель исполнения

### 3.1. Конвейер

Упрощённая схема сборки:

```text
.dpm source files
      │
      ▼
lexer / parser
      │
      ▼
semantic analysis
(modules, names, types, control flow, references, errors)
      │
      ▼
Core IR
      │
      ▼
IR verifier
      │
      ▼
C11 backend
      │
      ▼
C compiler + DPL runtime
      │
      ▼
native executable / static library
```

Компилятор DPL написан на C++20 в ограниченном подмножестве языка. Собственный фронтенд разбирает исходники, проверяет семантику и типы, формирует Core IR. IR проверяется отдельным верификатором. Затем C-бэкенд создаёт C11-код, который собирается системным C-компилятором.

Эталонный интерпретатор Core IR существует для тестирования и сравнения поведения. Согласно архитектурному решению проекта, он не является частью production-пути исполнения пользовательской программы. При проверках вывод и код завершения интерпретатора сравниваются с результатом нативной сборки.

### 3.2. Что это означает для разработчика

DPL — не интерпретируемый язык и не просто генератор исходников, который пользователь обязан вручную поддерживать. Нативную сборку выполняет команда `dpl build`; сгенерированный C используется как промежуточный артефакт компилятора.

Вместе с программой статически собирается runtime DPL. На Linux и Android используется POSIX-ориентированный порт runtime; для Windows есть отдельный порт. Runtime отвечает за ловушки, память встроенных значений, строки, вывод, аргументы программы, файлы и платформенный вход.

Практическая зависимость от C toolchain остаётся: для сборки необходимы совместимые C-компилятор, системные библиотеки и, при кросс-компиляции, соответствующий SDK/NDK и инструменты целевой платформы.

### 3.3. Цели сборки

| Цель | Текущий путь сборки | Как проверяется |
|---|---|---|
| Linux x86-64 | Хостовый C-компилятор, runtime Linux | Полный набор на Linux |
| Windows x86-64 | Clang + LLD поверх MinGW-w64 | Кросс-сборка и запуск тестов под Wine; периодическая проверка на настоящей Windows ещё требуется |
| Android arm64 | Clang из Android NDK, API 24; статические консольные программы | Набор запускается через qemu-aarch64; графическая программа собирается в APK через SDL3 и проверялась на устройстве автора |

Все три цели обозначены в матрице платформ как уровень поддержки 1. При этом важно различать автоматизированную проверку в эмуляторе и проверку на реальном устройстве: весь набор Android-тестов не равнозначен полному тестированию на физическом Android-устройстве, а прохождение Windows под Wine не заменяет проверку на настоящей Windows.

Первая волна предполагает 64-битные цели, little-endian и IEEE 754. Другие архитектуры и системы (например, iOS, macOS arm64, Linux arm64, Windows arm64) не входят в текущую первую волну.

## 4. Синтаксис и организация программы

### 4.1. Исходные файлы и модули

Один модуль — один UTF-8-файл `.dpm`. Имя модуля совпадает с именем файла без расширения. Импорт выглядит так:

```dpl
import os
import world
```

Поиск модуля выполняется рядом с главным модулем программы, затем в стандартной библиотеке, затем в каталоге привязок. Циклические импорты не допускаются. Объявления модуля — функции, структуры, перечисления, константы и импорты. Публичные имена помечаются `pub`.

```dpl
pub struct Unit {
    hp: i32
    alive: bool = true
}

const MAX_UNITS: i32 = 100

pub fn spawn(units: &mut List[Unit], hp: i32) int {
    units.push(Unit { hp })
    return len(units) - 1
}
```

Порядок объявлений в файле не важен. Из другого модуля доступ идёт через имя модуля: `world.spawn(...)`, `world.Unit`. Открытая функция не может выставлять в публичной сигнатуре закрытые типы.

### 4.2. Синтаксические особенности

- Инструкции заканчиваются концом строки; `;` в грамматике языка нет.
- Блоки оформляются фигурными скобками.
- Комментарий начинается с `//` и продолжается до конца строки; блочных комментариев нет.
- Идентификаторы состоят из латинских букв, цифр и `_`; регистр имеет значение.
- Выражения вычисляются слева направо.
- Приоритет операторов определён спецификацией; сравнения `a < b < c` не сцепляются.
- `let` объявляет неизменяемую переменную, `var` — изменяемую.

Пример:

```dpl
fn total(values: []i64) i64 {
    var sum: i64 = 0
    for value in &values {
        sum += value
    }
    return sum
}

fn main() {
    let result = total([10, 20, 30])
    println("total=" + str(result))
}
```

Это пример формы кода, а не рекомендация по производительности: срез `[]T` и передача коллекций имеют собственные правила владения и копирования, описанные ниже.

### 4.3. Функции и типы

Функция объявляется через `fn`, параметры и результат имеют явные типы:

```dpl
fn distance_squared(x: i32, y: i32) i64 {
    return i64(x) * i64(x) + i64(y) * i64(y)
}
```

Тип результата можно опустить у функции без результата (`void` подразумевается), а публичные функции, которые могут завершиться ошибкой, должны указывать тип ошибки явно.

Структуры (`struct`) содержат поля с типами и, при необходимости, значениями по умолчанию. Перечисления (`enum`) поддерживают варианты без данных, с позиционными данными и с именованными полями.

```dpl
pub struct Point {
    x: i32
    y: i32
}

pub enum Shape {
    Empty
    Circle(Point, i32)
    Rect { min: Point, max: Point }
}
```

DPL пока не имеет методов `impl` у пользовательских типов: операции над структурой обычно оформляются отдельными функциями, принимающими значение или ссылку на него.

## 5. Система типов и значения

### 5.1. Встроенные типы

| Тип | Назначение |
|---|---|
| `i8`, `i16`, `i32`, `i64` | Знаковые целые фиксированной ширины |
| `u8`, `u16`, `u32`, `u64` | Беззнаковые целые фиксированной ширины |
| `int` | Псевдоним `i64` на целевых 64-битных платформах первой волны |
| `f32`, `f64` | IEEE 754 binary32 и binary64 |
| `bool` | `true` / `false` |
| `str` | Неизменяемая строка UTF-8 |
| `List[T]` | Владеющий динамический список |
| `Map[K, V]` | Встроенное отображение ключей в значения |
| `Pool[T]` | Пул значений в слотах |
| `Handle[T]` | Хэндл элемента пула: номер слота и поколение |
| `[]T` | Невладеющий срез, только для чтения |
| `?T` | Необязательное значение: `T` или `none` |
| `E!T` | Значение `T` или ошибка из перечисления `E` |
| `Atomic[T]`, `Mutex[T]`, `Channel[T]` | Типы для совместного доступа между потоками |
| `struct`, `enum` | Пользовательские составные типы |

Пользовательские обобщённые типы и обобщённые функции пока не реализованы. Обобщённые конструкции ограничены встроенными типами и контейнерами языка.

### 5.2. Необязательные значения

`?T` используется там, где значения может не быть. Проверка и извлечение делаются через `if let`, `match` или оператор `??`:

```dpl
fn find(values: []i32, wanted: i32) ?int {
    for i in 0..len(values) {
        if values[i] == wanted {
            return i
        }
    }
    return none
}

let index = find([4, 8, 15, 16], 15) ?? -1
```

`none` не является `null` и не означает произвольный нулевой указатель. Для C-дескрипторов отдельные nullable-типы описывают соответствие указателю или `NULL` на границе FFI.

### 5.3. Целые и числа с плавающей точкой

Целые имеют фиксированную ширину. Обычные `+`, `-`, `*` и унарный минус вызывают ловушку, если результат выходит за диапазон типа. Для явно заворачивающей арифметики существуют `+%`, `-%`, `*%` и `T.wrap(x)`. Для вычислений без ловушки доступны `checked_add`, `checked_sub`, `checked_mul`, `checked_div`, `checked_neg`, возвращающие `?T`.

Деление целых отбрасывает дробную часть к нулю. Деление на ноль — ловушка. Сдвиг на отрицательное число или на ширину типа и больше — ловушка. Преобразования чисел с потерей диапазона должны быть явными; неявными разрешены только преобразования без потерь.

`f32` и `f64` следуют IEEE 754. Деление плавающего числа на ноль даёт бесконечность или NaN, а не ловушку. `f32` округляется к `f32` на каждом шаге. В детерминированном классе действуют дополнительные ограничения на режим округления, слияние операций и наблюдаемые NaN.

### 5.4. Строки

`str` хранит UTF-8, а операции индексации и `len` работают с байтами. Срез строки не может разрезать многобайтовый символ посередине: такое обращение вызывает ловушку. Строки неизменяемы; новые значения получаются склейкой, срезом и методами.

Поддерживаемые методы включают `trim`, `find`, `starts_with`, `split`; `str(x)` создаёт текстовую запись чисел, `bool` и строк. Отдельного типа Unicode-символа нет: байтовые операции используют `u8`.

### 5.5. Контейнеры

**`List[T]`.** Динамический массив с операциями `push`, `insert`, `pop`, `remove`, `clear`, `reserve`, `sort`, `contains`. Индекс за пределами списка — ловушка. `clear()` сохраняет ёмкость, `reserve(n)` позволяет заранее подготовить буфер.

**`Map[K, V]`.** Встроенное отображение. Ключи — целые, `bool`, `str` или `Handle[T]`. Порядок обхода определён: ключи идут по возрастанию, а не в порядке случайного хэширования. Чтение отсутствующего ключа через `m[k]` — ловушка; `m.get(k)` возвращает `?V`.

**`Pool[T]` и `Handle[T]`.** Пул хранит значения в слотах. `add` возвращает хэндл, состоящий из номера слота и поколения. При удалении поколения меняются, поэтому старый хэндл не может случайно обратиться к новому объекту, занявшему тот же слот. Есть обход живых элементов, `get`, `contains`, `remove`, `clear`, `reserve`, `handles`.

Пул полезен для сущностей игрового мира, снарядов, агентов и других долгоживущих объектов, которым нужен стабильный идентификатор без прямого указателя.

### 5.6. Важная особенность: семантика значений

`List`, `Map`, `Pool` и `str` являются значениями. Присваивание, передача по значению и запись в поле копируют содержимое. Общих изменяемых данных через обычные значения нет. Память встроенных контейнеров и строк освобождается автоматически при выходе значения из области видимости или перезаписи.

Это упрощает модель владения, но может быть дорогим на больших структурах. Разработчик должен учитывать цену копирования и использовать ссылки/срезы в предусмотренных языком местах. В текущей модели ссылки и срезы не являются универсальными долгоживущими представлениями.

## 6. Управление потоком и обработка ошибок

### 6.1. Управление потоком

Основные конструкции:

- `if` / `else` и `if let`;
- `while`, `break`, `continue`;
- `for i in a..b` для диапазона;
- `for x in &collection` для чтения коллекции;
- `for x in &mut collection` для изменения элементов;
- `match` с проверкой полноты ветвей;
- `defer` и `errdefer` для отложенных действий.

`match` умеет разбирать варианты перечислений и вложенные варианты `?T` / `E!T`. Компилятор проверяет полноту: пропущенный вариант — ошибка, как и недостижимая ветвь после уже покрытых случаев.

### 6.2. Ошибки как значения

Исключений в языке нет. Функция, которая может завершиться ошибкой, возвращает `E!T`: либо значение `T`, либо вариант перечисления ошибок `E`.

```dpl
pub enum ParseError {
    Empty
    BadDigit
}

pub fn digit(s: str) ParseError!i32 {
    if len(s) == 0 {
        fail .Empty
    }
    if !is_digit(s[0]) {
        fail .BadDigit
    }
    return i32(s[0] - '0')
}

fn twice(s: str) ParseError!i32 {
    let value = try digit(s)
    return value * 2
}
```

`fail` возвращает ошибку, `try` передаёт ошибку вызывающей функции, а `match` позволяет обработать успех и отказ. Результат `E!T` нельзя молча отбросить: его нужно передать через `try`, разобрать через `match` или явно отбросить как `_ = call()`.

Для непубличных функций допускается `!T`, когда тип ошибки можно вывести из `fail` и `try`. Публичный интерфейс должен указывать конкретный тип ошибки явно.

### 6.3. Ловушки во время выполнения

Нарушение проверяемого условия — например, переполнение обычного целого, выход индекса за границу, устаревший хэндл или взаимная блокировка — вызывает ловушку. Runtime выводит исходный файл, строку и столбец, пишет сообщение в stderr и завершает процесс с кодом 101.

Ловушка не является обычной ошибкой `E!T`: после неё программа не продолжает работу, а `defer` при ловушке не исполняется. Обычный возврат ошибки через `fail`/`try` проходит штатный путь выхода функции, в котором отложенные действия выполняются.

## 7. Память и ресурсы

### 7.1. Ссылки без побега

Ссылки записываются как `&T` и `&mut T`:

- `&T` даёт доступ только для чтения;
- `&mut T` даёт изменяемый доступ;
- ссылки разрешены как параметры функций и как механизм обхода коллекции;
- ссылку нельзя сохранить в поле, список или вернуть из функции.

Срез `[]T` также является невладеющим представлением. Он создаётся при передаче аргумента и не может произвольно жить в структуре или возвращаться из функции.

Эта модель сознательно проще полного borrow checker с произвольными временами жизни. Она исключает висячие ссылки за счёт ограничения того, где ссылка может существовать.

### 7.2. Исключительный изменяемый доступ

Компилятор проверяет, что пересекающиеся места памяти не передаются одновременно как независимые ссылки, если одна из них изменяющая. Например, изменение структуры и чтение её поля в том же вызове, где поле может быть инвалидировано, запрещается. Для коллекций действует одно правило доступа, учитывающее вызовы, обход и `parallel for`.

В некоторых сценариях нужно явно сделать копию значения перед вызовом. Это плата за ограниченную и предсказуемую модель ссылок.

### 7.3. Линейные ресурсы

Ресурсы, которые требуется закрыть ровно один раз (файл, дескриптор, окно, объект Vulkan), оформляются структурами `@linear`. Компилятор проверяет, что ресурс поглощён ровно один раз на каждом пути выполнения: закрыт, передан другой функции или возвращён вызывающему.

```dpl
fn save(path: str, parts: &List[List[u8]]) os.IoError!void {
    var file = try os.create(path)
    errdefer _ = os.close(file)

    for part in &parts {
        try os.write(&mut file, part)
    }

    try os.close(file)
}
```

У пользовательских типов нет автоматических деструкторов. Закрытие явно показывается через обычный вызов, `defer` или `errdefer`. Это делает порядок освобождения видимым и проверяемым компилятором, но требует дисциплины при проектировании API.

### 7.4. Кадровая память

Текущий подход к повторному использованию памяти для кадровых данных — сохранение ёмкости контейнеров через `clear()` и `reserve()`, а также пулы. Явные аллокаторы и арены не входят в реализованную базовую поверхность языка на текущем срезе; их необходимость должна решаться по измерениям на больших данных.

## 8. Детерминизм

### 8.1. Четыре класса поведения

В проекте определены четыре класса:

| Класс | Значение | Примеры |
|---|---|---|
| **D** — детерминированный | Одинаковые явные входы дают одинаковый результат побитово в пределах гарантированной области | Целочисленная арифметика, определённые операции IEEE 754, упорядоченные контейнеры, проверенная симуляция |
| **I** — определяемый реализацией | Фиксировано конкретной версией компилятора и цели, задокументировано и не наблюдается из D | Раскладка обычных структур, размер стека |
| **P** — платформозависимый | Может различаться между целями | Платформенная `libm`, API ОС, некоторые SIMD-операции |
| **N** — недетерминированный | Зависит от времени, планирования или внешнего мира | Часы, ввод-вывод, энтропия ОС, планирование задач, мьютексы и каналы |

Класс D объявляется атрибутом `@det` у функции либо импортом `@det import module`. Компилятор проверяет граф вызовов: код D может вызывать только функции и операции, совместимые с классом D. Например, ввод-вывод через `os`, обычный вывод или вызов C из детерминированной функции запрещены.

### 8.2. Для чего это полезно

Такой режим важен для:

- повторного воспроизведения симуляции по начальному состоянию и входам;
- синхронизации результатов между x86-64 и arm64;
- детерминированных тестов и поиска регрессий;
- проверки игровых миров, экономики, поведения агентов и других систем по хэшу состояния;
- одинаковых результатов при разных числах потоков.

В детерминированном классе плавающая арифметика ограничена режимами корректного округления и отключением неконтролируемого слияния операций. Порядок обхода `Map` и `Pool` определён. Время и внешние данные должны поступать в симуляцию как явные входы.

### 8.3. Демонстрация на текущем проекте

В репозитории есть `examples/swarm` — многопоточная симуляция роя агентов. Она записывает зерно и входы каждого такта, затем выполняет повтор и сравнивает хэш состояния после каждого такта. Проверки заявляют одинаковый результат на разных числах потоков, в debug/release и при повторе на x86-64 и arm64.

Это сильная демонстрация архитектурной идеи, но не заменяет независимого тестирования прикладной системы и полного аудита детерминизма для v1.0.

## 9. Параллелизм и конкурентный доступ

### 9.1. `parallel for`

`parallel for` выполняет независимые итерации одновременно. Ограничения компилятора призваны сделать безопасное разбиение данных явным:

- запись во внешние данные допускается через элемент, однозначно привязанный к переменной цикла (например, `output[i]`);
- если тело изменяет внешнюю коллекцию, чтение ограничено правилами доступа к соответствующим элементам;
- `break`, `return`, `fail` и `try` внутри тела запрещены; `continue` завершает текущую итерацию;
- вызов C и операции `os` запрещены в теле и в вызываемых им функциях;
- вывод `print`/`println`/`eprintln` буферизуется и выдаётся в порядке номеров итераций.

Тело `parallel for` исполняется в пуле потоков при нативной сборке; эталонный интерпретатор исполняет итерации по очереди. Проверки сравнивают их наблюдаемое поведение.

### 9.2. Задачи и общие значения

Блок `tasks { ... }` создаёт область задач. `spawn f(args)` запускает функцию DPL в отдельном потоке; блок завершается после завершения всех запущенных задач. Аргументы по значению копируются, а `&` и `&mut` разрешены только для заранее существующих мест с ограничениями на параллельный доступ.

Общие значения создаются встроенными функциями:

- `atomic(value)` — `Atomic[T]` для целых и `bool`; операции `load`, `store`, `add`, `sub`, `swap`, `cas`; используется последовательная согласованность;
- `mutex(value)` — `Mutex[T]`; данные доступны внутри `lock mutex as value { ... }`;
- `channel(n)` — `Channel[T]` с буфером; методы `send`, `recv`, `try_recv`, `close`.

Попытки повторно захватить мьютекс тем же потоком, отправить в закрытый канал, закрыть его повторно или довести систему до состояния, в котором все потоки ждут, приводят к ловушке. `select` для каналов пока не реализован. Общие конкурентные объекты и сам порядок планирования задач не принадлежат классу D.

### 9.3. Ограничения модели

Это не универсальная замена всем моделям конкурентности C++/Rust/Go. У DPL пока нет `async`/`await`, `select`, произвольных замыканий и общего механизма callback-объектов. Вызов экспортированной функции DPL из C до дальнейшего этапа разрешён только из одного потока одновременно. Внешние C-дескрипторы можно передавать между задачами только при явной пометке `@send`.

## 10. Взаимодействие с C и C++

### 10.1. C ABI в обе стороны

DPL использует C ABI как границу интеграции. Функция C объявляется через `extern fn`, библиотека указывается атрибутом `@link`:

```dpl
@link("SDL3")
extern fn SDL_Init(flags: u32) bool

extern type SDL_Window
```

Непрозрачные C-типы объявляются как `extern type`. В языке они выступают дескрипторами, а не произвольными указателями с арифметикой. `?H` представляет nullable-дескриптор.

Функции DPL можно экспортировать для хоста на C/C++ через `@export`. Команда `dpl build --lib` создаёт статическую библиотеку и заголовок C, через которые существующий проект может вызвать код DPL. Предусмотрены типы указателей на функции для callback-интерфейсов C.

### 10.2. Представление структур C

Для структур C предусмотрены:

- `@c` — раскладка полей как у C;
- `@union` — C union;
- `[N]T` — массив фиксированной длины;
- `@count(n)` — связь длины среза со счётчиком в структуре;
- `@c("header.h")` — структура, описанная в существующем заголовке;
- заимствующие поля для строк, срезов и ссылок;
- `?&mut S` как ограниченная цепочка вывода, в том числе для паттерна `pNext` Vulkan;
- `@slot(N)` — обращение к C-функциям через таблицы указателей на функции, как у JNI.

Официальные привязки Vulkan, SDL3 и JNI генерируются из закреплённых входных файлов/заголовков, сохраняются в репозитории и проходят проверки раскладки структур и вызовов.

### 10.3. Граница гарантий

Объявление `extern fn` должно точно соответствовать реальной сигнатуре C. Несовпадение типа, соглашения или структуры C находится за пределами гарантий языка и может привести к неопределённому поведению на стороне C. Модель безопасного DPL не делает произвольную внешнюю библиотеку автоматически безопасной.

DPL не совместим с C++ ABI. Для интеграции с C++ нужен C-совместимый слой или статическая библиотека DPL, вызываемая через C ABI. Это типичный, но всё же дополнительный слой интеграции.

## 11. Стандартная библиотека

Стандартная библиотека намеренно небольшая. Часть базовых операций встроена в язык и runtime; отдельный модуль `os` предоставляет аргументы и файловый ввод-вывод.

Основной документированный API `os`:

- `os.args()` — аргументы программы;
- `os.read_file`, `os.read_bytes` — чтение файла целиком;
- `os.create`, `os.open` — открытие файла;
- `os.write`, `os.read`, `os.close` — потоковая запись/чтение и закрытие;
- `os.write_file`, `os.write_bytes` — запись целиком.

Ошибки файловых операций представлены `os.IoError`: `NotFound`, `PermissionDenied`, `InvalidUtf8`, `NoSpace`, `Other`. `os.File` является линейным ресурсом и должен быть закрыт ровно один раз.

Встроенная поверхность включает числовые проверки, преобразования, строковые методы, коллекции, вывод и конкурентные примитивы. Для GUI, графики, системных API, JNI и других внешних возможностей используется FFI и библиотеки C.

Следствие: у разработчика нет готовой стандартной библиотеки уровня .NET, Java, Rust crates или Boost. До решения о переходе необходимо проверить наличие привязок и поддерживаемость всех используемых зависимостей.

### 12.3. Чего пока нет

На текущем срезе ещё не представлены как готовые инструменты:

- команда `query` для адресного получения сведений о символах и контрактах;
- пакетный менеджер, манифест проекта и lockfile;

- полноценный профилировщик и стандартизованный IDE/workflow уровня зрелых языков.

Эти пункты находятся в дорожной карте, главным образом в v0.4 и следующих этапах. Форматирование уже существует, но у текущих примеров есть отмеченные ограничения форматировщика для длинных строк и некоторых крупных C-структур.

## 13. Тестирование и инженерные гарантии

Проект использует несколько уровней проверки:

- тесты лексера, парсера и дерева исходного кода;
- проверки типов, потока управления, ссылок и ошибок;
- негативные тесты, которые подтверждают, что запрещённый код действительно отвергается;
- тесты Core IR и эталонного интерпретатора;
- сравнение интерпретатора и нативного C-бэкенда по stdout, stderr, коду выхода и местам ловушек;
- тесты runtime и стандартной библиотеки;
- C ABI и проверки раскладки структур;
- межплатформенные прогоны и повторы при разных числах потоков;
- ASan/UBSan для тестовых сборок на поддерживаемых конфигурациях;
- TSan для проверки многопоточной программы;
- фаззинг парсера и автоматические проверки структуры исходников/генераторов.

Инженерное правило проекта — каждая обнаруженная ошибка компилятора или runtime становится регрессионным тестом. Нормативные пункты спецификации получают идентификаторы; тесты должны ссылаться на эти идентификаторы. Ожидаемые выводы хранятся рядом с тестами и сверяются побайтно.

Аудит v0.2 от 17 октября 2026 года зафиксировал 1 014 тестов в полном наборе на тот момент. Это историческое число для указанной вехи, а не подтверждённый общий счёт тестов текущего среза.

Важное ограничение процесса: проектная документация отдельно отмечает отсутствие внешнего GitHub Actions CI как риск. Основной полный прогон запускается через `tools/check/run.sh` в рабочем окружении, а итог записывается в PR. Для стороннего потребителя важно выяснить, каким образом будет устроен независимый CI и релизная проверка после выпуска SDK.

## 14. Измерения и примеры текущего состояния

### 14.1. Многопоточная симуляция `swarm`

В `examples/swarm` есть симуляция роя из 5 000 агентов на 100 тактов. Замер `--release`, медиана трёх запусков на четырёхъядерной машине от 31 октября 2026 года:

| Число потоков | Время | Результат |
|---:|---:|---|
| 1 | 8,46 с | Одинаковый хэш |
| 2 | 4,57 с | Одинаковый хэш |
| 4 | 2,41 с | Одинаковый хэш |

Это показывает масштабирование конкретной симуляции и совпадение результата при изменении числа потоков. Это не сравнение DPL с C++ и не доказательство того, что любая нагрузка ускорится аналогично.

### 14.2. Пулы сущностей

В исследовании коллекций приводится замер кадра со 100 000 сущностей: обход `Pool` — 3,04 мс, ручной пул — 5,26 мс, вариант C++ — 1,73 мс. Из него можно сделать только ограниченный вывод: встроенный пул обошёл конкретную ручную реализацию в этой задаче, но пока уступил C++-эталону. Нужны повторные замеры на представительных проектах и нескольких конфигурациях.

### 14.3. Графика и FFI

`examples/triangle` использует SDL3 и Vulkan. Он строит кадр 64×64, сравнивает пиксели с эталоном и показывает результат в окне. Для описанного эталона ожидается 1 152 пикселя треугольника и контрольная сумма FNV-1a. Есть Linux-сборка, Windows-сборка под Wine и Android APK через SDLActivity.

Это подтверждает, что DPL способен участвовать в реальной нативной графической цепочке через FFI. Но пример — намеренно ограниченный треугольник, а не полноценный движок, редактор, рендерер или production-игра.

### 14.4. Работа с ИИ

Одна из центральных целей DPL — уменьшить стоимость работы ИИ-агента над кодом. Однако собственные замеры проекта не показывают устойчивого выигрыша уже сейчас: после улучшения руководства, добавления `checked_*`, `Map` и приёмов расход токенов на изменение в одном из замеров v0.1 оставался примерно на 18,4% выше C++-варианта.

Это важный факт для оценки. DPL может быть удобен для ИИ благодаря компактному синтаксису, явным контрактам и точным ошибкам компилятора, но преимущество должно быть повторно доказано на нескольких реальных задачах и с несколькими моделями. Пока не следует считать экономию токенов установленным преимуществом языка.

## 15. Ограничения, компромиссы и риски

### 15.1. Ограничения языка

По текущей спецификации и руководству в DPL отсутствуют:

- пользовательские generic-функции и generic-типы;
- методы `impl` у пользовательских типов;
- замыкания и лямбды;
- кортежи;
- `if` и `match` как выражения;
- форматные строки;
- `++`, `--` и отдельная конструкция `loop`;
- изменяемые глобальные переменные;
- исключения и `null`;
- произвольные хранимые ссылки и срезы;
- произвольные указатели и арифметика указателей;
- `async`/`await` и `select` для каналов;
- полная стандартная библиотека общего назначения.

Некоторые отсутствующие конструкции можно выразить структурами, именованными функциями, `?T`, `E!T`, `Pool[T]`, FFI или явным управлением потоком. Но обходные формы не всегда столь же удобны и могут увеличивать объём кода.

### 15.2. Цена семантики значений

Копирование `List`, `Map`, `Pool` и `str` — осознанное упрощение модели памяти. Для небольших объектов оно удобно, но для больших состояний может стать затратным по времени и памяти. Пока проект не предоставит достаточный набор представительных бенчмарков, разработчик должен самостоятельно профилировать копирование, выделения памяти и горячие участки.

### 15.3. C-бэкенд

C11-бэкенд позволяет использовать существующие компиляторы и платформенные toolchain, но добавляет промежуточное звено. Возможные риски — качество отладки, время сборки C, особенности оптимизатора и ошибки генерации C. Проект предусматривает критерии, при которых может понадобиться второй бэкенд, но готовый альтернативный backend на текущем этапе не является частью описанной поставки.

### 15.4. Зависимость от экосистемы C

Нативная интеграция — преимущество DPL, но также граница его удобства. Если проект сильно зависит от специфичных C++-библиотек, сложных шаблонных API, обширных SDK или C++-объектных интерфейсов, для подключения может потребоваться собственная C-прослойка. Наличие ABI не означает, что любая C++-библиотека автоматически становится удобной для DPL.

### 15.5. Платформенный охват

Поддержка первой волны ориентирована на Linux x86-64, Windows x86-64 и Android arm64. Для других платформ, архитектур и системных API потребуется отдельная работа. До принятия решения нужно сверить матрицу платформ с реальными платформами продукта, а не исходить из того, что «нативная компиляция» означает поддержку всех систем.

### 15.6. Стабильность семантики

До появления первого production-проекта действует режим R&D: язык, форматы и интерфейсы могут изменяться. После перехода к production-режиму планируется поддержка редакций, машинная миграция и формальная политика совместимости. Эти обещания должны быть проверены до v1.0; на текущем этапе их нельзя трактовать как уже действующую гарантию для внешнего потребителя.

## 16. Текущая зрелость и план до v1.0

### 16.1. Что уже есть

### 16.3. Что означает v1.0

v1.0 по проектному Definition of Done — не просто версия компилятора, которая успешно собирается. Требуется выполнение всех групп критериев:

- завершённая и согласованная спецификация с тестами соответствия;
- production-качество компилятора и полная проверка трёх целевых платформ;
- реальные нативные приложения: CLI, большие данные, многопоточность, графика, FFI;
- ABI и межъязыковая интеграция;
- детерминированные повторы между платформами, потоками и профилями;
- регрессии, фаззинг, санитайзеры и отсутствие необъяснённых критических ошибок;
- представительные бенчмарки производительности, памяти и времени сборки;
- минимально необходимые IDE/LSP, отладка, тестовый инструментарий и профилирование;
- воспроизводимая сборка и процесс выпуска;
- доказанный эксперимент эволюции языка с машинными миграциями;
- полная техническая документация;
- первый достаточно крупный production-style consumer project, разрабатываемый продолжительное время.

Для производительности в DoD предложен ориентир: медианная производительность представительных нагрузок не хуже C++ более чем в 1,25 раза. Это пока критерий-предложение, который должен быть подтверждён или изменён после измерений.

## 17. Лицензирование и доступность

На дату этого обзора репозиторий DPL закрытый и проприетарный. В документах проекта указано, что сейчас действует временная редакция `LICENSE` «все права защищены», и внешнее распространение не ведётся. Перед первой передачей двоичной поставки внешнему получателю планируется подготовить лицензию SDK с юридической проверкой; до v1.0 также предусмотрено соглашение о конфиденциальности.

Практическое следствие: описание языка само по себе не даёт стороннему разработчику права использовать компилятор, runtime, стандартную библиотеку или привязки. До реальной оценки необходимо отдельно согласовать доступ к закреплённой сборке, SDK, документации и лицензионные условия.

Также в TODO проекта остаётся проверка обозначения `dpl` у патентного поверенного. Для коммерческого внедрения нужно отдельно проверить права на название и товарный знак.

## 18. Кому стоит рассматривать DPL после стабилизации

### Хороший кандидат

DPL стоит включить в сравнительное исследование, если проект:

- содержит детерминированное ядро симуляции или игровую логику;
- интенсивно работает с сущностями и пулами объектов;
- требует повторов, хэширования состояния и межплатформенной воспроизводимости;
- уже имеет значительную часть инфраструктуры на C/C++ и может подключать новый код через C ABI;
- использует одну из трёх целевых платформ первой волны;
- готов принять более строгую и ограниченную модель памяти ради проверяемости.

### Сомнительный кандидат

Нужна особенно тщательная проверка, если проект:

- зависит от обширной экосистемы C++ и сложных template API;
- активно использует произвольные указатели и пользовательские аллокаторы;
- требует большого числа generic-абстракций, замыканий или callback-пайплайнов;
- опирается на широкую стандартную библиотеку, сетевой стек, асинхронный I/O или зрелый GUI toolkit;
- требует платформ, не входящих в первую волну;
- критичен к времени сборки, а выбранный проект ещё не имеет инкрементального компилятора и пакетного workflow.

### Не рекомендуется

Не следует переносить production-код на текущий незавершённый срез DPL только потому, что примеры компилируются или отдельные тесты проходят. До v1.0 отсутствует полный набор обещанных гарантий, инструментов и проверок на крупном потребительском проекте.

## 19. Практический чек-лист оценки перед переходом

Когда будет доступна кандидатная или стабильная сборка, независимому разработчику стоит пройти следующий сценарий.

1. **Зафиксировать поставку.** Получить точную версию компилятора, runtime, stdlib, bindings, спецификацию, редакцию языка, SDK и lockfile. Проверить лицензию и правила обновления.
2. **Проверить рабочее место.** Установить компилятор, C toolchain и SDK целевых платформ. Собрать минимальную программу в debug и release.
3. **Собрать реальный вертикальный срез.** Реализовать один модуль данных, один алгоритм, один файловый или UI/FFI-интерфейс, тесты и нативную сборку.
4. **Проверить память.** Измерить копирование `List`/`Map`/`str`, выделения, пулы, пиковую память и стоимость кадровых операций.
5. **Проверить производительность.** Сравнить с текущим C++-эталоном на одинаковом железе, одинаковом алгоритме и одинаковых параметрах; учитывать время запуска, сборки, FFI и работу runtime.
6. **Проверить детерминизм.** Повторить симуляцию в debug/release, на Linux x86-64 и Android arm64/Windows x86-64, при нескольких значениях `DPL_THREADS`; сравнить побитовые хэши.
7. **Проверить интеграцию.** Подключить одну настоящую C-библиотеку проекта, проверить ABI, владение ресурсами, обратные вызовы и системную сборку.
8. **Проверить инструменты.** Оценить LSP, навигацию, диагностику, форматирование, отладчик, профилировщик, тесты и CI на реальном проекте, а не только в примерах.
9. **Проверить обновление языка.** Убедиться, что обещанный `fix` действительно мигрирует проект между редакциями и что совместимость не держится на ручном переписывании.
10. **Проверить операционные риски.** Уточнить сроки поддержки платформ, реагирование на уязвимости, выпуск исправлений компилятора/runtime, воспроизводимость SDK и возможность продолжать разработку при недоступности автора.

Результат оценки стоит оформлять сравнительной таблицей с C++: качество, производительность, использование памяти, скорость сборки, время разработки, число исправлений после компиляции, токены/стоимость ИИ, качество отладки и цена интеграции.

## 21. Итоговая оценка

DPL предлагает интересную комбинацию для системного и игрового программирования: компактный синтаксис, явную обработку ошибок, ограниченную модель ссылок, линейные ресурсы, generational handles, детерминированный класс кода, проверяемый параллелизм и интеграцию через C ABI.

Его наиболее отличительная идея — не отдельная конструкция языка, а попытка связать семантические гарантии с повторяемыми тестами и измерениями. Особенно перспективна комбинация класса D, контролируемого параллелизма и воспроизводимого состояния для игровых симуляций.

Но есть и существенная цена: язык ещё развивается, семантика и инструменты не стабилизированы, стандартная библиотека невелика, пользовательские generic-конструкции и ряд привычных абстракций отсутствуют, а копирование значений требует внимания к производительности. Важнейшие преимущества пока должны быть доказаны на крупном прикладном проекте.

**Рекомендация стороннему разработчику:** следить за достижением v1.0 и затем проводить ограниченный пилот на репрезентативной подсистеме. Рассматривать постепенное внедрение рядом с C/C++ через C ABI, а не одномоментный перенос большого продукта. Решение о переходе принимать только после проверки производительности, памяти, инструментов, лицензии, сопровождения и детерминизма на собственных нагрузках.
