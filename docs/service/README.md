# Онлайн-компилятор dpl

Описание устройства онлайн-компилятора — безопасного интерфейса к
компилятору для будущей страницы на dpsmpx.com. Решение — Р49
(`docs/direction/DECISIONS.md`); задача и ворота запуска —
`ROADMAP/ROADMAP.md`, «Онлайн-компилятор (Р49)». Контракт для сайта —
[`integration.md`](integration.md).

**Запуск выключен.** В поставляемом профиле `available: false`: сервис
отвечает «недоступен», а `/api/v1/info` говорит сайту не показывать
страницу. Включение — только отдельным решением автора по Р5, после
проверки имени у поверенного (Р39) и выполнения DoD сервиса (раздел 12).

## 1. Что делает и чего не делает

- **Только проверка.** Сервис принимает один модуль, проверяет его тем же
  ядром, что `dpl check`, и возвращает диагностику. Программу он не
  исполняет и не собирает: исполнение — отдельное решение со своим слоем
  изоляции и моделью угроз (Р49).
- **Одно ядро.** Своей логики компиляции у сервиса нет: worker зовёт
  `api::check` (`compiler/api/compile.h`), как CLI и фаззер. Пределы
  профиля (размер, строки, длина имени, число сообщений, размер ответа)
  проверяет слой контракта `compiler/api/contract.h` до и после
  компиляции; у самого `api::check` параметр ресурсов один — предел
  вложенности (Р49).
- **Граница ответственности** (Р49):

| кто | за что |
|---|---|
| dpl (этот репозиторий) | компилятор, контракт, версии, диагностика, детерминизм, worker и его песочница, временный шлюз, профиль пределов |
| dpsmpx/SocialMediaImage | страница, редактор, HTTP-клиент, показ диагностики |
| инфраструктура | точка входа с TLS, внешний rate limit, запуск шлюза под пользователем без прав, оркестрация, мониторинг |

## 3. Путь запроса

```
браузер ─TLS─▶ точка входа инфраструктуры (внешний rate limit)
          ─HTTP─▶ шлюз service/gateway.py
                    маршрут, available, rate limit, Content-Type, длина тела, очередь
                  ─stdin─▶ dpl worker (отдельный процесс на запрос)
                             rlimits → поток → seccomp → чтение входа
                             → api::compile_v1 → api::check
                  ◀stdout─ ответ контракта v1
          ◀────── ответ + meta.duration_ms
```

Шлюз не разбирает JSON запроса и не компилирует: тело уходит worker-у
как есть, а ответ worker-а шлюз только проверяет по форме и дополняет
временем.

## 4. Контракт и версии

Полностью — [`integration.md`](integration.md). Кратко:

- запрос `POST /api/v1/compile` — объект `language`, `mode`,
  `file_name`, `source`; ответ — `api`, `compiler{version, language}` и
  `result` или `error`, затем `meta`;
- три версии независимы: версия API (`v1`, в пути), версия компилятора
  (`kCompilerVersion`, `compiler/support/version.h`) и версия языка
  (`kLanguageVersion`; запрос называет её в `language`). Несовместимое
  изменение контракта — новый путь `/api/v2`;
- **детерминизм:** всё, кроме `meta`, зависит только от тела запроса,
  версий и профиля. Тот же вход — те же байты: это проверяют проходы
  `worker` (каждый запрос дважды), `dpfuzz contract` и тест
  `service/deterministic`.

## 5. Worker

`dpl worker --request-bytes=N … --stack-bytes=N` — один запрос на
процесс. Пределы — только аргументами из профиля; значений по умолчанию
нет, пропущенный предел — отказ с кодом 2. Пользовательских данных в
аргументах нет: тело запроса — stdin, ответ — stdout.

Порядок до чтения входа:

1. закрыть дескрипторы от 3 и выше (`close_range`); `SIGPIPE` —
   игнорировать; одна арена `malloc` (`M_ARENA_MAX`);
2. готовый ответ на нехватку памяти и обработчик `new`;
3. rlimits: `RLIMIT_AS` = `memory_bytes`, `RLIMIT_CPU` = `cpu_seconds`
   (жёсткий — на секунду больше), `RLIMIT_NOFILE` = 3, `RLIMIT_CORE` = 0,
   `RLIMIT_FSIZE` = предел ответа + 64 КБ (запись, если stdout — файл);
4. поток компилятора со стеком `stack_bytes`;
5. в нём — песочница (раздел 6); не встала — код 3, вход не читается;
6. чтение stdin: не больше `request_bytes` + 1 байт.

| код выхода | что |
|---|---|
| 0 | ответ записан (результат или ошибка запроса) |
| 2 | неверный вызов: аргументы, сборка с санитайзерами |
| 3 | внутренняя ошибка, в том числе песочница не встала |
| 4 | не хватило памяти; записан ответ `limit_exceeded` (`memory_bytes`) |

`dpl worker --describe` печатает версии: шлюз спрашивает их при
запуске.

**Сборка.** Worker — только сборка Release без санитайзеров
(`build/release/dpl`): ASan делает системные вызовы вне списка
песочницы и резервирует адресов больше любого `RLIMIT_AS`. В сборке с
санитайзерами `dpl worker` отказывает с кодом 2. Под ASan контракт
проверяет фаззер `dpfuzz contract` в том же процессе, без песочницы.

## 6. Изоляция

Песочница — `lock_down` (`compiler/driver/sandbox.h`), необратимо, на все
потоки процесса (`SECCOMP_FILTER_FLAG_TSYNC`):

- `PR_SET_NO_NEW_PRIVS` и `PR_SET_DUMPABLE = 0`;
- фильтр seccomp-BPF: чужая архитектура и вызовы x32 — смерть;
  разрешены `read`, `write`, `brk`, `munmap`, `mremap`, `madvise`,
  `futex`, `rt_sigprocmask`, `rt_sigreturn`, `exit`, `exit_group`;
  `mmap` и `mprotect` — только без `PROT_EXEC`. Любой другой вызов —
  `SECCOMP_RET_KILL_PROCESS` (SIGSYS). Список снят strace на worker-е
  и пробнике: лишнего в нём нет;
- значит, после запирания нет сети, файлов, новых процессов и потоков,
  `exec`, `ptrace`, сигналов другим процессам и исполняемой памяти.

Снаружи worker-а шлюз даёт: отдельную группу процессов (`setsid`),
пустое окружение, временный рабочий каталог 0700 (удаляется после
запроса), только дескрипторы 0–2, таймаут по часам с `SIGKILL` всей
группы, предел объёма stdout и stderr.

Сетевые пространства имён, cgroup и контейнеры — слой инфраструктуры;
ядру и шлюзу они не нужны (Р49).

## 7. Шлюз

Временный, на Python 3 stdlib без сторонних пакетов (Р49):

```sh
python3 -I service/gateway.py --config service/config/online-v1.json \
    --worker build/release/dpl --listen 127.0.0.1:8080 \
    --metrics-listen 127.0.0.1:9100
```

- **Профиль** загружается строго: лишний или пропущенный ключ, ноль,
  неверный тип, повторный ключ — отказ запуска с кодом 2.
- **Маршруты:** `POST` и `OPTIONS /api/v1/compile`, `GET /api/v1/info`;
  `GET /metrics` — только на отдельном адресе метрик (держать закрытым).
- **Порядок проверок `compile`:** `available` → rate limit →
  `Content-Type: application/json` (кодировка — только UTF-8) → длина
  тела (`request_bytes`) → тело → очередь → worker.
- **HTTP:** только тело по `Content-Length`; `Transfer-Encoding`, повтор
  `Content-Length` и других значимых заголовков, неверная строка запроса
  или заголовок — 400; заголовков больше `http.headers` или длиннее
  `http.header_bytes` — 431; заголовки и тело — за `read_timeout_ms`,
  иначе 408. Соединение одно на запрос; после ответа — мягкое
  закрытие: конец записи, остаток входа дочитывается и отбрасывается
  (не дольше секунды), чтобы ответ 413 дошёл до клиента.
- **Соединений** не больше `http.connections`; лишнее — сразу 503.
- **Rate limit:** token bucket на клиента (`per_ip_per_minute`,
  `per_ip_burst`) и общий (`global_*`); клиент IPv6 — сеть
  `/ipv6_prefix`. `X-Forwarded-For` учитывается, только если соединение
  пришло от `trusted_proxies`; клиент — самый правый недоверенный адрес
  цепочки. Таблица клиентов — не больше `table_size`, вытесняется давно
  не виденный. Отказ — 429 с `Retry-After`.
- **Очередь:** одновременно не больше `queue.concurrency` worker-ов; ждут
  не больше `queue.length` запросов, FIFO; переполнение — 503
  `queue_full`, ожидание дольше `wait_ms` — 503 `queue_timeout`.
- **Итог worker-а:** код 0 или 4 и ответ правильной формы — ответ
  клиенту; таймаут по часам или смерть от `SIGXCPU`/`SIGKILL` —
  `compile_timeout`; переполнение вывода, падение, `SIGSYS`, мусор или
  чужой код ошибки — `compiler_internal_error` (`SIGSYS` — ещё и
  событие `sandbox_violation` в журнале).
- **Заголовки:** `Cache-Control: no-store`, `X-Content-Type-Options:
  nosniff`, `Content-Security-Policy: default-src 'none';
  frame-ancestors 'none'`, `Referrer-Policy: no-referrer`, `Vary:
  Origin`; CORS — только `cors.origins` (`https://dpsmpx.com`), без
  учётных данных.
- **Журнал** — строка JSON на запрос в stderr: время, хэш клиента,
  маршрут, статус, код, размеры, время worker-а и его код выхода.
- **Метрики** — текстовый формат Prometheus: запросы по кодам, запуски
  worker-а по итогам, занятость очереди, соединения.

## 8. Профиль online-v1

`service/config/online-v1.json` — единственное место всех пределов.
Числа выбраны по замерам (раздел 11); замер на сервере может их
сдвинуть — правкой профиля, без правки кода.

| ключ | значение | почему |
|---|---|---|
| `available` | `false` | запуск — решением автора по Р5 (Р49) |
| `limits.source_bytes` | 65 536 | страница-песочница, один модуль |
| `limits.lines` | 2 000 | ограничивает и худшие цепочки объявлений: самая дорогая — 0,5 с |
| `limits.request_bytes` | 409 600 | худшее экранирование JSON — 6 байт на байт исходника, плюс поля |
| `limits.identifier_bytes` | 128 | ограничивает длину сообщений, где есть имена |
| `limits.nesting` | 256 | человеку хватает; стек на ней — 3 МБ |
| `limits.diagnostics` | 100 | больше на странице не читают |
| `limits.output_bytes` | 262 144 | 100 сообщений — около 30 КБ, запас |
| `worker.memory_bytes` | 268 435 456 | `RLIMIT_AS`: нужно 26 МБ, запас около 10×; «бомба памяти» упирается в предел за 0,35 с CPU |
| `worker.cpu_seconds` | 2 | худший законный вход — 0,5–0,6 с CPU, запас 3× |
| `worker.stack_bytes` | 16 777 216 | наименьший рабочий стек — 3 МБ, запас 5× |
| `run.timeout_ms` | 4 000 | вдвое больше предела CPU: ожидание ввода-вывода и нагрузка |
| `run.stdout_bytes` | 524 288 | больше `output_bytes`: превышение — ошибка worker-а |
| `run.stderr_bytes` | 4 096 | хватает на сообщение о внутренней ошибке; остальное отбрасывается |
| `queue.concurrency` | 2 | ~200 запросов/с у предела на 4 CPU, половина машины остаётся прочему |
| `queue.length`, `queue.wait_ms` | 16, 3 000 | дольше трёх секунд пользователь ждать не будет |
| `rate_limit.per_ip_*` | 30 в минуту, запас 10 | проверка по кнопке; шквал правок обрезается |
| `rate_limit.global_*` | 600 в минуту, запас 60 | 10 запросов/с: даже худшие входы не занимают больше `concurrency` |
| `rate_limit.ipv6_prefix`, `table_size` | 64, 10 000 | абонент IPv6 — сеть /64; таблица — меньше мегабайта |
| `http.*` | 8 КБ заголовков, 64 заголовка, 5 с на чтение, 256 соединений | обычный браузер укладывается с большим запасом |
| `cors.origins` | `https://dpsmpx.com` | только своя страница (Р49) |
| `trusted_proxies` | пусто | задаёт развёртывание: адрес точки входа |

## 9. Модель угроз

| угроза | мера | проверка |
|---|---|---|
| исходник, роняющий компилятор переполнением стека | предел вложенности E0002 (`nesting`), стек потока, предел строк | `limits`, `worker/limit_nesting*`, `service/limit_nesting` |
| исходник, съедающий память (константы без бюджета, `TODO.md`) | `RLIMIT_AS`, готовый ответ `limit_exceeded` | `worker/limit_memory`, `service/memory_bomb` |
| исходник, вешающий компилятор (E0423 на «ромбе», `TODO.md`) | `RLIMIT_CPU`, таймаут по часам, `SIGKILL` группы | `service/cpu_bomb`, `service/worker_hang` |
| уязвимость компилятора, исполнение кода | seccomp: нет сети, файлов, процессов, `exec`, исполняемой памяти | `sandbox` (13 действий), `service/worker_env` |
| огромный вход | `request_bytes` до чтения тела (413), `source_bytes`, `lines`, `identifier_bytes` (422) | `service/payload_too_large`, `worker/limit_*` |
| огромный ответ | `diagnostics`, `output_bytes` в worker-е; `stdout_bytes` в шлюзе | `worker/truncated_*`, `service/worker_flood` |
| неверный JSON, повторные ключи, неверный UTF-8, суррогаты | строгий разбор | `worker/*`, `dpfuzz contract` |
| request smuggling, двусмысленный HTTP | без chunked, без keep-alive, повтор заголовков — 400 | `service/http_malformed` |
| медленный клиент (slowloris), много соединений | `read_timeout_ms`, `connections` | `service/slow_*`, `service/connection_limit` |
| поток запросов | rate limit на клиента, IPv6 по /64, общий; внешний — у инфраструктуры | `service/rate_*` |
| перегрузка | очередь с пределом и таймаутом | `service/queue_*`, `service/concurrency` |
| подмена адреса через `X-Forwarded-For` | учитывается только от `trusted_proxies` | `service/forwarded_untrusted`, `service/rate_limit_ipv6` |
| утечка исходника и адресов | журнал без тела, адрес — хэш с солью процесса; каталог worker-а удаляется | `service/log_private`, `service/worker_env` |
| запрос со стороннего сайта | CORS только для `cors.origins` | `service/cors` |
| зависший или неверный worker | таймаут, предел вывода, проверка формы ответа | `service/worker_*` |

**Не проверено в сессии (UNKNOWN):** поведение за реальной точкой входа
с TLS и внешним rate limit; запуск шлюза под отдельным пользователем без
прав; cgroup-пределы инфраструктуры; seccomp на ядре и архитектуре
сервера, если они отличаются от Linux x86-64 сессии (arm64 собран в
фильтре, но не запускался). Это — пункты DoD (раздел 12).

## 10. Приватность

- Исходник живёт только в памяти шлюза и worker-а на время запроса; на
  диск не пишется, в журнал и метрики не попадает.
- Адрес клиента в журнале — первые 16 знаков SHA-256 от соли процесса и
  адреса; соль новая при каждом запуске и нигде не хранится. Таблица rate
  limit держит адреса в памяти, не дольше вытеснения.
- Метрики — только счётчики, без адресов и содержимого.

## 11. Замеры и числа профиля

`python3 bench/service/measure.py --save DIR` (нужна сборка
`build/release`). Итог 7 октября 2026 на машине сессии (4 CPU, Linux
x86-64) — `bench/results/service-2026-10-07/summary.md`:

- **процесс на запрос дёшев:** пустой запуск worker-а — 2 мс, малая
  программа — 3 мс, программа у предела строк (1981 строка) — 8 мс, с
  46 ошибками — столько же; пиковая память — 15 МБ везде;
- **худшие законные входы у предела строк:** цепочка 2000 структур —
  0,5 с CPU (проверка E0423 около n³, `TODO.md`), цепочка констант —
  14 мс, цепочка функций с `try` — 21 мс; наибольшая принятая
  вложенность каждой конструкции прохода `limits` — до 5 мс;
- **наименьшие рабочие пределы:** стек — 3 МБ, `RLIMIT_AS` — 26 МБ при
  стеке 16 МБ;
- **шлюз по HTTP**, программа у предела: 98, 209 и 306 запросов/с при
  `concurrency` 1, 2 и 4; p95 — 95, 42 и 28 мс. Малая программа — до
  533 запросов/с.

Холодный и тёплый запуск не различаются: каждый запрос — новый процесс,
состояния между запросами нет; различие — только кэш страниц ОС,
двоичный файл в нём после первого запуска.

- [ ] прогон тестов `service` против развёрнутого сервиса и проверка

- [ ] решение автора по Р5.

## 13. Развёртывание (для инфраструктуры)

- Собрать Release: `cmake -S compiler -B build/release -G Ninja
  -DCMAKE_BUILD_TYPE=Release && cmake --build build/release`.
- Запускать шлюз под отдельным пользователем без прав, `python3 -I`,
  слушать только `127.0.0.1` за точкой входа с TLS; адрес метрик — не
  наружу.
- Точка входа передаёт `X-Forwarded-For`; её адрес — в
  `trusted_proxies`.
- Остановка — `SIGTERM`.
- Профиль меняется только правкой `service/config/online-v1.json` в
  репозитории; `available` — только решением автора.

## 14. Шлюз на dpl

Временный шлюз заменяется шлюзом на dpl, когда язык сможет: FFI
(v0.2), потоки (v0.3), ввод-вывод в библиотеке (Р49). Приёмка замены —
тот же проход `service`: тесты — чёрный ящик по HTTP и не зависят от
языка шлюза.
