# Архитектурный аудит плана: 3 октября 2026

Срез на дату: проверка формальной постановки проекта (`docs/direction/`,
`docs/design/`, `docs/policy/`, `ROADMAP/`) по вопросам автора до начала
реализации. Итог каждой проверки: **годно**, **годно с правкой** (правка
внесена — раздел 9) или **риск** (записан в `docs/direction/RISKS.md`).

## 1. Не стал ли язык чрезмерно сложным

Состав ядра v1.0: типы (целые, плавающая точка, `bool`, строки, срезы,
массивы, векторы и матрицы, «может не быть», «значение или ошибка»,
структуры, суммы типов, ограниченные обобщённые типы), модули, атрибуты,
контракты, блоки тестов, `extern`; поверх — три статических анализа
памяти (ссылки без побега, исключительность, линейные ресурсы) и
проверка класса поведения D.

- По объёму возможностей — уровень Zig или Odin; сложнее их на три
  анализа и проверку класса D.
- Все анализы — внутри функции, по сигнатурам: без вывода времён жизни
  между функциями и без вычислений над типами (Р8). Это держит их
  сложность средней.
- Самое рискованное сочетание — линейные ресурсы с обобщёнными типами,
  суммами типов и путями ошибок (`errdefer`). Поэтому в плане оно идёт в
  v0.3, после программ v0.1–v0.2 (О4, О5).
- Встроенные векторы и матрицы — нагрузка на компилятор, но без
  пользовательской перегрузки операторов (Р7) иначе их не сделать;
  набор держится минимальным.

**Итог: годно с правкой** — правило входа новой возможности в язык
(правка 5).

## 2. Не повторяет ли язык существующие без нужды

Ни одна отдельная возможность не нова: явные аллокаторы и `defer` — Zig,
Odin; ошибки-значения — Zig, Rust; ссылки второго сорта — Hylo;
исключительность — Swift; хэндлы — практика движков и Vale; редакции —
Rust; классы поведения — продолжение практики детерминированной
симуляции. Отличие — в сочетании и приоритетах: детерминизм,
проверяемый компилятором; механизм эволюции с первого дня; инструменты
для агентов; безопасность памяти без проверки заимствований.

Почему не взять готовый язык:

| язык | почему нет |
|---|---|
| Zig | нет 1.0, частые ломающие изменения — противоречит Р0 и Р26; нет защиты от алиасинга и гонок; в ReleaseFast проверки отключены |
| Odin | нет гарантий безопасности; неявный контекстный аллокатор |
| Rust | цена проверки заимствований для быстро меняющейся игровой логики; время сборки |
| Swift | ARC; слабая поддержка Android и Windows как основных целей |
| C++ | неопределённое поведение, время сборки — исходная причина проекта |

Главная альтернатива — не готовый язык, а план Б («свой C++»): он дешевле
и сохраняет большую часть пользы. Поэтому сравнение с ним — обязательные
ворота (К-3).

**Итог: риск** (Р-3), закрыт воротами К-2 и К-3; в план Б добавлена
запись о рассмотренных готовых языках (правка 7).

## 3. Не несоразмерна ли сложность компилятора выгоде

| компонент | сложность | выгода | вывод |
|---|---|---|---|
| фронтенд (лексер, парсер, дерево без потерь) | средняя | нужен `fmt` и `fix` | годно |
| три анализа памяти + класс D | средняя | закрывают классы ошибок | годно поэтапно |
| Core IR + верификатор | низкая–средняя | граница бэкендов, эволюция | годно |
| эталонный интерпретатор (только тесты) | средняя | оракул различающих тестов и детерминизма | годно: вторая реализация семантики — это и есть проверка |
| C-бэкенд | низкая–средняя | все цели сразу | годно |
| `fmt`, `query` | средняя | ИИ и люди | годно |
| движок `fix` и редакции | высокая | без него нет эволюции (Р0, DoD J) | необходимо |
| language server и инкрементальная сборка | высокая | DoD H, скорость цикла | необходимо; риск переделки фронтенда |

Риск переделки: если фронтенд в v0.1 построить как простую цепочку
проходов, language server и инкрементальность в v0.4 потребуют
перестройки. Нужна заранее выбранная архитектура фронтенда.

Оценка объёма v1.0 (грубо): 80–150 тыс. строк вместе с тестами;
бюджет ядра v0.1 — около 25 тыс. строк компилятора без тестов (Р-4).

**Итог: годно с правкой** — новый открытый вопрос об архитектуре
фронтенда (правка 1).

## 4. Не противоречит ли план цели детерминизма

Проверено по `docs/policy/DETERMINISM.md`, найдены три дыры:

1. **Состояние управления плавающей точкой.** Внешняя библиотека
   (драйвер, звук) может включить на потоке сброс денормалов или сменить
   округление; код класса D молча даст другой результат. Нужна проверка
   и восстановление состояния runtime на входе в класс D.
2. **Параллельная свёртка с плавающей точкой** зависит от разбиения:
   если размер частей зависит от числа потоков, сумма различается при
   разном числе потоков. Нужны фиксированное разбиение и фиксированное
   дерево объединения.
3. **Сортировка:** неустойчивая сортировка с равными ключами даёт
   порядок, зависящий от реализации. Алгоритм стандартной сортировки в
   классе D должен быть указан и устойчив.

Остальное согласовано: без FMA и fast-math, флаг `-ffp-contract=off`,
оптимизатор не переассоциирует, свои трансцендентные функции,
упорядоченные таблицы, нет часов и ввода-вывода в D.

**Итог: годно с правкой** (правка 2).

## 5. Не мешает ли план native-производительности

| источник цены | оценка | мера |
|---|---|---|
| проверки границ | у Google — 0,30% в среднем; в узких циклах больше | удаление доказанно лишних проверок; замер с v0.1 |
| проверки переполнения | дороже проверок границ в арифметике | явные операции заворачивания в горячих местах; замер |
| поколение хэндла | одно сравнение | — |
| упорядоченная хэш-таблица | память и скорость удаления | быстрая неупорядоченная — вне D (О12) |
| запрет FMA и fast-math в D | на физике и arm64 — заметно | только в D; рендер и прочее не затронуты (К-6) |
| исключительный доступ | выигрыш: можно выдавать `restrict` в сгенерированном C там, где анализ это гарантирует | возможность для v0.3 |

Статическая линковка runtime, отсутствие сборщика мусора и скрытых
выделений — в пользу производительности.

**Итог: годно**, с обязательной мерой «цена гарантий» в замерах (уже в
`docs/policy/BENCHMARKS.md`) и критерием К-6.

## 6. Не создаёт ли план проблем долгосрочной совместимости

- Стабильная поверхность S0 немаленькая: язык, API библиотеки, C ABI,
  форматы сериализации, манифест и lockfile, схема диагностики. Каждая
  её часть проверяется автоматически (`docs/policy/COMPATIBILITY.md`,
  раздел 5) — иначе обещание было бы пустым.
- Встроенные векторы и матрицы — часть языка (S0), их труднее менять,
  чем библиотеку: набор минимален.
- Поддержка всех редакций с v1.0 копится; снятие редакции разрешено
  решением с путём миграции (Г2).
- Core IR и сводки — S1, наружу не поставляются: внутренности можно
  менять.
- Слабое место — сила `fix`: без него эволюция не работает; проверка —
  эксперимент J до v1.0.

**Итог: годно.**

## 7. Не превращается ли проект в бесконечный R&D

- Definition of Done велик: двенадцать разделов, пять программ, проект
  на 30 тыс. строк, эксперимент эволюции, language server. При 1/6
  ресурса это вероятно год–два даже при темпе VoxelRPG.
- Защиты есть: версии с воротами, критерии К-1…К-3, аудит после каждой
  версии, план Б.
- Не хватало измерения: фактическую цену версии не с чем сравнить.

**Итог: годно с правкой** — после каждой версии аудит записывает
фактическую цену в шагах и прогноз до v1.0 (правка 4).

## 8. Способны ли решения ускорить production-разработку

Механизмы ускорения: целые классы ошибок закрыты статически; детерминизм
по построению (меньше ошибок рассинхронизации и повтора); быстрый `check`
по сводкам модулей; точная машиночитаемая диагностика для цикла ИИ;
дешёвый рефакторинг через `fix`.

Против: у нового языка нет экосистемы; ИИ знает его хуже, чем C++;
инструменты молоды; период двух языков дорог.

Доказательств пока нет. План ставит измерения раньше, чем копится
дорогая работа: ворота v0.0 и v0.1 (ИИ), К-3 против плана Б на v0.3,
эксперимент J, исследование главной метрики после v1.0.

**Итог: риск** (Р-2, Р-3) — открыт до замеров; план умеет остановиться.
