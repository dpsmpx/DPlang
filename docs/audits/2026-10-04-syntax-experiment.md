# Опыт с синтаксисом v0.0: 4 октября 2026

Срез на дату: шаг 0.5 `ROADMAP/IMPLEMENTATION.md`. Модель решает
эталонный набор на C++ и на трёх вариантах записи DPlang (A, B, C —
`docs/research/syntax/README.md`), зная DPlang только по краткой
спецификации. Данные прогона — `bench/results/r1/` (внутренний материал,
Р5): журналы попыток, снимки кода, задания, сводка `summary.md`.

## 1. Что мерили

| | |

## 3. Что это значит

1. **Правильность — наравне с C++ на всех трёх вариантах.** Модель,
   впервые видя язык по спецификации в ~13,5 тыс. символов, решила весь
   набор с первой попытки, как и на C++. Критерий остановки К-2 не
   сработал.
2. **Набор не различает варианты по правильности** — эффект потолка: все
   ячейки приняты сразу, и циклов исправления нет ни у одного языка.
   Различие между вариантами в этом прогоне — только в объёме.
3. **Код на DPlang короче C++ на 14–23%,** и запись даёт заметную долю:
   B и C короче A на 4,5–7% на одних и тех же программах и на 9–10% в
   решениях модели. Главное, что убирает лишнее против A, — `;`, `->`,
   тип ошибки в сигнатуре, полное имя варианта (`E.V`).
4. **B и C по объёму практически равны.** C экономит на `:` в объявлениях
   и на пометках аргументов, но в решениях модели выигрыш C над B (1,3%)
   меньше разброса между задачами.
5. **Спецификация дорога на холодном старте.** Пока модель не знает язык,
   каждая новая сессия читает спецификацию: в этом опыте она перевешивает
   экономию в решении (+16–18% к расходу сессии против C++). Экономия
   токенов (уровень 2, Р6) достигается, только когда цена спецификации
   делится на много изменений в сессии: кэш запроса, сжатая
   спецификация, знание языка из `query` и `explain` вместо полного
   текста. Это общая цена нового языка, а не одного варианта: у A, B и
   C она одинакова.

## 4. Ограничения

- **Символы, а не токены.** Точный счёт (Р35) ждёт ключа; данные
  сохранены так, что счёт делается без нового прогона:
  `bench/experiment.py restore r1`, затем `tokens r1` и `report r1 --save`.
  Отношения в символах могут сдвинуться при счёте в токенах.
- **Один прогон.** Разброс модели не оценён; второй прогон (`r2`) нужен,
  если разница B и C будет решающей.
- **Потолок набора** (п. 2): для ворот v0.1 набору нужны задачи, на
  которых модель ошибается хотя бы на C++, — длиннее, с несколькими
  шагами изменения.
- **Прототип вместо компилятора.** Переводчик не проверяет типы: ошибки
  типов, которые пропустил бы C++, прототип тоже пропустит. Здесь это
  ничего не исказило — все решения приняты, — но для DPlang возможна
  мягкость проверки.
- **Изоляция песочницы — правилом.** По журналам (4–6 действий на
  ячейку, одна проверка) нарушений не видно, но система их не исключает.
- **Отклонение от Р35:** при запуске t08–t09 одновременно работали
  четыре субагента вместо 2–3 — недолго, на итоги ячеек это не влияет
  (каждая работала в своей песочнице).

## 5. Ворота v0.0 и рекомендация по О1

| условие ворот | итог |
|---|---|
| К-2 не сработал | да: правильность DPlang на всех вариантах равна C++ |
| вариант выбран и записан решением | ждёт решения автора по О1 |

**Рекомендация: вариант B.**

- **Правильность** у всех трёх вариантов одна, поэтому выбор решают
  следующие уровни Р6.
- **Против A.** A длиннее B на 5% по записи и на 10% в решениях модели
  и ничего не даёт взамен.
- **Против C.** C короче B на 1–3%, но убирает две вещи, видные в коде:
  пометку изменения у аргумента (`&mut w`) и неизменяемые переменные
  (`let`). Это проверяемость и контролируемость, уровень 1 Р6, а они
  важнее краткости.
- **Риск рекомендации.** Точные токены могут сдвинуть разницу B и C.
  Если по точному счёту C окажется дешевле B заметно, то есть больше
  разброса двух прогонов, вопрос пересматривается.
