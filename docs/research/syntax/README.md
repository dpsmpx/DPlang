# Варианты синтаксиса dpl для опыта v0.0

Материал шагов 0.3–0.4 `ROADMAP/IMPLEMENTATION.md`: три записи одного и
того же подмножества языка. Опыт (шаг 0.5) меряет, на какой из них модель
пишет правильнее и дешевле в токенах. Это материал, а не решение (Р24);
решение — Р40, вариант B (`docs/direction/DECISIONS.md`, бывший О1),
итоги опыта — `docs/audits/2026-10-04-syntax-experiment.md`.

## Варианты

Семантика у вариантов одна — различается только запись в спорных местах.

| спорное место | A (как Rust и Zig) | B (как иллюстрация исследования) | C (как Go и Odin) |
|---|---|---|---|
| конец инструкции | `;` | конец строки | конец строки |
| тип результата | `fn f(x: i32) -> i32` | `fn f(x: i32) i32` | `fn f(x i32) i32` |
| имя и тип | `x: i32` | `x: i32` | `x i32` |
| режим параметра | `&T`, `&mut T`; та же пометка у аргумента: `f(&mut w)` | как A | `mut T`; у аргумента пометки нет |
| ошибка в сигнатуре | `E!T` — с типом ошибки | `!T` | `!T` |
| вариант перечисления | всегда `E.V` | `.V`, если тип ясен | `.V`, если тип ясен |
| объявление переменной | `let x = e`, `var x = e` | как A | `x := e`, `var x T = e` |
| `if` со значением из `?T` | `if let v = opt` | как A | `if v := opt` |
| атрибут | `#[det]` | `@det` | `@det` |

Общее у всех: фигурные скобки, ключевые слова `fn let var if for match
return`, приоритет операторов (`<<` и `&` — уровня `*`, как в Go),
`try`, `fail`, `?T`, `List[T]`, `[]T`.

## Где что лежит

| что | где |
|---|---|
| краткие спецификации (что получает модель) | `spec_A.md`, `spec_B.md`, `spec_C.md` — сгенерированы, вручную не править |
| шаблон спецификаций и генератор | `bench/syntax/spec_template.md`, `bench/syntax/mkspec.py` |
| образцовые программы (приложение спецификаций) | `bench/syntax/samples/` |
| переводчик вариантов в C++ (не компилятор) и его опора | `bench/syntax/cm.py`, `bench/syntax/cm_rt.hpp` |
| решения набора, драйверы, заготовки | `bench/tasks/*/cm/` (`bench/tasks/README.md`) |
| проверка всего этого | `bench/syntax/run_variants.py` — шаг «варианты» в `tools/check/run.sh` |

Исходники решений и образцов пишутся в варианте A; записи B и C
печатаются из них переводчиком. Поэтому смысл решений во всех вариантах
один и тот же.

## Что получает модель в опыте

Для каждой задачи и варианта:

1. `task.md` задачи;
2. спецификацию варианта (`spec_X.md`, вместе с образцами);
3. начальный код в записи варианта:
   - заготовку `cm/stub.cm`;
   - для `t12` — `cm/buggy.cm`;
   - для `t13` — модули `cm/before/`.

Драйвер и `expected.txt` модель не видит. Её решение переводится,
собирается с драйвером `cm/driver.cpp` и сравнивается с `expected.txt`;
сборка задания, проверка, журнал попыток и счёт токенов — обвязка шага
0.2, `bench/experiment.py` (`bench/README.md`).

Размер спецификаций — около 13,5 тыс. символов каждая без образцов.
Точный счёт токенов — API подсчёта (Р35), когда появится ключ (`TODO.md`).

## Наблюдения при подготовке

Записываются для отчёта опыта (шаг 0.5):

- **Приоритет сдвига.** `x << 7 * i` значит `(x << 7) * i` (как в Go).
  При написании решения `t10` это была первая ошибка — вывод разошёлся с
  эталоном. В спецификациях это отдельный пункт.
- **Пометки аргументов** в A и B (`&x`, `&mut x`) переводчик сверяет с
  режимом параметра. В C пометок нет, и изменяемость видна только по
  сигнатуре.
- **Сдвиг и маска в одной строке без скобок.** Запись
  `u8(v & 0x7f | 0x80)` верна (`&` сильнее `|`), но читается неочевидно.
