# 1. Язык, удобный для ИИ: токены, точность, обратная связь

Заметки исследования, 3 октября 2026. Каждое утверждение — со ссылкой.

## Токены и синтаксис

- **Разница между языками — до 2,6 раза.** Martin Alderson, 8 января
  2026: задачи RosettaCode с решениями на 19 языках, токенизатор GPT-4.
  Clojure ≈ 109 токенов на задачу, Haskell и F# ≈ 109, Python ≈ 115,
  Ruby ≈ 118, JavaScript ≈ 125, Go ≈ 145, C# ≈ 150, C ≈ 285. Вывод
  автора: статические языки с сильным выводом типов (Haskell, F#) почти
  так же экономны, как динамические, а типы дают быструю проверку
  компилятором. J — 70, APL — 110.
  https://martinalderson.com/posts/which-programming-languages-are-most-token-efficient/
- **Форматирование стоит четверть входных токенов.** Pan, Sun, Zhang,
  Lo, Du, «The Hidden Cost of Readability», ICSE'26 (август 2025): удаление
  отступов и пробелов сокращает входные токены в среднем на 24,5% при
  незаметной потере качества (Java, Python, C++, C#; 10 моделей);
  промпт или дообучение — до 36,1% короче выход без потери правильности.
  https://arxiv.org/abs/2508.13666
- **«Сахар для токенов».** Sun и др., «Token Sugar», ASE'25 (декабрь 2025):
  799 частых многословных шаблонов заменены обратимыми сокращениями —
  до 15,1% меньше токенов в коде, до 11,2% при генерации, Pass@1
  практически тот же. Важно: работает, потому что модель **обучена** на
  сокращениях; для нового языка без обучения выгода не переносится.
  https://arxiv.org/abs/2512.08266
- **Токены агента зависят от языка сильнее, чем от размера кода.** Wu,
  Anderson, Guha, «The Best Programming Language for Tokenmaxxing», июль
  2026: 5 моделей, Python/Java/Rust/OCaml — расход токенов сильно и
  устойчиво (у всех моделей) различается по языку. Причины перерасхода:
  в незнакомом языке агент многократно выдаёт некомпилирующийся код,
  переделывает уже проходящие решения, прототипирует на Python и
  переводит. https://arxiv.org/abs/2607.22807
- Пост в блоге D (Adam Wilson, 10 августа 2026): явные типы требуют
  меньше «сыскных» токенов (модель не выводит смысл переменной из
  окружения); единый оператор `.` вместо `.`/`->` и UFCS удешевляют
  правки. https://blog.dlang.org/2026/08/10/language-plasticity-is-more-important-than-ever/

## Новый язык, которого модель не знает

- **Малоресурсные языки заметно хуже.** MultiPL-E — стандартный
  многоязычный бенчмарк; модели сильны на Python/Java/JS и слабы на
  OCaml, Racket и т. п. MultiPL-T (дообучение на переведённом и
  проверенном тестами коде) удваивает pass@1 для OCaml и Racket, Lua
  догоняет Python. https://arxiv.org/abs/2308.09895
- **Эзотерические языки по документации — плохо, но лечится примерами.**
  NeurIPS 2025: по документации и редким примерам модели пишут часть
  правильного кода, но много хуже, чем на обычных языках; «самоподмости»
  (проверенные решения возвращаются в промпт как примеры) поднимают
  Pyth с 16,67% до 30,82%.
  https://neurips.cc/virtual/2025/122346
- **Освоение языка во время работы.** «Bridging the Knowledge Void»
  (январь 2026): агент с навигацией по документации и проверкой кода
  (запуск, тесты) пишет на новом статическом языке Cangjie с точностью
  63–82% (DeepSeek-V3.2 … Claude Sonnet 4.5) против 47–66% у RAG. Без
  семантического поиска по документации — 73,55% → 53,55%; без
  проверки — такое же падение. Вывод авторов: нужны хорошо устроенная
  документация и надёжные сообщения компилятора.
  https://arxiv.org/html/2602.06976v1

## Языки, задуманные для ИИ

- **MoonBit** (с 2022, пред-бета): «ИИ — первоклассный пользователь».
  Обязательные сигнатуры типов на верхнем уровне, чёткое разделение
  верхнего уровня и локальных определений, встроенные expect-тесты,
  единый набор инструментов (компилятор, пакеты, LSP). Каждая новая
  синтаксическая форма проверяется прогоном генерации LLM. Сэмплер,
  который на лету проверяет синтаксис и типы: накладные ≈ 3%, задержка
  ≈ 0,86 с на подсказку.
  https://www.moonbitlang.com/blog/ai-coding ·
  https://conf.researchr.org/details/icse-2024/llm4code-2024-papers/9/MoonBit-Explore-the-Design-of-an-AI-Friendly-Programming-Language ·
  https://deepengineering.substack.com/p/designing-for-ai-and-humans-with

## Типы и обратная связь компилятора

- **Ограничение генерации типами.** Mündler, He, Wang, Sen, Song,
  Vechev, ICLR/PLDI 2025: декодирование с учётом типов (префиксные
  автоматы, вывод типов) **вдвое с лишним сокращает ошибки
  компиляции** и повышает функциональную правильность в синтезе,
  переводе и исправлении кода. https://arxiv.org/abs/2504.09246
- **Цикл с компилятором.** «From LLMs to Agents in Programming» (январь
  2026): с обратной связью компилятора к третьей итерации ≥ 92%
  программ компилируются; эффект сильнее всего в первых итерациях, и
  агент не делает посторонних правок. https://arxiv.org/pdf/2601.12146
- **RustAssistant** (Microsoft Research): итерации LLM ↔ компилятор Rust
  исправляют ≈ 74% реальных ошибок компиляции; самые частые — E0277
  (не реализован трейт) и E0308 (несовпадение типов), > 18% вместе.
  https://www.microsoft.com/en-us/research/publication/rustassistant-using-llms-to-fix-compilation-errors-in-rust-code/

## Инструменты для агентов

- Anthropic, «Writing effective tools for agents»: ответы инструментов
  оптимизировать под токены; краткий режим ответа ≈ 72 токена против
  ≈ 206 подробного; до 40% токенов в нагруженных MCP-задачах уходит на
  описания инструментов; «отложить и искать» сокращает их ≈ на 85%.
  https://www.anthropic.com/engineering/writing-tools-for-agents

## Что взять

1. **Знакомый синтаксис, а не изобретательный.** Модель переносит знание
   с близких языков (MultiPL-T, Cangjie); экзотика (J/APL-подобное)
   экономит символы, но не точность. Ключевые слова и формы — как в
   Go/Rust/Swift/Zig.
2. **Вывод типов внутри, явные сигнатуры на верхнем уровне** (MoonBit,
   Haskell/F# по токенам): экономия токенов + проверка.
3. **Канонический компактный формат.** Форматирование стоит ~25% входа;
   формат — один, без лишних пробелов, и инструмент `fmt` в двух
   режимах (плотный для ИИ — по замеру, читаемый для человека).
4. **Документация как продукт для модели:** иерархия, поиск,
   примеры к каждому разделу (ILA, «самоподмости»).
5. **Компилятор как часть цикла агента:** быстрая проверка без сборки,
   точные короткие ошибки с правкой; ограниченная грамматикой и типами
   генерация — когда появятся свои инструменты.
6. **Мерить расход токенов агента по языку** — как Wu и др.: задачи,
   траектории, токены до прохождения тестов.

## Осторожно

- Счёт токенов на RosettaCode ≠ стоимость работы агента: в агенте
  доминируют чтение и циклы исправления (Wu и др., и замер VoxelRPG:
  67% стоимости — чтение кэша).
- Сокращения из Token Sugar выгодны только обученной на них модели.
- Цифра «94% ошибок компиляции LLM — ошибки типов» ходит по блогам; в
  аннотации первоисточника её нет — не использовать без проверки.
