# 2. Быстрая сборка и бэкенды для устройств

Заметки исследования, 3 октября 2026.

## Что делает сборку быстрой

- **Go: нет циклических импортов.** Циклическая зависимость пакетов —
  ошибка компиляции; граф пакетов ацикличен, каждый пакет компилируется
  независимо и параллельно, а зависимость читается из сводки
  экспортируемого (export data), а не из исходников. Пайк: отсутствие
  циклов заставляет держать граф зависимостей чистым и сборку быстрой.
  https://appliedgo.net/spotlight/no-import-cycles/ ·
  https://www.dolthub.com/blog/2025-03-14-go-import-cycle-strategies
- **Jai: 250 тыс. строк в секунду** на собственном x64-бэкенде (бета
  0.0.045; игра на 80 тыс. строк — меньше секунды); цель автора — 1 млн
  строк/с. Сборочные скрипты — код на самом языке.
  https://digitalmars.com/d/archives/digitalmars/D/Jai_compiles_80_000_lines_of_code_in_under_a_second_319451.html ·
  https://github-wiki-see.page/m/Jai-Community/Jai-Community-Library/wiki/Overview
- **Zig: свой x86_64-бэкенд по умолчанию в отладочных сборках** (0.15+,
  Linux) и инкрементальная компиляция. Ghostty: полная сборка 41 → 32 с
  (0.14 → 0.15), инкрементальная 19 → 16 с, ожидание — около 25 с и
  меньше после полного перехода на свой бэкенд (часть кода он ещё не
  тянет). https://mitchellh.com/writing/zig-builds-getting-faster ·
  https://ziggit.dev/t/self-hosted-x86-backend-is-now-default-in-debug-mode/10447
- **Rust — пример того, что тормозит.** Дорожная карта «Fast Builds» 2026:
  однопоточный фронтенд при 16+ ядрах в CI, LLVM в отладочных сборках,
  пробелы инкрементальности, разрешение трейтов и проверка типов;
  «CI средних проектов — 30+ минут». Меры: Cranelift и TPDE (в 10–20 раз
  быстрее LLVM -O0) для отладки, параллельный фронтенд (до −50% на
  реальном коде при 8 потоках), «перелинковать, а не пересобрать» при
  правке только тел функций (ожидают ×5–10), свой линкер Wild.
  https://goals.rust-lang.org/2026/roadmap-fast-builds.html ·
  https://blog.rust-lang.org/2023/11/09/parallel-rustc/
- **Carbon** ставит «быструю и масштабируемую разработку» в цели:
  синтаксис для быстрого разбора, раздельная и параллельная компиляция.
  https://docs.carbon-lang.dev/

Дорогие для сборки возможности (по Rust и C++): мономорфизация
обобщённых типов, макросы, разрешение перегрузок и трейтов, включение
заголовков, глобальный вывод типов, тяжёлые вычисления при компиляции.

## Бэкенды

| вариант | плюсы | минусы |
|---|---|---|
| **Генерация C** (Nim, Koka, Vala, Chicken; Zig умеет как один из выходов) | все платформы, где есть компилятор C: NDK clang, MinGW, MSVC; зрелые оптимизаторы; `#line` даёт строки исходника в отладчике (Nim: `--debugger:native`, `--lineDir:on`) | имена переменных в отладчике — сгенерированные; порядок вычисления и неопределённое поведение C надо обходить в генераторе; ошибки на стыке с чужим компилятором C; сборка C — тоже время |
| **LLVM** (Rust, Zig, Swift, Odin, Carbon) | лучший код, DWARF/PDB, все цели | медленно в отладке, огромная зависимость |
| **QBE** (Hare, cproc) | ≈ 15 тыс. строк C99; цель — 70% скорости кода промышленных компиляторов в 10% кода; на CoreMark > 63% | 25–75% скорости LLVM, мало целей; нет Windows/Android «из коробки» |
| **Cranelift / TPDE** | быстрая отладочная сборка | не для выпуска |
| **Свой бэкенд** (Jai, Zig) | максимальная скорость | годы работы на каждую архитектуру |

## Android и Windows

- NDK собирает C/C++ через CMake (тулчейн
  `<NDK>/build/cmake/android.toolchain.cmake`) или ndk-build; Gradle
  вызывает их блоком `externalNativeBuild` и кладёт `.so` в APK;
  NativeActivity — полностью нативная активность без своего Java-кода.
  Язык, который генерирует C, встраивается в этот путь без изменений
  Gradle: сгенерированный C — просто ещё исходники для CMake.
  https://developer.android.com/studio/projects/gradle-external-native-builds ·
  https://developer.android.com/ndk/guides/cmake.html ·
  https://developer.android.com/ndk/guides/concepts
- Windows: тот же сгенерированный C собирается clang + lld поверх
  MinGW-w64 (как сейчас у VoxelRPG) или MSVC.

## Что взять

1. **Модуль = единица компиляции, граф модулей без циклов** (Go);
   зависимость читается из сводки интерфейса модуля, а не из исходника.
   Сводка — она же ответ компилятора агенту «что есть в модуле».
2. **Проверка без генерации кода** — отдельная быстрая команда (как
   `cargo check`): главный цикл агента.
3. **Бэкенд первой версии — генерация C** с `#line`: сразу NDK, MinGW и
   MSVC, без своей кодогенерации; позже — второй бэкенд для быстрых
   отладочных сборок (QBE/Cranelift/свой) и LLVM для выпуска, если замер
   покажет нужду.
4. **Ограничить дорогое:** обобщённые типы — с бюджетом (мономорфизация
   с кэшем и дедупликацией), вычисления при компиляции — с лимитом,
   никаких макросов, меняющих синтаксис.
5. **Замер скорости сборки — проверка в CI** (строк/с на эталонном
   проекте), как у Rust дорожная карта, но с порогом.

## Осторожно

- C-бэкенд наследует неопределённое поведение C: генератор обязан
  выдавать код без него (явные переполнения, `-fwrapv`/встроенные
  проверки, порядок вычислений — временными переменными).
- Сборка сгенерированного C — заметная доля времени; мерить отдельно
  «наш фронтенд» и «компилятор C».
- Цифры Jai — заявления автора и сообщества, не независимый замер.
