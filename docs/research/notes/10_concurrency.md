## 1. Что решено и что есть

### Решения и правила

| что | что говорит о параллелизме |
|---|---|
| Р6 | надёжность и контролируемость прежде скорости разработки и удобства ИИ |
| Р44 | ссылка — только параметр, не хранится и не возвращается: побега нет |
| Р45 | значения копируются целиком; общих владельцев нет |
| Р57, Р60 | линейные значения: закрыть ровно один раз на каждом пути |
| Р59 | без указателей безопасность памяти — за компилятором |
| Р66 | одно правило исключительного доступа: вызов, обход, `parallel for` |
| Р67 | `Pool[T]`, `Handle[T]` — хэндлы вместо указателей |
| Р69 | тело `parallel for`: без выходов; `out[j]` не читать; вывод по номеру итерации; `os` и C — запрет по графу вызовов |
| О15 | подсчёта ссылок в библиотеке нет до v1.0, пока программа без него обходится |
| `LANGUAGE.md`, 3.2 | структурные задачи; данные в задачу — по значению; общее — только для чтения на время области; изменяемое — непересекающимися частями; общее изменяемое — атомики, мьютекс, каналы; долгоживущий поток — линейный ресурс с обязательным присоединением |
| `DETERMINISM.md`, раздел 3 | в D — только параллельные циклы и отображения с упорядоченным объединением; разбиение не зависит от числа потоков; атомики с гонками, мьютексы, каналы — класс N |
| DoD, C и E | многопоточная программа (симуляция на системе задач с повтором); тесты детерминизма на 1…N потоков |
| `TESTING.md` | TSan — для параллельных тестов на сгенерированном C |

### Что в компиляторе и runtime

- `parallel` — ключевое слово (`compiler/syntax/tokens.def`).
  `parallel for` проверяется правилом Р66 (`compiler/sema/access.cpp`) и
  понижается как обычный `for`: итерации идут по очереди
  (`compiler/ir/lower.cpp`, о `parallel` не знает).
- Правила Р69 ещё не действуют: проба 31 октября — `break`, `try`,
  `return` и `println` в теле `parallel for` проходят `dpl check` и
  выполняются.
- Runtime: главный код идёт в отдельном потоке с большим стеком
  (`runtime/linux/dp_entry.c`, `runtime/windows/dp_entry.c`); счётчик
  выделений — `_Atomic` (`runtime/core/dp_rt.c`). Других примитивов
  потоков нет.
- Интерпретатор (`dpl debug run`) однопоточный; набор `run` сверяет его
  вывод с выводом сборки.
- Компилятор — 19 285 непустых строк `.cpp`, `.h`, `.def` без фаззера;
  runtime — около 1 090. Бюджет ядра — около 25 тыс. (Р-4, предложение).

## 3. Практика других языков

### Структурные задачи

- **Trio — «ясли» (nursery).** Блок не заканчивается, пока не
  закончились запущенные в нём задачи. Автор Trio предлагает убрать
  «запуск и забыть» совсем: `go` — разновидность `goto` для потока
  управления. Ясли — обычный объект, их можно передать параметром, и
  задача переживает функцию, которая её запустила; это осознанный
  компромисс.
  [vorpus.org](https://vorpus.org/blog/notes-on-structured-concurrency-or-go-statement-considered-harmful/)
- **Swift — группы задач.** Задачи не переживают область, где созданы;
  отмена группы доходит до детей; второй путь — `async let`.
  [TaskGroup](https://developer.apple.com/documentation/swift/taskgroup),
  [SE-0304](https://forums.swift.org/t/se-0304-structured-concurrency/45314)
- **Java — `StructuredTaskScope`.** Пятый предварительный выпуск в JDK 25
  (JEP 505), шестой — JEP 525: API за пять лет так и не стал
  окончательным. Не цель — заменить `ExecutorService` и `Future`.
  [JEP 505](https://openjdk.org/jeps/505), [JEP 525](https://openjdk.org/jeps/525)
- **Rust — `thread::scope`** (с 1.63, 2022). Обычный `spawn` требует
  `'static` и не может занять локальные данные; в `scope` можно: все
  потоки присоединяются до выхода. Паника потока, присоединённого
  автоматически, становится паникой области.
  [Rust 1.63](https://blog.rust-lang.org/2022/08/11/Rust-1.63.0/),
  [std::thread::scope](https://doc.rust-lang.org/std/thread/fn.scope.html)
- **Chapel — `cobegin` и `coforall`.** `cobegin` запускает каждый оператор
  блока задачей, `coforall` — задачу на итерацию; родитель ждёт своих
  детей (не внуков).
  [спецификация](https://chapel-lang.org/docs/language/spec/task-parallelism-and-synchronization.html),
  [учебник](https://chapel-lang.org/docs/primers/taskParallel.html)

Вывод: занимать локальные данные безопасно ровно потому, что область
ждёт задачи (Rust `'env`). У dpl ссылка и так не переживает вызов (Р44):
«область задач как один большой вызов» ложится на Р66 без новых
понятий времени жизни.

### Неструктурные задачи и пул

- **Zig — `std.Thread.Pool` и `WaitGroup`.** Задачи ставятся в пул,
  ожидание — группой ожидания; пул присоединяет потоки в `deinit`.
  [Pool.zig](https://github.com/ziglang/zig/blob/master/lib/std/Thread/Pool.zig),
  [Zig Cookbook](https://cookbook.ziglang.cc/07-03-threadpool)
- **Go — горутины без хэндла.** Ожидание — каналом или группой
  ожидания; утечка горутины — частая ошибка (заблокированная отправка
  после тайм-аута).
  [обзор каналов](https://www.golinuxcloud.com/go-channels/)

### Общее изменяемое

- **Мьютекс владеет данными (Rust).** Данные доступны только через
  стража `lock`; страж снимает блокировку при уничтожении; паника под
  блокировкой «отравляет» мьютекс.
  [исходник std](https://git.dreamy.place/mirrors/rust/plain/src/libstd/sync/mutex.rs?h=1.14.0)
- **Атомики Go — одна модель.** Модель памяти Go 2022: атомарные
  операции не образуют гонок данных, синхронизирующие операции
  объяснимы одним общим порядком; программа без гонок исполняется
  последовательно согласованно (DRF-SC). Ослабленных порядков памяти у
  Go нет — в отличие от C11.
  [The Go Memory Model](https://go.dev/ref/mem)
- **Каналы Go.** Буферизованные и без буфера; закрывает отправитель;
  приём из закрытого и пустого — признак `ok = false`; отправка в
  закрытый — паника; `select` ждёт нескольких каналов.
  [обзор](https://www.golinuxcloud.com/go-channels/)

### Проверка

- **ThreadSanitizer.** Цели: Linux x86-64 и aarch64, Android aarch64 и
  x86-64, Darwin, FreeBSD, NetBSD; Windows — нет; 32-битные — не
  планируются. Замедление — 5–15 раз, память — 5–10 раз.
  [clang: ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html)

Вывод: TSan закрывает хост (Linux x86-64) и Android; для Windows
остаётся «тот же сгенерированный C, проверенный на хосте».

## 4. Развилки

Что у dpl отличается от источников (вывод):

- нет замыканий — задача запускается вызовом функции;
- ссылка не хранится (Р44) — задача не держит ссылку дольше области;
- значения копируются (Р45) — почти любое значение можно отдать задаче
  копией; исключения — `extern type` (дескриптор C с неизвестной
  привязкой к потоку) и линейные значения (переносятся, не копируются);
- подсчёта ссылок нет (О15) — общий объект живёт в области, где создан,
  либо нужен скрытый счётчик в runtime.

### 4.1. Форма задач

| вариант | запись | плюсы | минусы |
|---|---|---|---|
| А. Блок задач | `tasks { spawn load(&q); for w in 0..n { spawn work(&q, w) } }` | структурно; число задач любое; аргументы `spawn` — как аргументы одного вызова (Р66) | два новых слова (`tasks`, `spawn`) |
| Б. Блок операторов (Chapel `cobegin`) | `parallel { a = f(x); b = g(y) }` | ни одного нового слова; запись короче всех | число задач — по числу операторов; динамическое — только `parallel for`, а там Р69 запрещает `os` (П3 с несколькими загрузчиками не выразить) |
| В. Линейный хэндл (`Task[T]`) | `let t = spawn f(x)` … `let v = t.join()` | будущее значение; долгая задача без блока | аргументы только по значению; общий канал или мьютекс — только через скрытый счётчик ссылок (против О15); забытый `join` — E0511, но задача живёт неопределённо долго |

Структурный ответ на П3 (вывод): долгая работа — задача в блоке на
верхнем уровне `main`: `tasks { spawn loader(&q); spawn game(&q) }`.
Отдельный тип долгого потока тогда не нужен. Остаётся вопрос главного
потока: SDL требует, чтобы окно жило в главном потоке. Предложение:
первый `spawn` блока (или тело `parallel { }` — первый оператор)
выполняется в текущем потоке.

### 4.2. Что можно передать в задачу

- **По значению** — любое значение, кроме `extern type` и значений с
  ним (развилка 4.7); линейное — переносом (Р60).
- **`&x`** — только чтение на время блока: пока блок идёт, `x` никто не
  пишет (Р66, вывод).
- **`&mut x`** — непересекающиеся места: все `spawn` блока — как
  аргументы одного вызова (E0502); `spawn` в цикле блока — по правилу
  `parallel for`: место по переменной цикла (`&mut out[i]`).
- **Конкурентные типы** (`Atomic`, `Mutex`, `Channel`) — по `&`, их
  операции меняют значение через общую ссылку. Это исключение из Р66, и
  его надо записать (предложение).

### 4.3. Результаты, ошибки, ловушки

- **Результат задачи.** А и Б: через `&mut` в аргументах (`spawn
  sum(&part, &mut total[w])`). В: `t.join()` даёт значение.
- **Ошибка.** Варианты: функция задачи — без `E!T` (ошибку пишут в
  `&mut` результат) / блок — ошибка первой по порядку записи задачи с
  `E!T`, после ожидания всех (детерминированно). Предложение — первое:
  то же, что Р69 для `parallel for`.
- **Отмена.** Автоматической отмены нет; кооперативная — флаг
  `Atomic[bool]` (П4). Отмена по ошибке — после замера на шлюзе.
- **Ловушка в задаче** останавливает программу, как сейчас; сообщение —
  первой ловушки. В D это не наблюдаемый результат, а ошибка программы.

### 4.4. Атомики

- **Типы:** `Atomic[T]`, `T` — целые и `bool`.
- **Операции:** `load`, `store`, `add`, `sub`, `swap`, `cas`.
- **Порядок памяти:** только последовательная согласованность (как Go) /
  явные порядки C11. Предложение — первое: проще, ошибок порядка нет;
  ослабленный — по замеру на П1.
- **Класс D:** атомики — класс N (`DETERMINISM.md`), из D — E0425.

### 4.5. Мьютекс

Нужна форма без замыканий и без хранимой ссылки (Р44):

| вариант | запись | замечание |
|---|---|---|
| М1. Блок | `lock m as t { t.hits += 1 }` | `t` — `&mut T` до конца блока; снятие — на любом выходе, как `defer` |
| М2. Методы копией | `let v = m.get()`, `m.set(v)` | чтение-изменение-запись — гонка между `get` и `set` |
| М3. Линейный страж | `let g = m.lock()` … `g.unlock()` | данные через стража — хранимая ссылка, против Р44 |

Предложение — М1: одно новое слово `lock`, данные недоступны вне блока.
Взаимную блокировку (два `lock` в разном порядке) язык не ловит —
предложение: порядок блокировок в руководстве, проверка — после замера.

### 4.6. Каналы

- **`Channel[T]`** с ёмкостью: `send(v)` ждёт места; `recv()` → `?T`,
  `none` — канал закрыт и пуст; `close()`; отправка в закрытый —
  ловушка.
- **Без буфера** — нужен ли (рандеву) / только буферизованные.
- **`select`** — ожидание нескольких каналов и тайм-аут. Шлюзу нужен
  тайм-аут (вывод); предложение — после замера на шлюзе, не в первом
  шаге.
- **Кто владеет.** В А и Б канал живёт в области блока и передаётся
  `&`: счётчик ссылок не нужен. В В концы канала уходят в задачи по
  значению — нужен общий объект со скрытым счётчиком (против О15).

### 4.7. `extern type` и функции C в задачах

Р69 запретил `os` и C в теле `parallel for`. Для задач так нельзя: П3 —
это загрузка файлов и разбор в фоне. Варианты:

- в задачах разрешены `os` и C; `extern type` в задачу не передаётся
  (E0xxx), дескриптор живёт в создавшем его потоке;
- то же, плюс пометка у `extern type`, что дескриптор можно передавать
  (`@send`), — для библиотек, которые это разрешают;
- запрет C в задачах — П3 с разбором через C не выразить.

Предложение — второе, пометка — по запросу привязки (Vulkan разрешает
передачу большинства дескрипторов, SDL — нет).

### 4.8. Runtime и интерпретатор

- **Пул потоков:** по числу ядер; переопределение — `DPL_THREADS`;
  стек рабочих — как у главного (`DP_STACK_BYTES`). `parallel for` —
  части фиксированного размера (в D это требование политики), вложенный
  параллельный цикл — по очереди в своём потоке.
- **Цели:** pthreads на Linux и Android; Win32 (`CreateThread`,
  `SRWLOCK`, `CONDITION_VARIABLE`) на Windows; атомики — C11
  `stdatomic.h` (уже в runtime).
- **Вывод по номеру итерации** (Р69): буфер на итерацию, сброс по
  порядку.
- **Интерпретатор.** `parallel for` и блок без каналов можно исполнять
  по очереди — это допустимый порядок. Канал с ожиданием по очереди
  зависнет: производитель ждёт места, а потребитель ещё не запущен.
  Варианты: настоящие потоки в интерпретаторе / программы с каналами —
  только сборкой (как набор `ffi`). Предложение — потоки в
  интерпретаторе: набор `run` остаётся общим.
- **TSan:** проход `tsan` в `tests/run.py` — сборка программ с
  параллелизмом с `-fsanitize=thread` на хосте; любое сообщение — сбой.

## 5. Варианты модели целиком

Развилки 4.1–4.7 сводятся к трём вариантам (вывод):

| | А. Блок задач | Б. Блок операторов | В. Линейные задачи |
|---|---|---|---|
| форма | `tasks { spawn f(…) }` | `parallel { оператор; … }` | `let t = spawn f(…)`, `t.join()` |
| новые слова | `tasks`, `spawn`, `lock` | `lock` | `spawn`, `lock` |
| П1 | `parallel for` | `parallel for` | `parallel for` |
| П2 | да | да | да |
| П3 | задача в блоке `main` | только постоянное число задач | да |
| П4, П5 | `&Atomic`, `&Mutex` | то же | общий объект со счётчиком ссылок |
| ссылки в задачу | `&`, `&mut` по Р66 | то же | нет, только значения |
| счётчик ссылок | нет | нет | да (против О15) |
| оценка компилятора и runtime | 1 200–1 800 строк | 900–1 400 | 1 600–2 400 |

Оценки — до замера (вывод); общая часть (пул потоков, вынос тела в
функцию, Р69, вывод по итерациям, атомики, мьютекс, каналы, TSan) —
около 900–1 200 строк в любом варианте.

## 6. Как решить по замеру (Р24)

Весь раздел — предложение; решает автор.

1. **Общая основа** — нужна любому варианту и прототипу: пул потоков
   runtime на трёх целях, вынос тела `parallel for` в функцию, Р69,
   вывод по номеру итерации, проход TSan. Это прототип для замера, но и
   готовая часть реализации.
2. **Задачи t20–t24** с эталоном на C++ и тестами — по образцам П1–П5:
   - t20 — шаг симуляции с упорядоченной свёрткой (П1, D, 1…N потоков);
   - t21 — загрузка с разбором в фоне через канал (П3);
   - t22 — fork-join трёх разных вычислений (П2);
   - t23 — рабочие с общим счётчиком и флагом остановки (П4);
   - t24 — кэш под мьютексом у нескольких рабочих (П5).
3. **Варианты — режимами компилятора** (как замер Р66): А, Б, В на
   одном runtime.
4. **Мера:**
   - выразимость: решается ли задача, строк против C++;
   - атаки: около 30 попыток гонки (как `bench/o4/attacks.dpm`) — доля
     ошибок компиляции; принятые — под TSan;
   - сессии моделей с вариантом в руководстве (серии `k2`): правильность
     с первой попытки, токены против C++;
   - цена в строках; ускорение t20 на 1…N потоках против C++.
5. **Решение** — одно на всю модель; затем реализация выбранного
   варианта и снятие режимов.

## 7. Совет исследования (решает автор)

- Основа — **А** (блок задач): ложится на Р44 и Р66 без новых понятий
  времени жизни, без счётчика ссылок, П3 выражается задачей в блоке
  `main`. **Б** — запасной, если замер покажет, что `spawn` в цикле не
  нужен. **В** — только если П3 на А окажется неудобным в сессиях.
- Атомики — только последовательная согласованность; мьютекс — блок
  `lock`; каналы — буферизованные, `select` — после замера на шлюзе.
- `extern type` в задачу — только с пометкой `@send`.
- Начать с общей основы (раздел 6, п. 1): она нужна при любом выборе и
  без неё варианты не замерить.
