# Политика тестирования и корректности компилятора

Как проверяется язык, компилятор, runtime и стандартная библиотека, как
запускать проверки и как читать результат. Основание — Р13, Р23,
постановка автора (разделы 12–13).

## 1. Правила

1. **Каждая найденная ошибка компилятора или runtime становится
   регрессионным тестом** в том же PR, что её исправляет.
2. **Тесты детерминированы:** без времени и случайности, кроме зерна;
   исполнитель тестов выводит результаты в определённом порядке при любом
   числе потоков.
3. **Ожидаемый вывод — в файлах рядом с тестом** (золотые тесты);
   обновляется командой «принять» (`--bless`), дифф проходит ревью.
4. **Сообщения об ошибках — продукт:** у каждой диагностики — снимок; у
   каждого кода ошибки — хотя бы один тест отказа компиляции.
5. **Каждый нормативный пункт спецификации** имеет идентификатор и
   хотя бы один тест соответствия.
6. **Известная и необъяснённая критическая ошибка** компилятора или
   runtime блокирует выпуск (`docs/direction/DEFINITION_OF_DONE.md`, F).

## 2. Уровни

### Компилятор

| набор | что проверяет | форма |
|---|---|---|
| лексер | токены, позиции, ошибки | исходник → золотой список токенов |
| парсер | дерево без потерь, восстановление после ошибок | исходник → золотой AST; круг «разбор → печать → разбор» |
| семантика | имена, модули, видимость, граф без циклов | исходник → золотой HIR или диагностика |
| система типов | вывод, обобщённые типы, суммы типов, исчерпывающий `match`, проверки памяти и ресурсов, классы поведения | положительные и отрицательные примеры |
| Core IR | понижение и верификатор | золотые дампы IR; верификатор на каждом тесте |
| бэкенд | сгенерированный C компилируется без предупреждений и исполняется | исходник → ожидаемый вывод программы |
| диагностика | тексты, коды, правки | снимки (текст и JSON) |
| отказ компиляции | каждая запрещённая конструкция отвергается с нужным кодом | исходник с пометками ожидаемых ошибок (как UI-тесты Rust) |
| фаззинг | парсер и типизатор не падают; генерируемые корректные программы | раздел 3 |

### Runtime и стандартная библиотека

| набор | что проверяет |
|---|---|
| модульные | функции библиотеки и runtime |
| интеграционные | программы целиком: файлы, потоки, сериализация |
| ABI | обвязка на C: раскладка `extern`-структур, вызовы в обе стороны, обратные вызовы |
| платформенные | весь набор на каждой цели первой волны (`docs/policy/PLATFORMS.md`) |
| детерминизм | повторы, межплатформенные хэши, независимость от потоков (`docs/policy/DETERMINISM.md`, раздел 5) |

### Язык

| набор | что проверяет |
|---|---|
| соответствие | каждый нормативный пункт спецификации; каталог по номерам пунктов |
| тесты спецификации | примеры из текста спецификации исполняются |
| совместимость | корпус по редакциям (`docs/policy/COMPATIBILITY.md`, раздел 5) |
| регрессии | по одному тесту на исправленную ошибку, с номером |

### Production

Не только игрушечные примеры: программы проверки v1.0
(`DEFINITION_OF_DONE.md`, C и L) и нагрузочные случаи компилятора —
сгенерированные проекты на сотни тысяч строк, глубокая вложенность,
тысячи модулей, длинные цепочки обобщённых типов.

## 3. Стратегия против регрессий компилятора

| механизм | как |
|---|---|
| золотые тесты | AST, HIR, IR, сгенерированный C (выборочно), вывод программ, диагностика |
| различающие тесты | одна программа: эталонный интерпретатор Core IR (Р43) против native-сборки; `debug` против `release`; хост против другой цели (проходы `windows` — под Wine и `android` — под qemu-aarch64); функции C — набор `ffi`: сборка на трёх целях против ожидаемого; позже — C-бэкенд против второго бэкенда |
| фаззинг | грамматический фаззер парсера («не падает»); генератор корректных программ без неопределённого поведения (по образцу Csmith и YARPGen) + различающее сравнение; мутации тестов отказа компиляции |
| случайное тестирование | проверка свойств (property testing) для библиотеки и оптимизаций (сохранение семантики) |
| самопроверки компилятора | верификатор IR после каждого прохода в `debug`-сборке компилятора; внутренние утверждения |
| санитайзеры | ASan и UBSan на сгенерированном C в профиле `test`; TSan для параллельных тестов; найденное в сгенерированном C — ошибка бэкенда |
| набор отказа компиляции | каждый запрет спецификации и каждый код ошибки |
| снимки диагностики | текст и JSON |
| соответствие бэкенда | один набор исполнительных тестов на всех бэкендах и целях |

## 4. Раскладка тестов (целевая)

```
tests/ lex/ parse/ sema/ types/ ir/ backend/ diag/ fail/
       conformance/<пункт спецификации>/
       compat/<редакция>/
       runtime/ stdlib/ abi/ platform/ determinism/
       fuzz/ stress/ regress/<номер>/
```

## 5. Уровни прогона

| уровень | что | когда |
|---|---|---|
| быстрый | тесты затронутых частей + статические проверки | после каждой задачи |
| полный | `tools/check/run.sh`: все наборы на Linux-хосте, сборка Windows и Android, исполнение под Wine и эмулятором arm64 | перед переводом PR из черновика, перед вливанием, после рискованных правок |
| расширенный | фаззинг (часы), межплатформенные повторы, нагрузочные случаи, санитайзеры, замеры | перед выпуском и раз в веху |

Все уровни выполняются в сессии; GitHub Actions не используется (Р3,
`CLAUDE.md`).

## 6. Как читать результат

- Итог `run.sh`: на зелёном — счёт по наборам; на красном — первый сбой
  и хвост журнала; полный журнал — `build/check/`.
- Сбой золотого теста — дифф ожидаемого и полученного: сперва решить,
  ошибка это или верное изменение; «принять» — только второе, с
  объяснением в PR.
- Сбой различающего теста — ошибка в одном из путей; минимизировать
  пример (редуктор) и завести регрессионный тест.
- Сбой проверки детерминизма — номер такта, где разошлись хэши, и
  класс операции; это всегда ошибка, не «флаки».
- «Флаки» не бывает: нестабильный тест — ошибка теста или кода
  (`CLAUDE.md`, «Перед правкой и после»).
