# Инженерные правила и порядок участия

Как в проекте планируют, меняют, проверяют и документируют. Обязательный
минимум для агента — `CLAUDE.md`; здесь — полные правила и пояснения.
Основание — Р3 (инженерная культура VoxelRPG и лучшие практики).

## 1. Цикл задачи

1. **Сверка** запроса с `DECISIONS.md`, `CLAUDE.md`, `ROADMAP/`,
   `TODO.md`; расхождение — вопрос автору до работы.
2. **Контракт задачи** (для задач крупнее мелкой): цель — один
   проверяемый результат; что можно менять; что не трогать; условие
   готовности; какие проверки; «ничего не делать» — допустимый итог,
   если цель уже выполнена.
3. **Проверить — сделать или не трогать:** убедиться, что нужного
   поведения нет; есть похожее — дополнить, а не писать второе.
4. **Маленькие проверяемые изменения:** одно изменение — одна мысль;
   рефакторинг отдельно от изменения поведения.
5. **Проверки** — по `docs/policy/TESTING.md`, раздел 5.
6. **Коммит и пуш** после каждого законченного куска; PR — сразу
   черновиком с «сделано / осталось».
7. **Готово — остановиться:** условие выполнено и проверки прошли —
   не улучшать соседнее.

## 2. Решения

- Архитектурное решение записывается в `DECISIONS.md` (контекст,
  решение, почему, рассмотрено и отклонено, история) **до** работы, на
  которую оно влияет. Незаписанных решений нет: если код опирается на
  выбор, который нигде не записан, — это долг, его записывают.
- Вопрос, который ещё не решён, — в `docs/direction/OPEN_DECISIONS.md`
  с рекомендацией и сроком.
- Решение, которое можно измерить, принимается после эксперимента (Р24).
- **Новая возможность языка** входит, только если есть: программа,
  которой она нужна (не одна временная интеграция — Р22); замер или
  довод по порядку целей (Р6, Р25); оценка цены в компиляторе и в
  спецификации. Интересность — не довод (Р6, п. 9).
- Изменение языка в режиме production — по
  `docs/policy/COMPATIBILITY.md`, раздел 4.

## 3. Ревью

Проверочный список для PR (автор и агент):

- изменение в рамках контракта задачи, без посторонних файлов;
- нет расхождения с `DECISIONS.md` и спецификацией;
- нет второй реализации существующего;
- тесты: новое поведение покрыто; исправленная ошибка — регрессионный
  тест;
- диагностика: новые коды — в реестре, снимки обновлены осознанно;
- детерминизм: код класса D не трогает N и P;
- документы: обновлено то, что изменилось (раздел 5);
- полный `tools/check/run.sh` — зелёный, итог — в описании PR.

## 4. Аудиты и долг

- **Аудиты** — после каждой версии v0.x, перед выпуском и по запросу
  автора: соответствие плана и кода решениям, сложность, долг, риски
  (`docs/direction/RISKS.md`); после версии — ещё фактическая цена в
  шагах (шаг — законченный кусок с проверками, как в VoxelRPG) и прогноз
  до v1.0 для критерия К-1. Итог — `docs/audits/<дата>-<тема>.md`;
  находки — в `TODO.md` или `ROADMAP/`.
- **Долг** записывается в `TODO.md` только с подтверждением в коде,
  тестах или документах; критичное — сверху; устраняется в ближайшей
  задаче, которая трогает это место, или отдельной задачей.

## 5. Документация — часть инженерной системы

Критерий (Р3): по документам другой агент или разработчик может понять
архитектуру, найти компонент, понять контракт, внести изменение,
запустить правильные проверки и истолковать результат. Карта —
`docs/README.md`.

| документ | когда менять |
|---|---|
| `DECISIONS.md` | только при изменении решения |
| `OPEN_DECISIONS.md` | вопрос появился или решён |
| `docs/design/`, затем `docs/spec/` и описание устройства | изменилось устройство или семантика |
| `docs/policy/` | изменилось правило процесса |
| `ROADMAP/` | изменились состояние или границы задач |
| `TODO.md` | новый или закрытый хвост |
| `docs/CHANGELOG.md` | веха, выпуск, ломающее изменение |

CHANGELOG не заменяет описание устройства; архив — не источник решений.

## 6. Правила для кода

Общие (уточняются вместе с О16):

- вывод компилятора детерминирован: одинаковые входы — одинаковые
  байты; обход неупорядоченных контейнеров не влияет на вывод;
- нет изменяемого глобального состояния; каждый проход компилятора —
  функция с явными входами и выходами, у каждого — тесты;
- ошибки пользователя — диагностика с кодом, а не падение; падение
  компилятора — всегда ошибка;
- чужой код и чужие ассеты — только по `docs/THIRD_PARTY.md` и
  `CLAUDE.md`, «Защита и оригинальность»;
- если компилятор пишется на C++ (О16) — подмножество VoxelRPG: C++20,
  без исключений и RTTI.

## 7. Кто участвует

До v1.0 проект закрыт (Р5): участвуют автор и сессии ИИ по его
поручению. Внешние вклады не принимаются. Правила для внешних участников
— отдельным решением после v1.0.

## 8. Коммиты и ветки

- Сообщения коммитов — по-русски: что и почему; в конце — какие
  проверки прошли.
- Незаконченное — с `WIP:` в заголовке и словами, что осталось.
- Рабочая ветка → PR в `main`; вливает автор; `main` всегда зелёный
  (полный прогон перед вливанием).
