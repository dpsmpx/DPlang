# Архитектура toolchain dpl (проект)

**Статус:** целевое устройство, кода ещё нет. По мере реализации разделы
становятся описанием устройства и выносятся в `docs/compiler/`,
`docs/ir/`, `docs/runtime/` (карта — `docs/README.md`). Решения —
`docs/direction/DECISIONS.md` (Р16, Р17, Р26, Р28); открытые вопросы —
`docs/direction/OPEN_DECISIONS.md`.

## 1. Конвейер

```
исходник (.dpm, редакция в манифесте)
  → лексер и парсер ─────────── дерево без потерь (вместе с комментариями)
  → AST
  → разрешение имён и модулей ── сводки интерфейсов модулей (S1)
  → HIR: типы, классы поведения, проверки памяти и ресурсов, контракты
  → Core IR (S1, верификатор) ─ эталонный интерпретатор (только тесты)
  → оптимизация над Core IR
  → интерфейс бэкенда
  → C-бэкенд → C11 + #line → закреплённый компилятор C цели
  → runtime и ABI (статически)
  → native-программа или пакет (Linux, Windows, Android)
```

| этап | ответственность | вход → выход | класс | чем проверяется |
|---|---|---|---|---|
| лексер, парсер | токены, дерево без потерь, восстановление после ошибок; разбор не зависит от типов (Р7) | текст → дерево | S2 (грамматика — S0 через спецификацию) | тесты разбора, фаззинг «не падает» |
| AST | синтаксические конструкции с позициями | дерево → AST | S2 | снимки AST |
| разрешение имён | модули, видимость, граф без циклов (Р14), сводки интерфейсов | AST → связанное AST, сводки | S2, сводки — S1 | тесты имён и модулей |
| HIR и семантика | вывод типов в теле (Р8), исчерпывающий `match`, определённая инициализация (Р11), ссылки без побега и исключительный доступ (Р9), линейные ресурсы, классы поведения (Р29), контракты (Р13) | AST → HIR | S2 | тесты типов, снимки диагностики, тесты отказа компиляции |
| Core IR | маленькое явное представление: базовые блоки, явные проверки границ и переполнения, явные операции с памятью и вызовы; без неопределённого поведения | HIR → Core IR | S1 | верификатор, золотые дампы, интерпретатор |
| оптимизация | встраивание, свёртка, удаление доказанно лишних проверок, мёртвый код; сохраняет семантику детерминированного класса (без переассоциации плавающей точки) | Core IR → Core IR | S2 | различающие тесты: с оптимизацией и без, против интерпретатора |
| C-бэкенд | C11 только с определённым поведением: проверки явные, обёрточная арифметика — беззнаковая, переинтерпретация — через `memcpy`; `#line` на каждую строку исходника; `restrict` — только там, где исключительность доказана анализом (возможность v0.3) | Core IR → C | S2 | компиляция без предупреждений, исполнение, различающие тесты |
| компилятор C цели | закреплённая версия и флаги: `-ffp-contract=off`, `-fno-strict-aliasing`, без fast-math | C → объектные файлы | — (внешний, закреплён) | воспроизводимость сборки |
| runtime, линковка | вход в программу, ловушки, аллокатор по умолчанию, потоки, мост к платформе | → программа | runtime — S2, контракт с компилятором — S1 | тесты runtime и ABI на каждой цели |

## 2. Классы стабильности (Р26)

| артефакт | класс | версия | что значит для потребителя |
|---|---|---|---|
| исходный язык | S0 | редакция | код редакции E собирается всеми компиляторами, поддерживающими E |
| публичный API стандартной библиотеки | S0 | мажорная версия библиотеки | удаление — только после устаревания с правкой `fix` |
| C ABI объявлений `extern` | S0 | ABI платформы | раскладка и вызов — как у C на цели |
| форматы стандартной сериализации | S0 | версия формата в данных | старые данные читаются, пока формат объявлен поддерживаемым |
| манифест пакета и lockfile | S0 | поле `format` | инструменты переводят старый формат вперёд сами |
| схема диагностики (JSON) и коды ошибок | S0 | версия схемы | изменения внутри мажорной версии — только добавлением; коды не переиспользуются |
| Core IR | S1 | версия IR | внутренний контракт фронтенда и бэкендов; наружу не поставляется |
| контракт компилятора и runtime | S1 | версия компилятора | всегда одной версии |
| сводки интерфейсов модулей | S1 | хэш компилятора | пересоздаются, наружу не поставляются |
| AST, HIR, оптимизации, генерация кода, сгенерированный C | S2 | — | меняются свободно |
| внутреннее устройство runtime и библиотеки | S2 | — | меняется свободно |
| кэши и объектные файлы | S2 | ключ — хэш компилятора | никакой совместимости между версиями компилятора |

## 3. Что можно менять и чего это стоит

| изменение | исходник потребителя | пересборка программы | миграция | допустимо как ломающее |
|---|---|---|---|---|
| S2: оптимизации, генерация кода, внутренности runtime и библиотеки | не меняется | да | нет | нет — это не ломающее изменение |
| S1: Core IR, сводки, контракт runtime | не меняется | да | нет | нет |
| новый бэкенд или новая цель | не меняется | да (для цели) | нет | нет |
| новое предупреждение | не меняется | — | нет | нет (ошибкой — только по выбору проекта) |
| исправление ошибки компилятора, расходившегося со спецификацией | не меняется, если код следовал спецификации | да | нет | да, с записью в CHANGELOG |
| исправление дыры в надёжности (unsoundness) | может потребовать правки | да | правка `fix`, где возможна | да, по решению; с периодом предупреждения, где возможен |
| новая редакция языка | только при переходе модуля на неё | да | `fix --edition` | да, только редакцией (Р18) |
| устаревание API стандартной библиотеки | нет до удаления | да | `fix` | удаление — только в новой мажорной версии |
| формат стандартной сериализации | нет | да | данные: чтение старых версий сохраняется | только новой версией формата |
| схема сохранений самой программы | — | да | код миграции программы | решает программа (у VoxelRPG — его `DECISIONS.md`) |
| данные, конфигурация, внешние библиотеки за C ABI | нет | **нет** | нет | — |

Без пересборки меняются только данные, конфигурация и внешние
библиотеки за C ABI: runtime и стандартная библиотека линкуются
статически, стабильного ABI между модулями разных версий компилятора нет
(Р26). Пересборка дешёвая и воспроизводимая (раздел 5).

## 4. Версионирование

| что | схема | правило |
|---|---|---|
| язык | редакции по году (Р37) | модуль объявляет редакцию в манифесте; модули разных редакций собираются вместе |
| компилятор | MAJOR.MINOR.PATCH | после v1.0 поддерживает все редакции начиная с редакции v1.0; снятие — только решением с путём миграции |
| стандартная библиотека | поставляется с компилятором; мажорная версия API | устаревание — минимум два минорных выпуска с правкой `fix` до удаления |
| runtime | версия компилятора | внутренний; всегда той же версии |
| C ABI | ABI платформы | стабилен по определению |
| форматы данных | версия формата в каждом сохранённом блоке | список поддерживаемых версий — в документации библиотеки |
| манифест, lockfile | поле `format` | перевод вперёд — автоматически |
| диагностика | версия схемы JSON; реестр кодов ошибок | коды не переиспользуются |
| Core IR | внутренняя версия | меняется с компилятором; верификатор знает текущую |

До первого consumer project с production-кодом гарантий нет (Р0); с ним
действует `docs/policy/COMPATIBILITY.md`.

## 5. Сборка, пакеты, воспроизводимость

- **Модуль** — файл `.dpm`, единица компиляции и видимости (Р14, Р46);
  модуль-каталог — с пакетами в v0.4, отдельным решением. **Пакет** —
  набор модулей с манифестом: имя, версия, редакция, зависимости, цели,
  профили.
- **Зависимости** — путь или git с закреплённым хэшем; **lockfile** —
  точные хэши всего, включая инструменты генерации; реестра до v1.0 нет
  (О22).
- **Инкрементальная сборка** — по сводкам интерфейсов: правка тела
  функции не пересобирает зависимые модули; ключ кэша — (хэш
  компилятора, цель, профиль, хэши входов).
- **Чистая сборка** всегда возможна и даёт тот же результат, что
  инкрементальная (проверяется сравнением).
- **Воспроизводимая сборка** — те же входы дают те же байты (определение —
  `docs/policy/DETERMINISM.md`, раздел 6): без времени сборки в
  артефактах, упорядоченные входы, перенос путей (`-ffile-prefix-map`),
  закреплённые версии компиляторов C, NDK и MinGW.
- **Кросс-компиляция** — по описанию цели: тройка цели, закреплённый
  компилятор C и его флаги, корень SDK. Linux-хост собирает все цели
  первой волны (как VoxelRPG: clang + lld поверх MinGW-w64, NDK clang).
- **Профили:** `debug` (без оптимизаций, все проверки), `release`
  (оптимизации, проверки остаются — Р11), `test` (как `debug` + ASan и
  UBSan на сгенерированном C, TSan — для параллельных тестов).
- **Статический анализ** — проверки самого компилятора (линты с кодами) и
  стандартные анализаторы C на runtime.
- **Сгенерированный код** — привязки хранятся в репозитории, генератор и
  вход закреплены (О23); сгенерированный C — только в каталоге сборки.
- **Сценарии сборки** — произвольного кода при сборке нет до v1.0 (О25).
- **Проверки** — `tools/check/run.sh` уровнями: быстрый (после задачи),
  полный (перед вливанием), расширенный (фаззинг, долгие замеры —
  перед выпуском). Запускаются в сессии; GitHub Actions не используется
  (Р3, `CLAUDE.md`).

## 6. Платформенные границы (Р28)

1. **Описание цели** — данные: тройка, размер указателя, порядок байтов,
   компилятор C и флаги, системные библиотеки.
2. **Runtime под ОС** — вход в программу (консоль и `WinMain` на Windows,
   `NativeActivity` на Android), потоки, время, файлы, ловушки.
3. **Модуль `platform` стандартной библиотеки** — единственное место, где
   библиотека видит ОС; остальная библиотека от неё не зависит.
4. **Объявления с атрибутом цели** — условная компиляция только на уровне
   объявлений; каждая ветка компилируется и проверяется на своей цели.

Допущения первой волны: 64-битные адреса, порядок байтов от младшего,
IEEE 754. Цель, нарушающая их, — отдельное решение. Новая цель —
описание цели, порт runtime, модуль `platform`, задача CI; фронтенд и Core
IR не меняются (это и есть проверка границы).

## 7. Runtime и ABI

- **Runtime** — маленький, без сборщика мусора: вход и выход, обработчик
  ловушек с диагностикой (в отладке — стек вызовов), аллокатор по
  умолчанию, примитивы потоков, мост к платформе. Линкуется статически.
- **Внутреннее соглашение вызова** — S2, не специфицируется.
- **`extern`** — соглашение вызова C платформы; **`extern`-структуры** —
  раскладка C; у остальных типов раскладка не гарантирована.
- **Ловушка** (Р36) — детерминированная остановка: код ошибки, место в
  исходнике, в отладке — стек; программа может зарегистрировать
  обработчик аварии (отчёт, сохранение журнала), но не продолжить
  выполнение.

## 8. Отладка и профилирование

- `#line` в сгенерированном C: gdb и lldb на Linux, lldb из NDK на
  Android, отладчик Visual Studio или lldb на Windows показывают строки
  исходника dpl. Имена символов — читаемые (`модуль__функция`).
- Профилирование — внешние профилировщики (perf, simpleperf, ETW) и
  маркеры зон из стандартной библиотеки.
- Документированный порядок отладки на трёх целях — условие v1.0
  (`docs/direction/DEFINITION_OF_DONE.md`, H).

## 9. Инструменты

- **CLI компилятора** — `check`, `build`, `test`, `fmt`, `fix`,
  `explain`, `query` (Р15); машиночитаемый режим везде.
- **Language server** — поверх того же фронтенда и движка запросов
  (`query`): диагностика, переход к определению, поиск ссылок,
  переименование через движок `fix`.
- **`fmt`** — по дереву без потерь; один формат, без настроек (Р7).
- **`fix`** — миграции редакций и модернизаторы по дереву без потерь и
  семантике; каждая правка — машинно применима и проверяема.
- **Тесты и замеры** — `test` (блоки тестов, expect-тесты, фаззинг,
  повтор) и исполнитель замеров (`docs/policy/BENCHMARKS.md`).

## 10. Целевая раскладка кода

```
compiler/   syntax/ (лексер, парсер, дерево без потерь, AST)
            sema/   (имена, модули, HIR, типы, проверки)
            ir/     (Core IR, верификатор, интерпретатор для тестов)
            opt/    (оптимизации)
            backend_c/
            driver/ (CLI, сборка, кэш, пакеты)
            tools/  (fmt, fix, query, language server)
runtime/    core/ linux/ windows/ android/
stdlib/     модули стандартной библиотеки на dpl
bindings/   gen/ (генераторы) vulkan/ sdl3/ jni/ (сгенерированное)
tests/      по уровням — docs/policy/TESTING.md, раздел 4
bench/      нагрузки и результаты — docs/policy/BENCHMARKS.md
examples/   программы проверки v1.0 — DEFINITION_OF_DONE.md, C и L
```

Язык реализации компилятора — C++20 в подмножестве VoxelRPG (Р34).
