# Эталонный набор задач (v0.0, шаг 0.1)

Мера целей языка (`docs/direction/GOAL.md`, раздел 2): одни и те же задачи
решаются на C++ и на вариантах синтаксиса dpl (`ROADMAP/IMPLEMENTATION.md`,
v0.0). Набор — **внутренний материал** (Р5): не публикуется. Кода Galdhold
в нём нет — задачи описаны заново и лишь похожи по роду на работу движка и
игры.

## Устройство задачи

- `task.md` — постановка и интерфейс (в нейтральной записи: в каждом
  варианте синтаксиса интерфейс записывается своим способом).
- `ref.cpp` — эталон на C++20: над строкой `// --- driver ---` — решение,
  под ней — драйвер, печатающий результаты. У задачи из нескольких
  модулей (`t13`, `t19`) вместо него каталог `ref/`: модули и драйвер `main.cpp`.
- `expected.txt` — ожидаемый вывод драйвера.
- `buggy.cpp` (`t12`, `t18`) — версия с ошибками, которую нужно исправить.
- `before/` (`t13`, `t19`) — модули и драйвер до рефакторинга; дают тот же
  вывод. Модель получает модули `before/` без драйвера и целевой
  интерфейс — заголовки `ref/*.hpp` — и правит модули.
- `stub.cpp` (кроме задач на правку) — заготовка для модели на C++: те же
  объявления, что в `cm/stub.cm` и `dp/stub.dpm`, в записи эталона, с
  пустыми телами.
- `cm/` — то же на dpl (шаг 0.4): решение `sol.cm` в варианте A (B и C
  печатаются из него переводчиком `bench/syntax/cm.py`) и драйвер
  `driver.cpp` на C++ для переведённого интерфейса — один на все варианты;
  `stub.cm` — заготовка для модели: объявления, на которые опирается
  драйвер, с пустыми телами. У `t12` вместо заготовки — `buggy.cm`; у
  `t13` — `before/` (с ним модель и начинает), `ref/` и
  `before_driver.cpp`.
- `dp/` — то же на настоящем dpl (v0.1, шаг 13; язык `docs/spec/core.md`):
  решение `sol.dpm`, заготовка `stub.dpm` (у задач на исправление —
  `buggy.dpm`) и драйвер `main.dpm` на dpl (`import sol`). У задач на
  рефакторинг — модули `before/` и
  `ref/`, драйверы `main.dpm` (новый интерфейс) и `before_main.dpm`
  (старый). Свой `expected.txt` — только где запись чисел другая (`t14`:
  `f64` кратчайшей записью, Р48); численно он равен ожидаемому задачи.
  Проверка — `bench/dp_check.py`, проход `bench` в `tests/run.py`.

В опыте (шаг 0.5) модель получает `task.md`, начальный код и, на
вариантах dpl, краткую спецификацию варианта; драйвер и `expected.txt`
скрыты. Решение принято, если вывод драйвера совпадает с `expected.txt`.
Сборка задания и проверка — `bench/experiment.py` (`bench/README.md`).

## Проверка

```sh
python3 bench/run_refs.py          # входит в tools/check/run.sh
python3 bench/run_refs.py --bless  # переписать expected.txt — только осознанно
python3 tests/run.py -k bench/     # варианты dp/ на настоящем компиляторе
```

Решения на dpl проверяет `python3 bench/syntax/run_variants.py` (тоже в
`tools/check/run.sh`): исходник в каноническом виде; в каждом варианте —
разбор, идемпотентная печать, перевод, сборка и вывод, равный
`expected.txt`; задачи на правку — та же проверка на непустоту;
заготовка совпадает с интерфейсом решения. Заготовки `stub.cpp` и задания
опыта проверяет `python3 bench/experiment.py selftest` (шаг «обвязка»).

Эталоны собираются с `-Wall -Wextra -Werror`, без исключений и RTTI, под
ASan и UBSan (если компилятор их умеет). Задачи на правку проверяются на
непустоту: `buggy.cpp` **не** проходит; при рефакторинге старый драйвер со
старыми модулями даёт тот же вывод, а новый драйвер со старыми модулями
**не** проходит. `--bless` — только после ручной сверки вывода
с постановкой; дифф `expected.txt` — на ревью.
