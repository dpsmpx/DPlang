# Эталонный набор задач (v0.0, шаг 0.1)

Мера целей языка (`docs/direction/GOAL.md`, раздел 2): одни и те же задачи
решаются на C++ и на вариантах синтаксиса DPlang (`ROADMAP/IMPLEMENTATION.md`,
v0.0). Набор — **внутренний материал** (Р5): не публикуется. Кода VoxelRPG
в нём нет — задачи описаны заново и лишь похожи по роду на работу движка и
игры.

## Устройство задачи

- `task.md` — постановка и интерфейс (в нейтральной записи: в каждом
  варианте синтаксиса интерфейс записывается своим способом).
- `ref.cpp` — эталон на C++20: над строкой `// --- driver ---` — решение,
  под ней — драйвер, печатающий результаты. У задачи из нескольких
  модулей (`t13`) вместо него каталог `ref/`: модули и драйвер `main.cpp`.
- `expected.txt` — ожидаемый вывод драйвера.
- `buggy.cpp` (только `t12`) — версия с ошибками, которую нужно исправить.
- `before/` (только `t13`) — модули и драйвер до рефакторинга; дают тот же
  вывод. Модель получает `before/` и новый драйвер и правит модули.
- `cm/` — то же на DPlang (шаг 0.4): решение `sol.cm` в варианте A (B и C
  печатаются из него переводчиком `bench/syntax/cm.py`) и драйвер
  `driver.cpp` на C++ для переведённого интерфейса — один на все варианты;
  `stub.cm` — заготовка для модели: объявления, на которые опирается
  драйвер, с пустыми телами. У `t12` вместо заготовки — `buggy.cm`; у
  `t13` — `before/` (с ним модель и начинает), `ref/` и
  `before_driver.cpp`.

В опыте (шаг 0.5) модель получает `task.md`, краткую спецификацию варианта
и драйвер на этом варианте и пишет решение; решение принято, если вывод
драйвера совпадает с `expected.txt`.

## Проверка

```sh
python3 bench/run_refs.py          # входит в tools/check/run.sh
python3 bench/run_refs.py --bless  # переписать expected.txt — только осознанно
```

Решения на DPlang проверяет `python3 bench/syntax/run_variants.py` (тоже в
`tools/check/run.sh`): исходник в каноническом виде; в каждом варианте —
разбор, идемпотентная печать, перевод, сборка и вывод, равный
`expected.txt`; задачи на правку — та же проверка на непустоту;
заготовка совпадает с интерфейсом решения.

Эталоны собираются с `-Wall -Wextra -Werror`, без исключений и RTTI, под
ASan и UBSan (если компилятор их умеет). Задачи на правку проверяются на
непустоту: `buggy.cpp` в `t12` **не** проходит; в `t13` старый драйвер со
старыми модулями даёт тот же вывод, а новый драйвер со старыми модулями
**не** проходит. `--bless` — только после ручной сверки вывода
с постановкой; дифф `expected.txt` — на ревью.
