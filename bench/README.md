## Обвязка опыта

Модель решает задачу набора на C++, на варианте dpl (A, B, C —
прототип v0.0) или на dpl (`dp` — настоящий компилятор v0.1, шаг 13),
зная язык только по спецификации. Решают субагенты сессии с
чистым контекстом, одновременно — не больше 2–3 (Р35).

```sh
python3 bench/experiment.py prepare RUN [--tasks t01,t05] [--langs cpp,A] [--attempts 5] [--agent-model M] [--series]
python3 bench/experiment.py check DIR          # единственная проверка, доступная модели
python3 bench/experiment.py session RUN TASK|series LANG --tokens N [--tool-uses K] [--seconds S]
python3 bench/experiment.py tokens RUN [--model M]   # нужен ANTHROPIC_API_KEY
python3 bench/experiment.py report RUN [--save]      # --save — в bench/results/RUN/
python3 bench/experiment.py restore RUN [--force]    # из bench/results/RUN/ обратно в рабочий каталог
python3 bench/experiment.py selftest           # шаг «обвязка» в tools/check/run.sh
```

### Ячейка, песочница, журнал

Ячейка — задача × язык (`cpp`, `A`, `B`, `C`, `dp`). Варианты есть у
задач с каталогом `cm/`, `dp` — у задач с `dp/`; `prepare` пропускает
языки, которых у задачи нет. Прогоны лежат в
`$DPL_EXP_WORK`, по умолчанию — `build/experiment/` (не в git):

| путь | что |
|---|---|
| `RUN/tNN/LANG/PROMPT.md` | задание: правила, постановка, у `t13` — целевой интерфейс, у вариантов — спецификация варианта с образцами, у `dp` — спецификация ядра |
| `RUN/tNN/LANG/src/` | начальный код; модель правит только его |
| `RUN/_log/tNN/LANG/meta.json` | задача, язык, коммит, компилятор и флаги, предел попыток, модель субагента, расход сессии |
| `RUN/_log/tNN/LANG/attempts.jsonl` | попытки: номер, время, класс, вывод проверки, хэши файлов |
| `RUN/_log/tNN/LANG/attempt-0/`, `attempt-N/` | начальный код и снимок кода на каждой проверке |
| `RUN/_log/tNN/LANG/tokens.json` | счёт токенов ячейки |

### Что получает модель

Одно и то же для всех языков: постановку, язык, начальный код. Драйвер,
`expected.txt` и эталоны скрыты — модель узнаёт о них только из
проверки.

| | C++ | вариант dpl (A, B, C) | dpl (`dp`) |
|---|---|---|---|
| постановка | `task.md` | `task.md` | `task.md` |
| язык | строка сборки (C++20, `-Werror`, без исключений и RTTI, ASan и UBSan) | спецификация варианта `docs/research/syntax/spec_X.md` с образцами | спецификация ядра `docs/spec/core.md` с раздела 1 |
| начальный код: написать | `stub.cpp` — объявления, на которые опирается драйвер | `cm/stub.cm` в записи варианта | `dp/stub.dpm` как `src/sol.dpm` |
| начальный код: исправить (`t12`) | `buggy.cpp` над чертой драйвера | `cm/buggy.cm` в записи варианта | `dp/buggy.dpm` как `src/sol.dpm` |
| начальный код: рефакторинг (`t13`) | модули `before/` без `main.cpp` | модули `cm/before/` в записи варианта | модули `dp/before/` |
| целевой интерфейс (`t13`) | `ref/*.hpp` | открытые объявления `cm/ref/*.cm` без тел, в записи варианта | импорты и `pub`-объявления `dp/ref/*.dpm`, тела функций — `// ...` |

Субагенту отправляется только «Прочитай `<песочница>/PROMPT.md` и
выполни задание оттуда.» — `PROMPT.md` сам говорит, где работать,
какой командой проверять и сколько попыток.

### Проверка

`check` собирает решение из `src/` (на варианте — переводит прототипом
`bench/syntax/cm.py`, на `dp` — компилятором dpl `dpl build`,
`dp_check.py`) со скрытым драйвером, запускает и сравнивает вывод с
ожидаемым построчно (у `dp` — `dp/expected.txt`, если он есть). Печатает номер попытки, класс и **первую**
ошибку — одинаково для всех языков; число ошибок сборки — в скобках.

| класс | что |
|---|---|
| `разбор` | dpl: синтаксическая ошибка (файл, строка, столбец; у `dp` — коды E01xx и E02xx); нет файлов решения |
| `перевод` | вариант: ошибка, найденная переводчиком (неизвестный вариант, пометка аргумента, …) — с именем функции |
| `сборка` | ошибка компиляции в коде модели; у варианта — в переведённом C++, с именем функции dpl; у `dp` — диагностика компилятора с местом и фрагментом кода |
| `интерфейс` | драйвер не собирается с решением: изменены или не написаны объявления, которые он вызывает (у `dp` — ошибки только в драйвере) |
| `ловушка` | запуск упал: ловушка опоры dpl, ASan, UBSan, иной код возврата |
| `время` | драйвер не закончил за 20 с |
| `вывод` | вывод расходится: первая несовпавшая строка, ожидаемая и полученная |
| `прототип` | сбой самого переводчика, а не решения: попытка разбирается вручную |
| `компилятор` | `dp`: внутренняя ошибка компилятора dpl или окружения (коды 2 и 3) — разбирается вручную |
| `принято` | вывод совпал |

Попыток — не больше 5 (`--attempts`); после «принято» и после последней
попытки проверка не собирает код. Каждая попытка пишется в журнал вместе
со снимком кода.

### Меры

| мера | как |
|---|---|
| правильность | ячейка принята или нет |
| с первой попытки | принята на попытке 1 — «без исправлений» (`GOAL.md`, раздел 2) |
| циклы | номер принятой попытки; путь — классы попыток по порядку |
| прочитано на входе | токены `PROMPT.md` и начального кода |
| диагностик | токены всех выводов проверки |
| написано | токены строк, новых или изменённых от снимка к снимку, начиная с начального кода; оценка снизу — без повторённых при правке строк и без рассуждений |
| решение | токены последнего снимка |
| сессия | полный расход субагента (чтение, рассуждения, вывод) из итога инструмента Agent, если он его сообщает, — записывается командой `session` |

- Токены считает `POST /v1/messages/count_tokens` (Р35) по ключу из
  `ANTHROPIC_API_KEY`; модель счёта — `--model`, по умолчанию
  `claude-opus-5-5`, она же должна быть моделью субагентов (токенизатор
  зависит от модели). Каждый текст считается одним сообщением; постоянная
  обвязка сообщения — несколько токенов — одинакова для всех языков.
  Кэш счёта — `token_cache.json` в каталоге прогонов, по тексту и модели.
- Без ключа `tokens` сообщает об этом, `report` показывает символы.
- Сводка `report` складывает меры только по задачам, принятым на всех
  языках прогона: токены сравниваются между решениями, равными по
  корректности (`GOAL.md`, раздел 2).
- Повторяемость: проверка и счёт одной и той же ячейки дают те же числа
  (снимки, кэш). Разброс самой модели — несколько прогонов (`r1`,
  `r2`, …) и сравнение их сводок.

### Порядок прогона (шаг 0.5)

1. `prepare RUN --agent-model M` — песочницы всех ячеек.
2. На каждую ячейку — субагент (инструмент Agent, одна модель на все
   ячейки) с единственным сообщением «Прочитай `<песочница>/PROMPT.md` и
   выполни задание оттуда.»; одновременно — не больше 2–3.
3. По итогу субагента — `session RUN tNN LANG --tokens …` из его расхода.
4. После каждой партии ячеек — `report RUN --save` и коммит с пушем:
   рабочий каталог не в git, а сессию может оборвать лимит. В
   `bench/results/RUN/` — сводка `summary.md`, данные `summary.json`,
   журналы и задания ячеек (`log/tNN/LANG/PROMPT.md`).
5. `tokens RUN`, затем `report RUN --save`. В новой сессии прогон
   сначала возвращается из `bench/results/` командой `restore RUN`; так
   же досчитываются токены, когда появится ключ.
6. Отчёт — `docs/audits/<дата>-syntax-experiment.md`, решение — О1.

### Серия (Р-17)

В обычном прогоне ячейка — отдельная сессия субагента. Поэтому
спецификация читается в каждой ячейке заново, и чтение перевешивает
экономию в коде (риск Р-17). Серия мерит другой случай: несколько
изменений в одной сессии.

- `prepare RUN --series` создаёт ячейки как обычно и, кроме них, задание
  серии на каждый язык — `RUN/series/LANG/PROMPT.md`. В нём один раз
  правила, затем задачи по порядку, у каждой — своя папка и своя команда
  `check`, в конце один раз спецификация. `PROMPT.md` ячейки — только
  ссылка на задание серии.
- На каждый язык — один субагент с сообщением «Прочитай
  `RUN/series/LANG/PROMPT.md` и выполни задание оттуда.»
- Попытки, журнал и снимки — по ячейкам, как обычно.
- Расход всей сессии записывает `session RUN series LANG --tokens …` в
  `RUN/_log/_series-LANG.json`. Копия задания серии лежит рядом, в
  `_series-LANG.PROMPT.md`.
- `prepare --doc guide` даёт dpl вместо спецификации ядра краткое
  руководство `docs/guide/README.md` (приёмы с примерами); выбор
  записывается в `meta.json` (`doc`).
- `report` добавляет раздел «Серии». В нём задание серии в символах и
  расход сессии на одну принятую задачу — главная мера целей
  (`GOAL.md`, раздел 2) при нескольких изменениях на сессию.

### Ограничения

- Песочница изолирована правилом в `PROMPT.md`, а не системой:
  субагент технически может прочитать репозиторий или сам запустить
  компилятор. Нарушение не видно в журнале; при подозрении (принято без
  попыток сборки, необъяснимо быстрое исправление) ячейка перепроверяется
  новым прогоном.
- Варианты проверяет прототип, а не компилятор: ошибки типов приходят
  сообщениями компилятора C++ по переведённому коду (с именем функции
  dpl), ловушки — из опоры `bench/syntax/cm_rt.hpp`. Это сдвигает
  циклы исправления не в пользу dpl. Язык `dp` проверяет настоящий
  компилятор: диагностика и ловушки — его собственные (ворота К-2).
- «Написано» — оценка снизу; полный расход — мера «сессия».

### Самопроверка

`selftest` (шаг «обвязка» в `tools/check/run.sh`, после сборки
компилятора) на всех задачах и их языках проверяет: в `PROMPT.md` есть
команда проверки и спецификация (варианта или ядра), у `dp`-рефакторинга —
целевой интерфейс, нет драйвера и ожидаемого вывода; `src/` — начальный
код; на `cpp`, `A` и `dp` начальный код не проходит с ожидаемым классом
(заготовка — `сборка`, исправление — `вывод` или `ловушка`, рефакторинг —
`интерфейс`), а эталон принимается; на `B` и `C` начальный код и эталон
переводятся; `stub.cpp` собирается с драйвером и называет те же функции,
что `cm/stub.cm` и `dp/stub.dpm`; путь модели — проверка, повтор, предел попыток, журнал,
отчёт, `tokens` без ключа; сохранение в `bench/results/` и `restore` дают
те же тексты для счёта.
