Задание опыта: решить по очереди 4 задач в одной работе.

## Правила

- Задачи решаются по порядку, следующая — после того, как кончилась предыдущая. У каждой задачи своя папка (в её разделе): читай этот файл и `src/` папки задачи, правь файлы в её `src/`. Других файлов не открывай, по диску и в сети не ищи.
- Компилятор и другие программы сам не запускай. Проверка задачи — только командой из её раздела. Она собирает его со скрытым драйвером, запускает и сравнивает вывод с ожидаемым; печатает «принято» или первую ошибку.
- Попыток проверки на задачу — не больше 5, каждая записывается. Проверяй, когда решение готово целиком, а не для разведки.
- Задача кончается на «принято» или когда попытки кончились. Ответ в конце — по строке на задачу: задача, номер последней попытки и её итог.

### t20. Фоновая сборка по заказу

Игровой цикл заказывает сборку чанков в фоне и забирает готовые
результаты опросом раз в кадр, не дожидаясь их. Новый заказ того же
чанка делает прежний устаревшим. Менеджер может уйти раньше, чем
кончились заказы.

#### Интерфейс

- `build(chunk: i64, seed: u64) -> i64` — дано в заготовке: чистая
  дорогая функция (сборка чанка).
- `Cmd` — структура команды сценария: `kind: i32`, `chunk: i64`,
  `seed: u64`.
- `run(script: ссылка на список Cmd, limit: i32) -> список str` —
  исполняет команды по порядку и возвращает строки вывода:
  - `kind = 0` — **заказ**: номер заказа — следующий по порядку (с 1);
    сборка `build(chunk, seed)` идёт в фоне, игровой цикл её не ждёт;
    заказ делает устаревшими прежние заказы того же чанка;
  - `kind = 1` — **кадр**: забрать готовые результаты, не больше `limit`
    за кадр, не ожидая остальных; результат устаревшего заказа
    выбрасывается, остальные применяются: значение чанка — результат;
  - `kind = 2` — **сверка**: дождаться всех заказов и забрать все
    результаты (без предела, устаревшие — выбросить), затем добавить
    строку `sync K: C1=V1 C2=V2 ...` — `K` — номер сверки (с 1), чанки с
    применённым значением по возрастанию; без них — `sync K:`;
  - `kind = 3` — **уход**: менеджер уходит, не дожидаясь незаконченных
    заказов; их результаты не применяются; остальные команды не
    исполняются.

  `limit >= 1`. Функция может вернуться, пока сборки ещё идут (после
  ухода); программа при этом не должна падать или терять память иначе
  чем по правилам языка.

Сборки идут в нескольких потоках одновременно; общих изменяемых данных
без синхронизации нет.

#### Проверки

Драйвер — `expected.txt`: сценарий из заказов, кадров и сверок с
устаревшими заказами, уход с незаконченными заказами, пустой сценарий.

### t22. Три расчёта одновременно, буфер на рабочего

Три разных расчёта над одним списком слов идут одновременно (fork-join);
первый из них сам делится между рабочими, и у каждого рабочего свой
буфер, который он переиспользует от слова к слову.

#### Интерфейс

- `Stats` — структура: `distinct: список i64` (27 чисел), `longest: str`,
  `anagrams: i64`.
- `analyze(words: ссылка на список str, workers: i32) -> Stats` — три
  расчёта идут одновременно; функция возвращает, когда кончились все:
  1. `distinct[k]` — число слов, в которых ровно `k` разных букв `a`–`z`
     (другие байты не считаются). Слова делятся между `workers`
     рабочими (`workers >= 1`) частями подряд: рабочий `w` берёт слова с
     номерами от `n * w / workers` до `n * (w + 1) / workers` (без
     последнего). У каждого рабочего — свой буфер из 26 отметок, который
     он очищает перед каждым словом (без нового выделения на слово);
     счётчики рабочих складываются после;
  2. `longest` — первое из самых длинных слов (длина в байтах); у пустого
     списка — пустая строка;
  3. `anagrams` — число пар соседних слов `words[i]`, `words[i+1]`,
     которые анаграммы друг друга: у них одинаковые счётчики байтов
     (одинаковые слова — тоже анаграммы).

Работа действительно идёт в нескольких потоках; общих изменяемых данных
без синхронизации нет.

#### Проверки

Драйвер — `expected.txt`: большой список при 1, 4 и 7 рабочих (итог не
зависит от их числа), пустой список, малые списки.

### t23. Рабочие с общими счётчиками и флагом остановки

Несколько рабочих берут работы из общего счётчика, складывают итоги в
общие атомарные счётчики и останавливаются все, когда один нашёл
плохую работу.

#### Интерфейс

- `cost(v: i64) -> i64` — дано в заготовке: чистая дорогая функция.
- `Totals` — структура: `ok: bool`, `bad: i64`, `count: i64`, `sum: i64`,
  `odd: i64`.
- `run_jobs(jobs: ссылка на список i64, workers: i32) -> Totals` —
  `workers` рабочих (`workers >= 1`) работают одновременно. Рабочий берёт
  номер следующей работы из общего счётчика (каждый номер — одному
  рабочему, по возрастанию) и, пока не поднят флаг остановки:
  - `jobs[j] < 0` — плохая работа: поднять флаг и записать `j` в общий
    наименьший номер плохой работы;
  - иначе `r = cost(jobs[j])` и добавить в общие счётчики: `count` +1,
    `sum` + `r`, `odd` +1, если `r` нечётно.

  Счётчики, флаг и наименьший номер — общие атомарные значения; списков
  результатов рабочие не собирают. Итог: если плохая работа была —
  `ok = false`, `bad` — наименьший номер плохой работы, остальные поля 0;
  иначе `ok = true`, `bad = -1` и счётчики.

Рабочие берут номера по возрастанию, поэтому наименьшая плохая работа
находится всегда, сколько бы рабочих ни было, хотя часть работ после неё
может быть сделана зря.

#### Проверки

Драйвер — `expected.txt`: работы без плохих при 1, 4 и 8 рабочих, с
плохими, пустой список, малые списки.

### t24. Общая таблица: читают многие, пишет один

Один писатель меняет общую таблицу, несколько читателей одновременно
читают её целиком. Чтение не должно видеть изменение наполовину.

#### Интерфейс

- `Move` — структура: `from: i32`, `to: i32`, `amount: i64`.
- `Report` — структура: `table: список i64`, `reads: i64`, `bad: i64`.
- `run_bank(accounts: i32, moves: ссылка на список Move, readers: i32,
  reads: i32) -> Report` — таблица из `accounts` счетов, у каждого
  вначале 1000. Одновременно идут:
  - **писатель** (один) — переводы по порядку: со счёта `from` на `to`
    переводится `amount`, а если на `from` меньше, — всё, что на нём есть
    (`from == to` — ничего не меняется);
  - **читатели** (`readers >= 1`) — каждый делает `reads` чтений: чтение —
    сумма всех счетов. Перевод сумму не меняет, поэтому верное чтение
    всегда видит `accounts * 1000`.

  Таблица общая; перевод и чтение синхронизированы так, что чтение не
  видит перевод наполовину. Итог: `table` — счета после всех переводов
  по номеру, `reads` — сколько чтений сделано (`readers * reads`), `bad` —
  сколько чтений увидели другую сумму (у верного решения 0).

#### Проверки

Драйвер — `expected.txt`: много переводов при 1 и 4 читателях, малые
таблицы.
